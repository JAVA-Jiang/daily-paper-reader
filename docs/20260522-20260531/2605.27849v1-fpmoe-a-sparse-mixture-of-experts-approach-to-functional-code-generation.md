## 摘要
尽管基于大语言模型的代码生成取得了快速进展，但现有模型主要针对命令式语言训练，导致函数式编程语言（如Haskell、OCaml和Scala）长期未被充分探索，即使是前沿模型在FPL上的表现也明显较差。微调是一种自然的补救措施，但我们的实验表明，针对单一语言的微调未能捕获共享的函数式抽象，而合并的多语言微调则引入了跨语言干扰。为了解决这个问题，我们提出了FPMoE，一个轻量级的开源代码生成模型，基于稀疏混合专家（MoE）架构，包含三个特定语言的路由专家（分别对应Haskell、OCaml和Scala）以及一个共享专家，用于捕获跨语言的函数式模式，如单子推理和类型导向编程。这种设计同时解决了两种失败模式：专用专家消除了干扰，而共享专家保留了单一语言模型遗漏的抽象。在FPEval上，FPMoE显著优于微调基线模型，并且仅使用3B个激活参数，就能与包括DeepSeek-Coder-6.7B、Qwen2.5-Coder-14B-Instruct和Qwen3-Coder-30B-A3B在内的更大模型性能相媲美。

## Abstract
Despite rapid progress in LLM-based code generation, existing models are predominantly trained on imperative languages, leaving functional programming languages (FPLs) such as Haskell, OCaml, and Scala chronically underexplored, with even frontier models performing substantially worse on FPLs. Fine-tuning is a natural remedy, but our experiments show that per-language fine-tuning fails to capture shared functional abstractions, while merged multi-language fine-tuning introduces cross-language interference. To address this, we introduce FPMoE, a lightweight, open-source code generation model built on a sparse Mixture-of-Experts (MoE) architecture with three language-specific routed experts (one each for Haskell, OCaml, and Scala) and a shared expert that captures cross-language functional patterns such as monadic reasoning and type-directed programming. This design resolves both failure modes simultaneously: dedicated experts eliminate interference, while the shared expert preserves abstractions that per-language models miss. On FPEval, FPMoE substantially outperforms fine-tuned baselines and, with only 3B active parameters, matches the performance of much larger models including DeepSeek-Coder-6.7B, Qwen2.5-Coder-14B-Instruct, and Qwen3-Coder-30B-A3B.

## 1. 核心问题与整体含义（研究动机和背景）
- **问题**：现有LLM-based代码生成模型主要针对命令式语言（如Python、Java）训练，在函数式编程语言（FPL）如Haskell、OCaml、Scala上表现大幅下降。即使前沿模型（如GPT-5、Claude Opus）也存在显著的习语性违反（FPViolation）。
- **微调的两难**：单语言微调无法捕获跨语言的函数式抽象（如monadic推理、类型导向编程）；多语言混合微调则引入跨语言干扰，导致各语言性能退化。标准方法无法同时解决这两个失败模式。
- **动机**：FP社区代码数据规模小且增长缓慢，仅靠扩大预训练数据难以弥合差距。需要架构上更高效的利用现有FP数据的方法。

## 2. 论文提出的方法论
- **核心思想**：采用稀疏Mixture-of-Experts（MoE）架构，显式引入语言身份作为路由偏置。
  - 三个语言专用路由专家（E₁: Haskell, E₂: OCaml, E₃: Scala），每个从对应语言微调模型初始化。
  - 一个始终激活的共享专家（E_shared），从混合语言微调模型初始化，用于捕获跨语言函数式模式。
- **关键技术细节**：
  - **训练三阶段**：
    1. 专家预训练：①独立对每个语言SFT，得到三个专用检查点；②对混合语料SFT，得到共享专家初始化。
    2. MoE组装：将专用FFN权重放入路由专家，混合语言FFN权重放入共享专家，路由器和共享门控随机初始化。
    3. 联合MoE微调：在整个混合语料上联合训练，优化因果语言建模损失 + 负载平衡损失（L_aux）。
  - **MoE-FFN块**：每个Transformer层中，FFN子层被替换为N=3个路由专家（Top-K=2激活）和一个共享专家。共享专家输出通过可学习标量门控λ = σ(w_λ^T h + b_λ)调节。最终输出 h' = o_routed + λ·o_shared。

- 架构专门化比单纯数据扩展对FP代码生成更有效：混合语料微调（"add more FP data"）仍受跨语言干扰，远不如FPMoE。

## 7. 优点
- **创新性**：首次将语言身份显式作为路由偏置引入MoE代码生成模型，并设计始终激活的共享专家来捕获跨语言抽象。
- **轻量高效**：仅需3B/6B活跃参数即取得与大规模模型竞争的性能，适合资源受限部署。
- **实验严谨**：消融实验设计系统，分别验证共享专家初始化、共享专家存在性、语言预热等组件的必要性和贡献。
- **开源**：模型公开，可复现验证。
- **全面评估**：不只看功能正确率，还评估习语风格违反率（FPViolation），更贴近实际工程需求。

## 8. 不足与局限
