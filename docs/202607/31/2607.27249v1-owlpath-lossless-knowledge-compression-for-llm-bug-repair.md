## 摘要
基于大型语言模型的软件工程智能体受限于有限的上下文窗口：大约10万词元（token）内必须存储结构相关的代码子集以解决缺陷。标准检索模型将代码视为纯文本，迫使智能体通过缓慢的试错过程来解析多跳依赖关系，包括子类链、传递调用者和接口实现。我们通过无损知识压缩来应对这一限制，将源代码编码为OWL2本体，以使用最小相关代码片段回答结构查询。我们提出了OwlPath，一个构建在CodeGraph之上的OWL2推理层，CodeGraph是一个广泛使用的代码智能平台，拥有超过50万的GitHub星标，为结构代码检索提供了统一的命令行界面。凭借tree-sitter解析的支持，OwlPath支持多语言仓库（Python、JavaScript、TypeScript、Go等），并将语言特定语义编码为统一的OWL2本体。它采用两个互补模块。首先，一个传递闭包引擎通过单次SPARQL属性路径查询获取所有结构关联符号，捕获字符串匹配所遗漏的多跳关系。其次，OWL软件知识图谱（OWL-SKM）预计算了一个紧凑的3KB摘要，包含模块树、核心API和与问题相关的符号，引导智能体在首次查询中定位目标模块。在18个SWE-bench Pro实例上的评估中，OwlPath的严格应用率为68.4%，而CodeGraph基线为66.7%，同时将词元使用量减少了28.8%，运行时间缩短了39.5%。在67个实例的离线检索测试中，OwlPath将召回率提升了2.06倍（0.464对0.226），命中率达到88.1%，而CodeGraph为59.7%。在一个37题的结构检索基准测试中，召回率从4.4%提升至28.8%，在传递调用者和接口任务上的准确率达到69%-80%。”}

## Abstract
LLM-based software engineering agents are constrained by limited context windows: roughly 100K tokens must store structurally relevant code  subsets to resolve bugs. Standard retrieval models treat code as plain text, forcing agents to resolve multi-hop dependencies including subclass  chains, transitive callers and interface implementations through slow trial and error. We tackle this limitation with lossless knowledge  compression, encoding source code into an OWL2 ontology to answer structural queries using minimal relevant code fragments.   We present OwlPath, an OWL2 reasoning layer atop CodeGraph, a widely used code intelligence platform with 500K+ GitHub stars, offering a unified  CLI for structural code retrieval. Powered by tree-sitter parsing, OwlPath supports multi-language repositories (Python, JavaScript,  TypeScript, Go, etc.) and encodes language-specific semantics into a unified OWL2 ontology. It adopts two complementary modules. First, a  transitive-closure engine fetches all structurally linked symbols via single SPARQL property-path queries, capturing multi-hop relations missed  by string matching. Second, the OWL Software Knowledge Map (OWL-SKM) precomputes a compact 3KB summary with module trees, core APIs and  issue-related symbols, directing agents to target modules in the first query.   Evaluated on 18 SWE-bench Pro instances, OwlPath obtains a 68.4% strict-apply rate versus 66.7% for the CodeGraph baseline, cutting token usage  by 28.8% and runtime by 39.5%. In offline retrieval tests over 67 instances, OwlPath improves recall 2.06 times (0.464 vs 0.226) and reaches  88.1% hit rate compared to CodeGraph's 59.7%. On a 37-question structural retrieval benchmark, recall rises from 4.4% to 28.8%, with 69-80%  accuracy on transitive caller and interface tasks.

## 1. 核心问题与整体含义

- **核心困境**：LLM软件工程智能体受限于上下文窗口（约100K token），无法直接处理包含数百万行代码的整仓代码库，必须**先检索出结构相关的代码子集**，才能进行缺陷修复推理。
- **现有检索方式的根本缺陷**：grep、BM25、嵌入检索等方法都将代码当作**扁平文本**处理，只返回包含匹配字符串的文件，无法捕捉bug真相与问题描述之间**无字符串重叠、仅靠结构关联**的依赖关系，例如：
  - 子类链（subclass chains）
  - 传递调用者路径（transitive caller paths）
  - 接口实现层级（interface implementation hierarchies）
- **论文主张**：通过**无损知识压缩**（lossless knowledge compression）——将源代码编码为OWL2本体——使结构查询能够以最少的相关代码片段作答，从根本上弥补文本匹配的盲区。

## 2. 方法论

### 2.1 核心思想
在CodeGraph（tree-sitter解析生成的SQLite代码图）之上构建一层OWL2推理层，将代码的结构关系（继承、调用、接口实现、包含、引用、导入）编码为带传递性声明的本体断言，从而用**SPARQL属性路径**在单次查询中完成多跳关系遍历。

### 2.2 系统架构（三阶段流水线）
1. **提取**：tree-sitter将源码解析为SQLite代码图（节点为类、函数、方法、接口等符号，边为`extends`、`implements`、`calls`、`references`、`contains`、`imports`等关系）。
2. **投影**：单条SQL语句将每个节点映射为`owl:NamedIndividual`，每个边映射为OWL断言；`extends`、`implements`、`calls`、`imports`声明为`owl:TransitiveProperty`。投影是**双射**——不丢失任何结构信息，这是"无损"的保证。
3. **查询服务**：运行时通过SPARQL 1.1属性路径（如`:extends+`、`:calls+`）执行传递闭包查询。

### 2.3 两个互补机制
- **传递闭包引擎**：首次查询时物化一次全闭包（O(n+m)），此后查询为摊还O(1)的哈希查找。对比SQL递归CTE的O(n^k)最坏复杂度，对≥3跳查询有数量级优势。
- **OWL-SKM咨询层**：预计算约3KB的压缩摘要，包含两个层级：
  - **Layer 1（模块地图）**：基于文件树解析出的模块层级，按信息密度打分（`score = log(symbols)×0.5 + log(files)×0.3 + log(symbols_per_file)×0.2`），选出核心模块。
  - **Layer 2（问题地图）**：从问题描述和测试补丁中提取4–8个关键词（camelCase、snake_case、大写标识符），运行`codegraph explore`收集问题相关符号候选。
  - 该摘要仅在智能体**首次调用** `owlpath search` 时输出一次，引导其首次查询即命中正确模块。

### 2.4 核心公式与理论保证
- **无损投影定理**：对于任意SPARQL属性路径P和锚点a，OwlPath结果`R_owl`包含所有结构可达的地面真值集合Δ，即`R_owl(G,q) ⊇ Δ`。
- **BFS–SPARQL等价定理**：图上的BFS遍历与SPARQL传递闭包查询产生相同结果。
- **复杂度定理**：一次物化O(n+m)时间、O(n²)空间；后续查询摊还O(1)；SQL递归CTE的k跳查询为O(n^k)。
- **信息及时性定理**：当信息相关性不确定且信息体量超过上下文一半容量时，**按需策略严格优于强制注入策略**——这是论文实验发现的核心理论解释。

1. **端到端效率显著提升**：18条匹配实例上严格应用率68.4%（13/19）vs 66.7%（12/18），token消耗减少28.8%，墙钟时间减少39.5%，API调用减少16.7%。
