## 摘要
仓库级代码生成需要在考虑复杂的跨文件依赖和项目特定约定的同时实现目标函数。现有的检索方法主要依赖词汇、结构或语义相似性，往往忽略了那些尽管标识符或应用领域不同但实现相似过程逻辑的仓库函数。我们提出ProjAgent，一个仓库级代码生成系统，它将过程相似性作为显式的检索信号。ProjAgent将目标函数分解为中间推理步骤，并采用代理工作流来检索在每一步中表现出相似过程行为的仓库函数。检索到的过程上下文与传统的语义检索相结合，为代码生成构建更丰富的仓库上下文。ProjAgent进一步引入了一个保守的静态分析反馈循环，利用编译器和静态分析反馈迭代修复生成的代码。在REPOCOD上的评估显示，ProjAgent达到了41.14%的Pass@1，超越了现有的基于检索的基线。这些结果表明，过程相似性对于仓库级代码生成是一个有效且此前未被探索的检索维度。

## Abstract
Repository-level code generation requires implementing target functions while accounting for complex cross-file dependencies and project-specific conventions. Existing retrieval methods predominantly rely on lexical, structural, or semantic similarity, often overlooking repository functions that implement similar procedural logic despite differing in identifiers or application domains. We propose ProjAgent, a repository-level code generation system that introduces procedural similarity as an explicit retrieval signal. ProjAgent decomposes the target function into intermediate reasoning steps and employs an agentic workflow to retrieve repository functions that exhibit similar procedural behavior at each step. The retrieved procedural context is integrated with conventional semantic retrieval to construct a richer repository context for code generation. ProjAgent further incorporates a conservative static-analysis feedback loop that iteratively repairs generated code using compiler and static-analysis feedback. Evaluated on REPOCOD, ProjAgent achieves 41.14% Pass@1, outperforming existing retrieval-based baselines. These results demonstrate that procedural similarity is an effective and previously unexplored retrieval dimension for repository-level code generation.

# 论文详细总结：ProjAgent: Procedural Similarity Retrieval for Repository-Level Code Generation

## 1. 核心问题与整体含义（研究动机和背景）

仓库级代码生成（Repository-Level Code Generation）相比于独立函数生成更具挑战性，因为它需要处理跨文件的依赖关系、项目特定的 API 和约定。现有检索方法（如 BM25、密集嵌入搜索）主要依赖词汇、结构或语义相似性，但它们经常忽略那些虽然标识符或应用领域不同但实现了相似过程逻辑的函数。例如，两个函数分别来自不同模块，都执行“输入验证并抛出异常”这一计算模式，但函数名、变量名完全不同，导致现有检索方法无法召回。这种**过程相似性**（procedural similarity）是未被利用的检索维度。本文提出 ProjAgent，通过显式捕捉过程相似性来补充传统检索信号，从而构建更丰富的仓库上下文，提升目标函数生成的质量。

## 2. 方法论

### 核心思想
将目标函数分解为若干个中间推理步骤（target steps），然后使用代理化工作流（agentic workflow）从仓库中检索出与每个步骤过程相似的上下文函数。同时结合传统语义检索（lexical + semantic）提供仓库特定的符号信息（API、类、常量等）。最后通过静态分析反馈循环迭代修复生成代码。

### 关键技术细节
1. **离线预处理阶段**  
   - 从仓库中筛选出包含目标函数最多的多个文件（按目标函数数量排序，取前20个文件），提取其中的上下文函数。  
   - 将每个上下文函数分解为逻辑步骤（step），每个步骤包含自然语言描述和对应代码片段。  
   - 对每个步骤进行**三重验证**：  
     (1) 描述是否存在于函数 docstring 中（ROUGE-L > 0.7）；  
     (2) 代码片段是否存在于原函数体；  
     (3) 使用嵌入模型检查描述与代码片段的一致性（余弦 > 0.75）。  
   - 对每个通过验证的步骤，提取其隐藏状态（hidden states）并投影到“推理子空间”（reasoning subspace），形成投影向量。投影方法基于 Hu et al. 提出的 SVD 分解（对 unembedding 层参数矩阵做 SVD，取非主导奇异值对应的右奇异向量构成推理子空间）。  
   - 为解决各向异性（anisotropy）问题，额外引入 PCA 去偏：计算所有投影向量的均值和第一主成分，然后从每个投影向量中减去均值和沿第一主成分的分量。

2. **过程上下文检索**  
   - **初始种子发现**：对每个目标步骤，计算其投影与所有候选步骤投影的余弦相似度，保留高于阈值 0.75 的 Top 20 候选，再用 LLM 验证是否真正过程相似，得到初始种子。  
   - **代理种子发现**：使用一个 LLM 代理（配备 `ls`, `read_func`, `search_func` 等工具）主动探索仓库，寻找尚未被分解的潜在相关函数，并验证其步骤是否过程相似。为防止上下文溢出，对探索历史采用 LLM 压缩策略。  
   - **种子扩展**：对于每个目标步骤，利用已知种子，从已处理的步骤中筛选出与至少两个种子投影相似度 > 0.65 的候选步骤（避免冗余），再用 LLM 验证 Top 30。  
   - **计划确认**：将找到的过程上下文呈现给 LLM，判断是否足够实现该步骤；若不足，更新步骤描述并进入下一轮迭代（最多 5 轮）。

3. **语义检索**  
   - 基于目标文件中的 import 语句，通过静态分析追踪所有可访问的文件，构建符号池（函数、类、常量）。  
   - 对每个目标步骤，将步骤描述与检索到的过程步骤描述拼接成增强查询，与每个符号计算 BM25 和 Dense 得分的加权平均（各0.5），取 Top 20 作为语义上下文。

4. **代码生成与反馈循环**  
   - 将过程上下文和语义上下文格式化后，与目标步骤描述一起输入 LLM，生成代码。  
   - 静态分析反馈：先后进行 AST 语法检查、方法调用检查、字段访问检查、变量-方法检查、独立函数调用检查，仅报告可确认的错误。  
   - 将错误反馈重新输入 LLM 要求修改，重复最多10次。

## 6. 主要结论与发现

1. **ProjAgent 达到 SOTA**：REPOCOD 上 Pass@1 为 41.14%，分别超越 SPARSE（26.58%）、DENSE（28.83%）、SAME_FILE（14.98%）、SpecAgent（34.52%）。
