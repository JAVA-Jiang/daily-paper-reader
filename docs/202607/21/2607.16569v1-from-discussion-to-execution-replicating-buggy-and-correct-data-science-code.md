## 摘要
由于问题规格不明确、依赖缺失和性能瓶颈，从非正式来源复现可靠的数据科学代码具有挑战性。尽管开发者问答论坛提供了关于诊断和修复实际问题的丰富讨论，但信息往往不完整且非结构化，限制了其在自动调试和验证中的应用。在本文中，我们介绍了Reprodgen，一种基于大语言模型（LLM）的框架，用于从问答论坛帖子中自动复现可执行的缺陷和补丁数据科学程序。给定一个问题及其对应的答案，Reprodgen重建问题中描述的缺陷行为以及答案中描述的预期修复，生成可执行的缺陷和补丁代码对，反映原始讨论。该框架构建代码意图（CI）、功能需求（FR）和结构化思维链（SCoT）的结构化表示，并使用基于LLM的审查员迭代优化代码，直到代码可执行且语义一致。我们在七个数据科学库（包括pandas、numpy和scikit-learn）的Stack Overflow（SO）和GitHub Issues（GI）上评估了Reprodgen，并构建了一个由人类专家验证的可运行缺陷和补丁程序基准。我们的流程使用LLM进行语义评估，而可执行性则通过实际执行验证。结果显示可靠的复现，模型性能存在明显差异。

## Abstract
Reproducing reliable data science code from informal sources is challenging due to ambiguous problem specifications, missing dependencies, and performance bottlenecks. Although developer Q&A forums provide rich discussions on diagnosing and fixing real-world issues, the information is often incomplete and unstructured, limiting its use for automated debugging and verification. In this paper, we introduce Reprodgen, a large language model (LLM) based framework for automatically replicating executable buggy and patched data science programs from Q&A forum posts. Given a question and its corresponding answer, Reprodgen reconstructs the buggy behavior described in the question and the intended fix described in the answer, producing executable buggy and patched code pairs that reflect the original discussion. The framework builds structured representations of code intent (CI), functional requirements (FR), and Structured Chain of Thought (SCoT), and iteratively refines code using an LLM-based reviewer until it is executable and semantically consistent. We evaluate Reprodgen on Stack Overflow (SO) and GitHub Issues (GI) across seven data science libraries, including pandas, numpy, and scikit-learn, and construct a benchmark of runnable buggy and patched programs validated by human experts. Our pipeline uses LLMs for semantic assessment, while executability is verified through actual execution. Results show reliable replication with clear differences in model performance.

开发者问答论坛（如 Stack Overflow、GitHub Issues）中包含了大量关于数据科学代码调试和修复的讨论，但这些讨论通常信息不完整、缺少依赖、执行上下文和示例数据，导致难以从中自动复现可执行的代码。现有方法要么只能生成不可执行的代码片段，要么无法同时合成 buggy 代码与其对应的修复代码。这阻碍了自动化调试、补丁生成和基准测试的开展。论文旨在填补这一空白：**从非正式文本讨论中自动生成可执行的 buggy-patched 代码对**，从而为数据科学程序的调试与修复研究提供可靠、可复现的基准。

## 2. 论文提出的方法论：核心思想、关键技术细节
**核心思想**：基于大语言模型（LLM）的 Generator–Reviewer 双角色框架，通过结构化中间表示（Code Intent, Functional Requirements, Structured Chain of Thought）指导代码生成，并通过执行验证和 LLM 审查器迭代细化，直至代码可执行且语义忠实于原始讨论。

**关键技术细节**：
- **整体流程**：
  1. **Q&A 解析**：提取问题与选定答案。
  2. **思想生成（Thought Generation，可选阶段）**：生成三种结构化中间产物：
     - **Code Intent (CI)**：描述开发者意图的高层规范（buggy 和 patched 版本）。
     - **Functional Requirements (FR)**：用户期望的输入-输出行为，独立于实现。
     - **Structured Chain of Thought (SCoT)**：逐步推理过程，描述如何从输入到输出。
  3. **代码生成**：基于上述产物（或直接基于问题-答案）生成可执行的 buggy 和 patched 代码，同时推断依赖和生成模拟数据（mock data）。
  4. **执行验证与审查**：在隔离的 Docker 容器中执行代码，捕获标准输出、错误流和退出码。若执行失败，将错误反馈给生成器细化。LLM 审查器判断代码行为是否与原始讨论一致（标签：Correct/Partially Correct/Incorrect/Unknown），并提供理由用于再次细化。每个子任务最多迭代 3 次。
- **Generator–Reviewer 协作**：生成器 LLM 负责产生候选代码，审查器 LLM 负责评估语义忠实性。角色可互换。
- **可执行性保证**：通过实际执行（Docker 隔离环境）验证，而非仅静态分析。

## 6. 论文的主要结论与发现
- **RQ1（有效性）**：Qwen 2.5-Coder 和 Gemma 3 在开放模型中表现出最强的整体性能。Buggy 代码复现的成功率普遍高于 Patched 代码（因为 buggy 代码更直接可见）。
- **RQ2（可靠性）**：Gemma 3 和 Qwen 3 作为审查器时最可靠（平均覆盖加权 F1 分别为 0.88 和 0.86）。所有模型在文本子任务（CI, FR, SCoT）上表现良好，但在代码级评估（尤其是 patched 代码）上性能显著下降。
- **RQ3（效率）**：Gemma 3 生成速度最快，Qwen 2.5 需要最少的执行迭代来稳定 patched 代码。更快的模型不一定更高效，因为可能需要更多细化轮次。
- **其他发现**：
  - Guidance 能显著提升可执行性（ER），但对 SR 影响不显著。
  - 开放模型对输出格式的遵守不一致，依赖推理能力弱。
  - 手动提供已接受的答案有助于提升补丁质量，但并非必需。

## 8. 不足与局限

- **语义过滤偏差**：初始过滤排除了许多未明确描述 bug 的帖子，可能遗漏模糊但有价值的案例。

- **环境推断困难**：LLM 难以推断正确的库版本和依赖关系，可能导致环境配置错误。
