## 摘要
我们提出了ARBIGRAPH，一个用于评估工具辅助语言代理在扩展推理工作流中能否保留、更新、组合和丢弃任务相关上下文的基准生成器。ARBIGRAPH将每个任务表示为一个自然语言问题，并配备可执行的Python求解器，通过类型化的中间状态（此处实例化为标量和列表值）来组合任务。这种设计能够生成可控制的任务图，其长度、依赖结构、干扰项数量和值类型均可变化，同时保持精确的自动验证。我们使用数学、GSM风格的文字问题和Python跟踪任务类别实例化ARBIGRAPH，并在四种拓扑结构上评估了Qwen3.5-27B工具辅助代理。结果显示，在孤立任务上准确率很高，但在更复杂的依赖任务上显著下降：在依赖数学任务的分支链上准确率下降高达33.3%。这表明ARBIGRAPH揭示了仅通过单任务评估无法发现的失败。我们的代码、生成的数据集和评估结果可在https://github.com/pavelgolikov/ArbiGraph.git获取。

## Abstract
We introduce ARBIGRAPH, a benchmark generator for evaluating whether tool-assisted language agents can retain, update, compose, and discard task-relevant context across extended reasoning workflows. ARBIGRAPH represents each task as a natural-language problem with an executable Python solver, and composes tasks through typed intermediate states, instantiated here as scalar and list values. This design enables controllable task graphs whose length, dependency structure, distractor count, and value type can be varied while preserving exact automatic verification. We instantiate ARBIGRAPH with math, GSM-style word-problems, and Python-tracing task categories, and evaluate a Qwen3.5-27B tool-assisted agent across four topologies. The results show high accuracy on isolated tasks but substantial degradation on more complex dependent tasks: accuracy drops by up to 33.3% on branching chains of dependent math tasks. This shows that ARBIGRAPH exposes failures that are not visible from single-task evaluation alone. Our code, generated datasets, and evaluation results are available at https://github.com/pavelgolikov/ArbiGraph.git

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：语言模型代理（tool-assisted language agents）在解决复杂、多步骤推理任务时，不仅需要局部问题求解能力，更需要**上下文管理能力**——即保留有用信息、更新中间状态、丢弃无关或过时信息。现有基准（如长上下文、多轮对话、记忆评估）已经显示出模型受干扰项、位置偏移和长历史记录的影响而失败，但这些失败并非总是知识或局部推理的失败，更多是上下文维护、更新或丢弃的失败。
- **研究背景**：现有评估通常通过长文档、对话或记忆历史来研究此问题，但往往固定了组合模式（如打包独立问题、指令序列、依赖链或类型化操作符），而不是将依赖拓扑本身作为受控变量来测试代理是否能够保留、传播、总结或丢弃中间任务状态。需要一个能够独立变化上下文长度、依赖结构和值类型，支持用户指定任务图拓扑，并区分局部任务失败与状态传播、选择性遗忘或跨任务干扰失败的基准。

## 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：将上下文视为**类型化的计算状态**（typed computational state）。每个任务节点是一个自然语言子问题，配备可执行的Python求解器。任务通过类型化中间状态（本论文中实例化为标量和列表值）进行组合。任务图可以是用户指定的任意DAG，节点依赖关系通过显式命名输出变量（如`task_i_out`）表示。
- **关键技术细节**：
  - **任务节点**：一个任务节点由输入`x_i`、预处理适配器`a_i`、自然语言提示`p_i`、后处理适配器`b_i`、输出`y_i`和可执行求解器`s_i`组成。求解器仅用于生成地面真值，代理不可见。
  - **任务组合**：当一个任务依赖于另一个任务时，其提示会引用前一个任务的输出变量名。生成器同时存储所有中间输出和最终答案，以便后续分析。图构造通过匹配输出类型和输入类型实现。
  - **适配器**：预处理和后处理适配器用于将中间数据（标量/列表）转换为任务特定格式，例如截断/填充列表、模运算、类型强制转换等。这控制了单个任务的复杂度，防止大图中复杂度爆炸。实验中适配器将列表长度限制为10，标量幅度限制为100。
  - **任务类别**：
    - **数学任务**：40个手工选择的算子，覆盖4种类型签名（list→list, list→scalar, scalar→scalar, scalar→list），来自线性代数、多项式、离散变换、组合数学、几何和数论。
    - **Python追踪任务**：80个来自LeetCode Dataset的算法，要求代理追踪具体函数在具体输入上的执行，而不是编写代码。每个任务保留原始LeetCode标识符和难度标签。
    - **GSM-style文字题**：标量到标量类别，基于GSM-Symbolic模板，增加自然语言算术变体。
- **拓扑结构**：四种评估拓扑（图2所示）：
  - Baseline：仅目标任务，测量基本求解能力。
  - Forgetting：目标任务前放置3个无关干扰任务，测量丢弃无关信息的能力。
  - Chain：线性依赖路径（4个任务），输出传递给下一个任务，测量状态传播能力。
  - Multichain：分支依赖图，中间状态分裂、独立演化、再合并，最后到目标任务（8个任务）。仅适用于支持列表输出的任务（数学和Python追踪，GSM只有标量输出无法生成multichain）。

- **对比方法**：本文未与其他模型或agent方法对比，仅评估Qwen3.5-27B这一种模型，属于初步单模型验证。

## 6. 论文的主要结论与发现

- Baseline准确率在所有任务上都高（数学94.5%，Python追踪96.8%，GSM 100.0%），说明目标任务本身局部可解。
- Forgetting拓扑产生较小但一致的下降（数学→89.2%，Python→92.5%，GSM不变），表明干扰上下文会降低性能。
- Chain拓扑中数学准确率大幅下降至75.5%，Python追踪90.1%，GSM 96.0%。
- Multichain拓扑中数学进一步下降至61.2%（下降33.3%），Python追踪保持90.5%。
- **关键发现**：上下文管理负担在不同任务类别间不均匀：数学链对传播状态错误最敏感，Python追踪更鲁棒。ArbiGraph成功区分了局部求解能力和上下文管理能力——高基线准确率并不保证高链/多链准确率。
- 过程指标（平均token数和回合数）显示，复杂拓扑不仅降低准确率，还显著增加推理开销。例如数学多链平均生成52K tokens、12回合，而基线仅10K/7回合。

## 7. 优点

- **方法论创新**：将上下文管理形式化为类型化计算状态和可验证任务图，使依赖拓扑本身成为可控变量。
- **自动验证**：所有任务都有可执行Python求解器，无需人工标注，可大规模生成。
- **任意可扩展**：用户可指定任意DAG，长度、干扰项、分支均可调节，为未来更复杂场景提供基础。
- **故障隔离**：通过修复协议（工具调用修复、输出修复、截断修复）减少机械性失败对结果的影响。
- **过程指标**：记录tokens、回合数等辅助信息，帮助区分推理失败与上下文管理失败。
- **跨类别覆盖**：数学、代码追踪、文字题三种不同风格的推理任务，增加实验多样性。

## 8. 不足与局限

- **实验覆盖有限**：仅评估了一种模型（Qwen3.5-27B）和一种agent设计（calculator tool），未对比其他模型系列（如GPT-4、Claude、Llama等）或不同工具配置。
