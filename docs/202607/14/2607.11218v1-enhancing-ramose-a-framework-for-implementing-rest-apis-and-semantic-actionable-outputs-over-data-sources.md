## 摘要
学术基础设施越来越多地通过遵循共享规范的REST API暴露其数据，例如科学知识图谱互操作性框架（SKG-IF），该框架为研究信息定义了通用数据模型、交换格式和REST API。然而，在现有数据源上实现此类规范需要许多开放基础设施无法承担的开发工作。RAMOSE（基于SPARQL端点的RESTful API管理器）是一个开源Python框架，通过将声明式配置文件转换为基于RDF三元组存储的有文档的REST API，减少了这一工作。本文介绍了其第二个主要版本，该版本通过九个新需求扩展了该工具。新功能包括跨多个SPARQL端点和非RDF源的查询编排，并对其结果进行连接；可插拔的输出格式和请求参数；分页和缓存；OpenAPI导出；以及写操作，并对API消费者和受保护端点进行身份验证。一个内置模块封装了SKG-IF规定的格式和过滤器，使提供者仅通过配置即可暴露兼容端点。与九种类似工具的功能比较（基于可重复测试）表明，只有RAMOSE能在一次API操作中对任意键连接RDF和非RDF结果。RAMOSE服务于OpenCitations REST API，该API在2025年5月至2026年5月期间峰值达到近3800万月请求，并已被GRAPHIA项目采用，用于将其数据源纳入基于SKG-IF的联邦中。

## Abstract
Scholarly infrastructures increasingly expose their data through REST APIs that follow shared specifications, such as the Scientific Knowledge Graph - Interoperability Framework (SKG-IF), which defines a common data model, exchange format, and REST API for research information. Implementing such specifications over existing data sources, however, requires a development effort that many open infrastructures cannot afford. RAMOSE, the RESTful API Manager Over SPARQL Endpoints, is an open-source Python framework that reduces this effort by turning a declarative configuration file into a documented REST API over RDF triplestores. This article presents its second major version, which extends the tool with nine new requirements. The new features include query orchestration across multiple SPARQL endpoints and non-RDF sources, with joins across their results; pluggable output formats and request parameters; pagination and caching; OpenAPI export; and write operations, with authentication both of API consumers and towards protected endpoints. A built-in module packages the format and filters that SKG-IF prescribes, letting a provider expose a compliant endpoint only through configuration. A functional comparison with nine similar tools, grounded in reproducible tests, shows that only RAMOSE joins RDF and non-RDF results on arbitrary keys within one API operation. RAMOSE serves the OpenCitations REST APIs, which peaked at almost 38 million monthly requests between May 2025 and May 2026, and has been adopted by the GRAPHIA project to onboard data sources into its SKG-IF-based federation.

### 2. 论文提出的方法论：核心思想、关键技术细节

**核心思想**：基于声明式配置（HF/YAML）实现中间件层，将 REST API 请求映射为对后端数据源的 SPARQL 查询或 SPARQL 更新，并支持多步骤的查询编排、结果连接、格式转换、缓存、分页与认证。

**关键技术细节**：

- **架构**：`APIManager` 路由请求，`Operation` 执行流水线（预处理→查询→后处理→缓存→分页→格式转换）。使用 SPARQL Anything 桥接非 RDF 源（CSV、JSON、XML、HTML 等）。
- **多源查询编排**：
  - `@@with source=...` 指定查询目标端点或后端引擎（sparql-anything 用于非 RDF）。
  - `@@join left_var=?x right_var=?y type=left/inner` 将新查询结果按变量值与当前累加器连接。
  - `@@values ?var` 将累加器中某变量值注入下一查询的 SPARQL VALUES 子句。
  - `@@foreach variable=?var placeholder=foo` 对每个不同值执行一次查询，`[[foo]]` 替换为当前值。
  - `@@page ?var` 在查询执行阶段进行实体级分页（避免后续查询处理所有实体）。
  - `@@remove ?var` 丢弃不再需要的变量。
- **可插拔输出格式**：`#format` 字段关联函数名，接收 CSV 表后返回任意格式（如 JSON‑LD）。
- **自定义请求参数**：通过 `#custom_params` 声明，可过程式（Python 函数）或声明式（YAML 文件定义 SPARQL 片段注入）实现。
- **分页与缓存**：
  - 内置行级分页（`page`/`page_size`），可被格式函数重写为实体级分页；`@@page` 在查询阶段分页。
  - 缓存以 SQLite 存储操作后结果表，键为 endpoint + operation URL + 数据参数（不含分页页号，除非使用 `@@page`），默认生存期 1 天，写操作清空全部缓存。
- **OpenAPI 导出**：从配置自动生成 OpenAPI 3.2 规范，包括自定义格式媒体类型、自定义参数、认证安全方案；在 `/docs` 路由提供 Swagger UI。
- **SKG‑IF 模块**：内置 `ramose.skg_if` 模块，提供预定义的输出格式 `skg_if` 和过滤器参数 `filter`（通过 YAML 映射 SKG‑IF 过滤器词汇到 SPARQL 片段）。
- **写操作与认证**：
  - 声明 `#method post/put/delete`；查询语句为 SPARQL Update；成功则清空缓存。
  - 消费者认证：`#auth required` 启用 Bearer Token 验证，令牌哈希存本地 SQLite。
  - 端点认证：通过环境变量为每个端点配置 Authorization 头部，转发至 SPARQL 端点。
