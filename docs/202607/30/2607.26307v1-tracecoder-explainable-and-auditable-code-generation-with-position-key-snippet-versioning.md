## 摘要
当代基于大语言模型的代码智能体产生代码时如同黑箱输出：每一行代码背后的原理是隐藏的，通过基准驱动修复的代码演变是短暂的，事后审计是不可能的。我们提出了一种代码生成概念，通过三种互补机制解决这些缺陷：(i) 关系型片段历史模式，记录每次修复事件中的基准参考、轮次、失败文本和大语言模型解释，实现完整的溯源查询；(ii) 基于浏览器的可视化工具，将此历史呈现为热图标注、悬停注释的源代码；(iii) 一种带树节点分隔符的竞争性分数位置键索引方案，为每个代码片段分配稳定且按字典序排列的标识符，实现细粒度跟踪而不干扰周围行。我们在30个算法编程任务上评估了TraceCoder，涵盖字符串处理、数学计算和数据结构操作，涉及两种提供商配置。其中，10个任务在具有微妙边界情况的行为上耗尽了6次迭代预算。平均Chg%达到30%，十分之三的代码片段带有可追踪的修复事件行，相比之下，在20个任务子集上仅使用Gemini 2.0 Flash作为唯一提供商时，该比例为21%。三个详细案例研究展示了系统如何解释最终程序的每一行由哪些特定基准失败塑造。所提出的机制使自动代码生成的内部“叙事”变得可审计和可重放，这对于生产部署中的信任和问责至关重要。

## Abstract
Contemporary LLM-based coding agents produce code as black-box outputs: the rationale behind each line is hidden, the evolution of the code through benchmark-driven repair is ephemeral, and post-hoc auditing is impossible. We present a code generation concept that addresses these shortcomings through three complementary mechanisms: (i) a relational snippet-history schema that records, per repair event, the benchmark reference, round number, failure text, and LLM explanation, enabling full provenance queries; (ii) a browser-based visualisation tool that renders this history as heat-mapped, hover-annotated source code; and (iii) a competitive fractional position-key indexing scheme with tree-node delimiters that assigns stable, lexicographically-ordered identifiers to each code snippet, enabling fine-grained tracking without disrupting surrounding lines. We evaluate TraceCoder on 30 algorithmic programming tasks spanning string processing, mathematical computation, and data-structure manipulation, across two provider configurations. Of these, 10 exhaust the 6-iteration budget on tasks with subtle edge-case behaviour. Mean Chg% reaches 30%, three in ten code snippets carry a traceable repair-event row, compared to 21% when using Gemini 2.0 Flash as sole provider on a 20-task subset. Three detailed case studies demonstrate how the system explains which specific benchmark failures shaped each line of the final program. The proposed mechanism makes the internal "narrative" of automated code generation auditable and replayable, a property essential for trust and accountability in production deployments.

## 1. 核心问题与整体含义（研究动机和背景）
- 当前基于大语言模型的代码生成智能体（如 GPT-Engineer、SWE-agent）将生成的代码视为黑箱输出。整个生成过程缺乏可解释性（为何某行代码以当前形式存在？）、可审计性（无法追溯决策链）和可追溯性（迭代修复中产生的边缘案例信息被丢弃）。
- 这在生产部署中引发三个关键问题：当代码行为异常时无法回溯根本原因；组织需要满足合规性要求，需证明每一行代码的测试依据；迭代修复循环本应提供丰富的语义信息，却未被记录。
- 核心洞察：迭代修复循环中的每次基准失败都是值得记录的因果事件，若能永久保存这些事件与代码片段的关联，就能建立可查询、可回放的代码叙事。

## 2. 方法论：核心思想、关键技术细节
### 核心思想
- 将代码生成视为一个可记录、可查询的带历史溯源的过程，每个代码片段（snippet）与其修改原因（基准失败、LLM解释）永久绑定，通过位置键确保稳定索引。

### 关键技术
- **竞争性分数位置键索引方案（FIS）**：
  - 设计目标：全局有序（ASCII比较）、支持任意位置插入/删除、保持键稳定、紧凑。
  - 字符集：base-64版本使用线性字符（0-9, A-Z, a-z）和树节点（以`.`开头、`-`结尾的内键）。ASCII保证了`-` < `.` < 数字 < 大写 < 小写。
  - 生成算法：
    - 初始键设为 `V`（中点）。
    - `KeyAfter(lo)`：在`lo`右侧生成新键，若其最后一个字符为`z`则递归扩展。
    - `KeyBetween(lo, hi)`：处理三种情况（一方耗尽、一方为树节点、两者为线性字符），递归或取中点返回新键。
  - 优势：无理论上的键数量限制，无需自定义比较器，平均键长接近最优。
- **关系型片段历史模式**：
  - 数据库模式（SQLite）包含三张核心表：`code`（当前代码片段及其位置键、创建/禁用轮次）、`snippet_failure`（每个修改过的片段每轮对应一个基准失败行）、`snippet_explanation`（每轮LLM根因文本）。
  - 每行代码的`position_key`唯一标识，修改时旧行被“墓碑标记”（enabled=0），新行插入并继承历史行（通过`inherits_key`）。
  - 支持对等、修改、移动、插入、删除五种差异操作，每类操作均保留完整溯源链。
- **智能体循环**：
  - 三个LLM操作：初始代码生成（`generate_initial_code`）、基准创建（`create_benchmark`）、代码修复（`fix_failing_code`）。修复时返回解释文本并直接存入数据库。
  - 循环可从中断状态重启（基于最大已记录轮次）。

## 7. 优点
1. **完整解决可解释性缺口**：首次将代码生成过程中的每个修复事件（基准失败、LLM解释、轮次）永久链接到具体代码片段，形成可查询、可回放的审计轨迹。
2. **创新的位置键索引**：FIS方案在理论上无边界的键数量、原生字符串比较、紧凑键长等方面超越现有分数索引方法，支持任意顺序的插入/删除而不破坏稳定性。
3. **轻量级且部署友好**：使用SQLite作为持久存储，无需额外基础设施；浏览器查看器独立于数据库，无需外部依赖；数据库大小极小（几十KB），历史开销在可接受范围内。
4. **模型无关**：方法适用于任何LLM提供商，实验验证了两个截然不同的配置。
5. **实际应用价值**：直接满足合规审计、回归分析、信任校准、开发者入职等生产需求。
