## 摘要
基于LLM的代码智能体通过与代码库和工具的迭代交互，已推动了仓库级软件开发的进展。然而，特性开发需要通过连贯的跨组件功能链将新行为集成到现有架构中。现有智能体通常通过自由形式推理推导此类功能链，往往产生功能链不完整、不可靠的特性设计。此外，文本设计难以验证和执行，使得在整个长周期开发中维持设计与实现的一致性颇具挑战。我们提出CodeSpec，一种面向仓库级特性开发的双重可执行规范方法。它通过将子需求语义与仓库架构配对形成证据，构建可靠的功能链，然后将其编译为互补的架构和行为规范，以检查链的完整性与正确性，同时在长交互中保持设计-实现一致性。在针对现有仓库特性开发的FeatureBench基准上，CodeSpec在DeepSeek-V4-Pro下分别达到70.7%、55.0%和49.9%的通过率，优于Claude Code等代表性基线。在仓库生成基准NL2Repo-Bench上的结果进一步证明了其泛化性。

## Abstract
LLM-based code agents have advanced repository-level software development through iterative interaction with codebases and tools. However, feature development requires integrating new behaviors into existing architectures through coherent cross-component functional chains. Existing agents typically derive such chains through free-form reasoning, often producing unreliable feature designs with incomplete functional chains. Moreover, textual designs are difficult to verify and enforce, making it challenging to maintain design-implementation consistency throughout long-horizon development. We propose CodeSpec, a dual executable specification method for repository-level feature development. It builds reliable functional chains from evidence pairing sub-requirement semantics with repository architectures, then compiles them into complementary architecture and behavior specifications that check chain completeness and correctness while preserving design-implementation consistency over long interactions. On FeatureBench, which targets feature development in existing repositories, CodeSpec achieves 70.7%, 55.0%, and 49.9% pass rates under DeepSeek-V4-Pro, outperforming representative baselines such as Claude Code. Results on the repository generation benchmark NL2Repo-Bench further demonstrate its generalizability.

- **意义**：提出一种可执行的双规范方法，通过将功能链转化为可自动检查的架构和行为规范，在长周期开发中持续保持设计-实现一致性，显著提升特征开发的可靠性。

## 2. 论文提出的方法论

### 2.1 核心思想
- 提出 **CodeSpec**，一种双可执行规范方法，包含两个核心组件：
  1. **证据增强的功能链构建**：将子需求语义与仓库架构证据（如设计模式、调用关系、依赖）配对，推导出仓库级可追溯的跨组件实现路径。
  2. **双可执行规范编译**：将每个功能链编译为两种互补的可执行规范 —— **架构规范**（检查路径完整性）和**行为规范**（检查运行时行为正确性），共同验证功能链的完整性和正确性。

### 2.2 关键技术细节
- **功能链构建**：
  - 将特性指令分解为子需求集合 `{r1, r2, ..., rm}`。
  - 为每个子需求 `ri` 识别候选实现单元 `{u1, u2, ..., un}`，并执行证据驱动的链推理：每个相邻单元对 `(uki, u(k+1)i)` 由成对的证据 `eki` 支持，证据包含需求语义和仓库架构信息。最终功能链为 `ci = {u1i, e1i, u2i, ..., uki, eki, u(k+1)i}`。

- **双可执行规范编译**：
  - **架构规范** `sarch_i`：基于模板 `τarch`，从 `ci` 生成三类检查：`CheckUnit`（验证功能单元存在）、`CheckRelation`（验证单元间架构关系，如调用、委托）、`CheckDataFlow`（验证数据流状态）。在执行时，缺失单元、断裂关系或中断数据流会被报告为局部架构违规。
  - **行为规范** `sbeh_i`：基于模板 `τbeh`，联合分析 `ci` 和 `sarch_i`，导出多个观测作用域（单元、过渡、子路径）上的检查：`CheckOutput`（输出正确性）、`CheckBoundary`（边界条件）、`CheckState`（状态转换）。执行时报告运行时行为违规。

- **规范引导的代码生成**：
  - 将所有子需求的架构规范 `Sarch` 和行为规范 `Sbeh` 聚合。
  - 智能体在实现过程中持续执行这两个规范，将违规反馈（`Farch`, `Fbeh`）用于后续编辑，直至全部通过或达到交互预算 `K`。
  - 算法流程（Algorithm 1）：循环执行代码生成、更新补丁、执行架构检查、执行行为检查，若全部通过则退出，否则继续迭代。

1. **总体性能领先**：在 FeatureBench 三个 split 上，CodeSpec 在 DeepSeek-V4-Pro 下均取得最高 `%Passed`（Lite 70.7%、Fast 55.0%、Full 49.9%）和最多 `#Resolved`（9、17、28），显著优于 OpenHands、Claude Code、Mini-SWE-Agent 和 RTADev。

3. **消融实验确认组件贡献**：

6. **成本增量适度**：平均成本增加仅 $0.01-$0.03/任务，换来持续的性能提升。

## 7. 优点

- **方法创新性**：将证据增强推理与可执行规范相结合，解决了自由形式推理和文本计划无法保证长周期一致性的核心痛点。双规范体系（架构+行为）互补覆盖路径完整性和运行时正确性。
- **设计可验证性**：规范本身是可执行的，能自动检测违规并给出精确定位（如缺失单元、断裂关系、错误输出），为智能体提供比自由文本更精准的迭代信号。
- **实验充分且公平**：多维度对比（方法、骨干模型、任务规模、交互预算）、系统性消融、统计显著性（bootstrap）、开源代码和数据（GitHub 地址），可复现性强。
- **泛化性优秀**：不仅在仓库演化任务（FeatureBench）上表现好，在绿色字段生成（NL2Repo）上也一致提升，表明方法不依赖于预存代码结构。
- **低成本收益比**：仅增加少量推理成本（$0.01-$0.03/任务），但带来显著性能增益，尤其是在长周期、高复杂度场景。

## 8. 不足与局限

- **语言与生态限制**：实验仅在 Python 仓库上进行（FeatureBench 和 NL2Repo 均为 Python），未验证 Java、TypeScript 等主流语言。证据增强和规范执行可能依赖 Python 的特殊工具（如 AST 分析），泛化到其他语言需额外工程适配。
- **基准规模有限**：FeatureBench Full 仅 200 任务，NL2Repo 104 任务，虽然相对已有基准更大，但仍然不足以完全覆盖真实开发场景的多样性。
- **硬任务增益有限**：在 NL2Repo Hard 上增益仅 1.1%（相对 RTADev），说明当前方法在处理极大型仓库（>4K LOC）时仍面临挑战，功能链构建和规范检查的准确性可能下降。
- **交互预算依赖**：方法成功依赖足够的交互次数（K=300 轮）。在预算紧张时，规范指导的优势可能无法充分发挥（论文未详细分析不同预算下的性能）。
- **未考虑真实人工反馈**：实验完全自动化，未模拟开发中的人工审查或需求澄清环节。规范生成本身依赖 LLM，存在幻觉风险，可能导致规范与实际需求不匹配。
- **成本虽低，仍有提升空间**：相对于 OpenHands（$0.09-$0.11/任务），CodeSpec 成本高出约 60%-100%，在工业大规模部署中可能需权衡。
