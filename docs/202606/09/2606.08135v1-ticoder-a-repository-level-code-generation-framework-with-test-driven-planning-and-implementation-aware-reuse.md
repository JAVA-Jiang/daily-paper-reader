## 摘要
使用大型语言模型（LLM）进行仓库级代码生成仍然具有挑战性，主要原因是复杂的依赖关系和有限的上下文窗口。最近的方法采用检索增强生成（RAG）和规划机制来重用仓库中潜在的被调用函数。然而，这些方法通常存在两个局限性：规划过程中缺乏测试驱动的行为指导，以及在重用过程中忽略了仓库代码中嵌入的实现逻辑。结果，生成的计划可能不符合预期行为，检索到的函数可能无法有效重用。在本文中，我们提出TICoder，一种新颖的仓库级代码生成框架，它改进了规划和重用两方面。TICoder引入了一种测试驱动的迭代规划机制，利用测试用例作为行为规范来细化实现步骤。此外，TICoder采用一种实现感知的代码重用策略，通过双视角相似性检索潜在的被调用函数，该相似性同时捕获功能和实现方面。然后，我们通过双阶段选择策略识别相关的使用模式，结合基于结构的聚类和基于困惑度的过滤。我们在广泛使用的仓库级代码生成基准上使用多种LLM进行了大量实验。实验结果表明，TICoder优于最先进（SOTA）方法，平均提升11.52%。

## Abstract
Repository-level code generation with Large Language Models (LLMs) remains challenging, primarily due to complex dependencies and limited context windows. Recent approaches adopt retrieval-augmented generation (RAG) and the planning mechanism to reuse potential callee functions in the repository. However, these approaches often suffer from two limitations: lack of test-driven behavioral guidance during planning and overlooking the implementation logic embedded in repository code during reuse. As a result, generated plans may not align with expected behaviors, and retrieved functions may not be effectively reused. In this paper, we propose TICoder, a novel repository-level code generation framework that improves both planning and reuse. TICoder introduces a test-driven iterative planning mechanism that leverages test cases as behavioral specifications to refine implementation steps. Furthermore, TICoder employs an implementation-aware code reuse strategy, which retrieves potential callee functions using a dual-view similarity that captures both functional and implementation aspects. We then identify relevant usage patterns through a dual-stage selection strategy, combining structure-based clustering and perplexity-based filtering. We conduct extensive experiments on widely used repository-level code generation benchmarks with various LLMs. Experimental results demonstrate that TICoder outperforms state-of-the-art (SOTA) methods, achieving an average improvement of 11.52%.

## 1. 核心问题与整体含义（研究动机和背景）
- **问题背景**：仓库级代码生成（Repository-Level Code Generation）因跨函数依赖、有限的上下文窗口而极具挑战。现有方法主要依赖检索增强生成（RAG）和规划机制，从仓库中检索相似代码片段或分解需求为步骤来指导生成。
- **核心局限性**：
  - **L1**：规划阶段缺乏测试驱动行为指导。仅从自然语言需求推导实现步骤，而需求往往模糊或不完整，导致计划不可靠。
  - **L2**：复用阶段忽视代码级实现逻辑。现有方法仅基于语义相似度检索功能，未考虑代码执行逻辑，检索到的函数难以被正确调用。
- **研究动机**：开发一个同时改进规划与复用的框架，以提升仓库级代码生成的效果。

## 2. 方法论文（核心思想、关键技术细节）
- **整体框架**：TICoder 分为三阶段：测试驱动迭代规划 → 实现感知复用 → 增强代码生成。
- **两阶段规划过程**：
  1. **初始计划生成**：LLM-as-planner 基于需求+测试用例，遵循五项原则（清晰可验证、边界条件、显式依赖、可维护性、适当分解）生成初始步骤序列（最大步数 n_s=5）。
  2. **迭代细化**：LLM-as-judge 从三个维度（功能覆盖与一致性、独立性、粒度）评分（0-100），若分数低于阈值（90）则反馈给planner细化，迭代至最大迭代次数 n_i。
- **实现感知复用**：
  - **双视图函数检索**：
    - 功能相似度 Sim_F：步骤描述与函数描述间的余弦相似度。
    - 实现相似度 Sim_I：为步骤生成的代码表示与函数实现的余弦相似度。
    - 联合得分：`Sim(i,j) = α * Sim_F(i,j) + β * Sim_I(i,j)`，α+β=1。排序后取每个步骤的 top-1 候选。
  - **双阶段使用模式选择**：
    - 基于调用图（RCG）识别候选调用者函数。
    - **结构聚类**：按调用函数集相同聚簇。
    - **困惑度过滤**：对每个簇中心计算 PPL（给定上下文预测需求的困惑度），保留最低 PPL 的簇中心；全局排序后选 top-n_p（实验取2）作为最终使用模式。
- **增强代码生成**：将需求、测试用例、检索到的 callee 函数集、选中的使用模式拼接为提示，由 LLM 生成最终代码。

## 6. 主要结论与发现
- **总体性能**：TICoder 在所有基准上一致超越 SOTA（平均相对提升 11.52%），最大提升出现在 DevEval 上（22.76%）。
- **消融发现**：移除任何子模块（规划、测试用例、迭代、双视图检索、使用模式、选择）都会导致性能下降，其中规划影响最大（↓6.87%），生成阶段去除测试用例影响最重（↓10.42%）。
- **迭代次数**：迭代细化普遍提升性能，但非单调，过多迭代可能引入噪声；最优迭代次数因 LLM 而异。
- **相似度权重**：功能相似度贡献大，但加入实现相似度可进一步改进；最优 α/β 依语言不同（Python：α=0.8，β=0.2；Java：α=0.6，β=0.4）。
- **使用模式数量**：n_p=2 达到最佳（比1提升5.56%），过多（3）则因冗余和 token 消耗而下降。
- **关键启示**：测试用例对规划和生成均至关重要；实现感知复用（双视图检索+使用模式选择）能显著提升函数检索和调用的准确性。
