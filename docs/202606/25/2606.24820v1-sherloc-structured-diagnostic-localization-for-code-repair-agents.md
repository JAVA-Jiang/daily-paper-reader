## 摘要
LLM代理通过多轮工具使用解决仓库级编码任务，但在编辑前将一半预算用于定位故障。专门的定位框架已经出现，但仍被评估为文件检索而非可操作诊断，产生的定位缺少修复代理所需的诊断上下文。我们提出SHERLOC（结构化假设驱动探索与推理定位），一个无需训练的框架，将推理LLM与紧凑的仓库工具和自我恢复相结合，无需微调或多代理编排。SHERLOC跨模型尺度达到最先进的定位：在SWE-Bench Lite上达到84.33%的accuracy@1，在SWE-Bench Verified上达到81.27%的recall@1；在约30B参数下，它匹配或优于其他代理方法。将我们的定位和诊断发现注入修复代理中，平均在SWE-Bench Verified上提升5.95个百分点的解决率，同时将定位和总token数分别减少36.7%和23.1%。

## Abstract
LLM agents solve repository-level coding tasks through multi-turn tool use, but utilize half their budget on locating faults before editing. Dedicated localization frameworks have emerged, yet are still evaluated as file retrieval rather than actionable diagnosis, producing locations without the diagnostic context a repair agent needs. We introduce SHERLOC (Structured Hypothesis-driven Exploration and Reasoning for Localization), a training-free framework pairing a reasoning LLM with compact repository tools and self-recovery, without fine-tuning or multi-agent orchestration. SHERLOC reaches state-of-the-art localization across model scales: 84.33% accuracy@1 on SWE-Bench Lite and 81.27% recall@1 on SWE-Bench Verified; at ~30B parameters, it matches or outperforms other agentic methods. Injecting our locations and diagnostic findings into repair agents yields, on average, +5.95 pp resolve rate on SWE-Bench Verified while cutting localization and total tokens by 36.7% and 23.1%.

#### 1. 核心问题与整体含义（研究动机与背景）

-   **核心问题**：当前基于LLM的代码修复代理（如SWE-Agent、OpenHands）在修复仓库级代码缺陷时，会消耗大量交互预算和token用于定位故障（平均48%的交互轮次和超过320k tokens）。然而，现有的定位方法（如文件检索、函数级定位）仅输出故障所在的文件或函数，**缺乏可操作的诊断上下文**（如根本原因分析、修复思路），导致下游修复代理仍需自行理解上下文，效率低下。
-   **研究动机**：作者假设，明确地提供**候选位置、根本原因分析和可操作的解决方案指导**，能形成更丰富、更具可迁移性的定位结果。论文围绕两个核心研究问题（RQ）展开：
    -   （RQ1）一个单一的推理LLM，配合紧凑的结构化工具接口，能否在没有微调或多代理编排的情况下，达到任务特定训练定位器的性能？
    -   （RQ2）这些定位结果和诊断发现何时、以及如何迁移到下游的代码修复任务，对解决率和token成本有何影响？
-   **整体含义**：本文主张，定位任务不应仅被评估为文件检索，而应被视为一种**结构化诊断**，其价值在于向修复代理传递可操作的、根因导向的上下文信息。

#### 2. 方法论：核心思想、关键技术细节

-   **核心思想**：SHERLOC是一个**无需训练**的框架，它将一个**推理型LLM**与一个**紧凑的、LLM友好的工具套件**以及**轻量级的自我恢复机制**相结合。其核心是将问题定位建模为一个**迭代的、工具中介的推理过程**。
-   **关键技术细节**：
    1.  **初始化与上下文构建**：首先过滤掉文档、构建文件等非核心目录，生成一个简化的仓库树视图，与问题描述、工具说明和输出格式要求一起作为初始提示。
    2.  **工具套件（Tool Suite）**：设计了四个紧凑、结构化的工具：
        -   `View File`：查看文件内容（支持行范围）。
        -   `Codebase Search`：仓库范围内的文字搜索。
        -   `Repository Tree`：展示过滤后的文件层级结构。
        -   `Connected Tree`：显示文件间的导入依赖关系。
    3.  **迭代交互循环**：
        -   LLM根据问题描述和当前观察决定下一步行动（工具调用或输出最终结果）。
        -   执行器解析并运行工具，将观察结果添加到对话历史。
        -   循环最多20轮，直到LLM输出格式化的最终答案。
    4.  **结构化诊断输出**：输出包含两大部分：
        -   **发现（Findings）**：结构化字段，包括位置解释、根本原因、解决方案思路、依赖关系和测试影响。
        -   **位置（Locations）**：预测的需要修改的代码区域（文件路径和行号范围）。
    5.  **自我恢复机制**：包含上下文截断、循环检测、隐式工具调用恢复、响应长度管理和最终轮强制合成，以提高系统在长时间交互中的鲁棒性。

#### 3. 实验设计：数据集、基准与对比方法

-   **数据集与基准**：
    -   **主基准**：`SWE-Bench Lite` (300个实例) 和 `SWE-Bench Verified` (500个实例)。
    -   **开发集**：`SWE-Gym` 用于组件消融实验。
-   **评估指标**：
    -   **文件级**：`Accuracy@1`， `Recall@1`， `F1`， `Exact Match`， `Set Accuracy`。
    -   **块级**：`Coverage Recall`， `Precision`， `Average Tightness` (针对行号区间)。
-   **对比方法**：
    -   **定位器**：`OrcaLoca`， `SWERank`， `SWE-Debate`， `Agentless`， `RepoSearcher`/`ToolTrain` 等。
    -   **修复代理**：`SWE-Agent` 和 `OpenHands` 两种框架，配合5种不同的LLM骨干网络。

#### 4. 资源与算力

-   **计算基础设施**：所有实验在内部计算集群上进行，使用 **NVIDIA H100 (80GB) 和 A100 (80GB) GPU**。
-   **模型服务**：基于 `sglang` (定位) 和 `vLLM` (下游修复) 提供服务。
-   **算力消耗**：
    -   30B参数量级的模型使用2-4块GPU；235B/480B级别的模型使用一个**完整的8-GPU节点**。
    -   论文所有实验（包括定位、消融、控制和下游修复）的总推断预算约为 **10,000 H100/A100 GPU-hours**。

#### 5. 实验数量与充分性

-   **实验数量**：实验设计非常全面，包括：
    -   **主定位实验**：在2个基准上评估4种骨干网络，每种3个随机种子。
    -   **组件消融实验**：分别对工具套件（4个工具）和自我恢复机制（5个机制）进行消融。
    -   **推理模式消融**：对比Thinking与Instruct模式。
    -   **隐式知识控制实验**：通过masked issue、masked paths等多种方式隔离基准数据污染。
    -   **下游代码修复转移实验**：在2种框架（SWE-Agent, OpenHands）和5种骨干网络上，测试了7种输入条件（Baseline, Masked, Shuffled, All SHERLOC, QF SHERLOC, Oracle等）。
    -   **质量阈值敏感性分析**：对质量过滤器的阈值进行扫描。
    -   **发现字段消融**：剥离诊断发现中的不同字段，分析其贡献。
-   **充分性与客观性**：
    -   **充分**：实验覆盖了定位任务的全链条和下游应用，包括详尽的消融、控制变量和迁移实验。
    -   **公平**：对比了多种先进的现成方法，使用方法统一的种子设置（3个种子取均值），并明确指出了自身方法的局限（如大型模型的计算成本更高）。控制实验（如shuffled、masked）精心设计，用以排除数据泄露等干扰因素。

#### 6. 主要结论与发现

1.  **定位性能SOTA**：SHERLOC在SWE-Bench Lite上达到84.33% accuracy@1，在SWE-Bench Verified上达到81.27% recall@1，显著超越了先前最优的定位方法（包括一些经过微调的模型）。
2.  **无需训练即可迁移**：SHERLOC能跨模型家族（如Qwen3、DeepSeek-V3、R1）取得优异表现，证明了方法的泛化性。
3.  **可诊断的上下文是关键**：与仅提供文件位置不同，SHERLOC提供的结构化诊断发现（特别是“解决方案思路”字段）是提升下游修复效率的核心。去除该字段，性能下降最明显。
4.  **下游修复收益**：将SHERLOC的输出注入现有代码修复代理，平均提升解决率 **+5.95个百分点**，同时将定位阶段的token消耗减少 **36.7%**，总token消耗减少 **23.1%**。
5.  **质量过滤器至关重要**：对于本身定位能力强的强模型，盲目注入所有发现可能造成负迁移。引入LLM质量评估与过滤，可以保留高质量发现带来的收益，同时规避低质量发现的干扰。
6.  **隐式知识混淆**：实验表明，部分定位性能来自LLM对公开基准的预训练熟悉度（隐式知识）。SHERLOC通过工具辅助的主动探索，可以显著提升在模型不熟悉仓库上的表现（约22pp的增益）。

#### 7. 优点

-   **无需训练**：框架无需任何微调或强化学习，降低了应用门槛。
-   **即插即用**：可以作为独立模块，无缝集成到现有代码修复框架中，显著提升其性能和效率。
-   **结构化、可操作的输出**：不只输出文件路径，还输出层次化的诊断信息（根本原因、解决方案），这些信息对下游任务价值巨大。
-   **方法设计精巧**：紧凑的工具套件和轻量级的自我恢复机制设计精良，有效了平衡探索能力和计算开销。研究发现定位失败主要是“选错文件”而非“搜错区域”，为后续优化提供了线索。
-   **实验严谨**：通过精巧的控制实验（如masked issues、shuffled findings），排除了常见的数据污染和偶然性因素，强化了结论的可信度。

#### 8. 不足与局限

-   **隐式知识混淆**：近58%的定位召回率可以仅从问题描述文本中实现（尤见于流行仓库）。这表明SWE-Bench等基准测试并不能完美衡量代码推理能力，**存在严重的基准污染风险**。作者即使通过控制实验进行了量化，但此混淆无法完全消除。
-   **计算成本与规模**：最顶尖的定位性能依赖于235B参数量的大型模型，这带来了较大的计算成本。虽然在30B量级上表现同样出色，但最亮眼的结果使用的是大模型。
-   **基准与框架局限**：所有实验仅在 **SWE-Bench** 上进行，使用的修复框架也限于 **SWE-Agent** 和 **OpenHands**。对多语言、多模态、或使用不同框架（如GPT-Engineer）的情况，其泛化能力尚属未知。
-   **基于外部监督的质量过滤器**：质量过滤器（Quality Filter, QF）依赖于一个基于**ground-truth patch**进行评估的LLM判分器（GPT-5.2）。这使其在**实际部署**中不可用，因为它需要一个已知的错误修复补丁来做判断。这是一个分析阶段的实验，而非一个可用的测试时滤波器。
-   **提示敏感度**：不同模型对同一套提示指令的反应不同（如DeepSeek-R1的零工具调用率更高）。这意味着在迁移到新骨干网络时，可能需要进行模型特定的提示调整，而非完全即插即用。
