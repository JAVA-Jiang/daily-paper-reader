## 摘要
我们提出了一种基于依赖类型的证明器，其设计围绕LLM（以及人类）通常编写数学的方式，补充了Lean和Rocq等现有系统。其核心设计选择是模拟数学自然语言的外表，以及一个规则驱动的自动化层，用于填补教材通常会省略的常规步骤，使得被接受的证明可以重新输出为经过检查的Lean文件。早期实验表明，即使没有针对特定证明器的训练数据，LLM也能学会在miniF2F基准上有效地使用它。Lean输出摘录：https://github.com/xiyuzhai-husky-lang/visored/

## Abstract
We present a dependent-type-based prover designed around the way LLMs (and humans) tend to write mathematics, complementing existing systems such as Lean and Rocq. Its core design choices are a surface that imitates mathematical natural language and a rule-driven automation layer that closes the routine steps a textbook would omit, so that an accepted proof can be re-emitted as a checked Lean file. Early experiments suggest that, even without any prover-specific training data, LLMs can learn to use it effectively on the miniF2F benchmark. ## 1. 论文的核心问题与整体含义（研究动机和背景）
- **问题**：大型语言模型（LLM）生成的数学证明常因幻觉而不可信，需要经过形式化验证。但现有证明器（如 Lean、Rocq）要求严格的代码式语法，与 LLM 和人类书写数学的“自然语言”风格严重脱节；自动形式化（autoformalization）过程需要将非正式的数学散文映射为机器可检查的形式，其间涉及大量隐含假设（如类型转换、子类型、边缘情况约定），这些决策在表面文本中没有痕迹，而现有的全自动形式化管道在表面到语义的跃迁上表现欠佳。
- **整体含义**：本文主张，为 LLM 数学工作流设计证明器时，应优先使用接近自然语言的外表（controlled natural language, CNL），并通过规则驱动的自动化层填补教材中省略的常规步骤，从而降低 LLM 生成可验证证明的门槛。Visored 正是这一理念的原型实现，旨在成为连接 LLM 自然数学写作与形式验证的桥梁。

## 2. 论文提出的方法论：核心思想、关键技术细节
- **核心思想**：采用“受控自然语言”（CNL）作为输入表面，内部基于依赖类型中间表示（Visored MIR），并借助规则驱动的证明搜索（称为 Miracle 运行时）自动闭合“Then...”等步骤。接受后的证明可选转换为 Lean 4 源代码进行内核级再验证。
- **关键技术细节**：
  - **CNL 表面**：输入为嵌入 LaTeX 的受控自然语言句子模板（如 `Let ...`、`Assume ...`、`Then ...`），模板由外部 `.lpcsv` 规范文件定义，可扩展而不修改解析器。
  - **语法与语义阶段**：数学模式用优先级栈解析器，文本模式用字典树模式匹配。语义阶段进行名称解析、类型推断和种类（kind）分配，采用自底向上赋型，达到类型规范形式。
  - **类型检查时的良定义性**：模仿 PVS，在类型检查时强制执行良定义性条件（如 `1/x` 要求 `x ≠ 0`，`√x` 要求 `x ≥ 0`），这些条件同样由 Miracle 运行时自动证明。
  - **规则驱动的求解器**：Miracle 运行时使用代价约束的非确定性搜索（类似于 ProofGrader 的代价系统），包含前向规则库（Ashisogi Jizō）和后向规则库（Tekken Tachikaze），通过代价预算保证终止。
  - **Lean 发射**：接受后的证明经过 UVL MIR 中性中间表示，再由格式化器输出为 Lean 源文件。发射采用“稀疏方案”每条推导步骤对应一个私有 lemma，造成极大文件体积，但可调试性高。

## 7. 优点：方法或实验设计上的亮点
- **自然语言表面**：使得 LLM（尤其是未经过证明器专用微调的模型）能够自然生成可验证证明，大幅降低形式化门槛。
- **规则驱动的自动化**：通过代价约束的规则搜索闭合“教科书省略”的常规步骤，避免了全自动定理证明的不可判定性问题，与 LLM 提供的粗略 outline 互补。
- **层次化设计与可扩展**：语法、类型、求解器、发射完全解耦，且通过外部规范文件（.lpcsv）定义语言和规则，允许用户在不修改编译器的情况下扩展功能。
- **渐进式诊断**：失败时返回定位到具体源位置的诊断，比单个 Lean 编译失败提供更细粒度的反馈，适合 LLM 迭代修正或作为强化学习中的密集奖励信号。
- **可选 Lean 输出**：桥接了自然语言形式化与现有生态（Mathlib），虽然发射质量尚不理想，但证明了概念可行性。

## 8. 不足与局限
- **数学范围有限**：当前规则库和预置类型仅覆盖中代数、基本数论、集合论、部分分析，缺失 AM-GM 不等式、三角函数恒等式、有限域类型、极限推理等，导致 IMO 问题覆盖率低（35%）。
- **实验设计不完善**：仅在开发集上报告覆盖率，缺乏独立测试集评估和与基线系统的公平对比；消融实验缺失，无法判断各组件贡献。
- **Lean 发射极度冗长**：稀疏方案导致代码量巨大，增量编译慢，成为持续迭代的主要瓶颈；作者称为此代码库积累的“技术债务”，后续将采用更密集的方案。
- **求解器诊断信息不足**：失败时仅报告未闭合的目标和位置，不提供“哪条规则几乎匹配”或“最佳候选差距”等信息，限制 LLM 的修正效率。
- **工程成熟度低**：系统为早期原型，规则组织、规范文件布局、IR 边界仍在变化中，不适合稳定部署；作者称其为 evolving design。
- **类型系统的天花板**：有意采用轻量依赖类型，无法处理高阶归纳类型或复杂的依赖索引，难以覆盖更高级的数学领域。
- **副作用**：规则库的维护和添加新推导类型需要同时修改求解器侧和 Lean 侧，工作量呈工程两方性。
