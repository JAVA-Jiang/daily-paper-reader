## 摘要
本地LLM智能体（如OpenClaw和Nanobot）在终端用户机器上运行，并通过自然语言目标对主机资源（shell、文件系统、浏览器、存储的凭证和消息应用）进行操作。这些智能体已成为特权软件运行时，在用户意图、模型输出和主机级操作之间进行中介。现有研究通过提示注入、恶意技能、市场风险或智能体的黑盒评估来描绘这一领域。但执行这种中介的实现层——提示构建器、解析器、工具调度器、技能加载器、内存写入器、网络客户端和权限门——仍然是一个未经检查的安全边界。据我们所知，之前没有工作检查智能体的源代码树来审计这些组件的实现级安全弱点。我们提出了CLAWAUDIT，一个用于测量本地LLM智能体运行时中漏洞暴露的静态审计框架。CLAWAUDIT从STRIDE推导出五类漏洞分类，并开发了自定义静态分析规则，针对已建立漏洞分析规则集中缺失的智能体特定模式。我们在两个后端实例化该分类：47条Semgrep YAML规则和30条CodeQL查询，并在OPENCLAWBENCH上进行评估，该基准测试包含来自OpenClaw仓库的446个源代码级公告，并按时间分为229个规则推导（训练）和217个保留（测试）公告。在保留测试上，CLAWAUDIT将Semgrep召回率从21.7%（Pro基线）提升到66.8%，CodeQL召回率从13.8%（安全扩展）提升到75.1%。所有四种配置的训练/测试差距保持在4个百分点以内，表明规则能够泛化到规则编写时未见过的漏洞。初步的实时代码审计表明，这些关注召回率的规则需要手动分类，这促使在生产部署前进行语义过滤。

## Abstract
Local LLM agents such as OpenClaw and Nanobot run on end-user machines and act on host resources - the shell, filesystem, browser, stored credentials, and messaging applications - through natural-language goals. These agents have become privileged software runtimes that mediate between user intent, model outputs, and host-level actions. Existing research characterizes the landscape through prompt injection, malicious skills, marketplace risks, or black-box evaluation of agents. But the implementation layer that performs this mediation, the prompt builder, parser, tool dispatcher, skill loader, memory writer, network client, and permission gate, has remained an unexamined safety boundary. To our knowledge, no prior work has examined the agent's source tree to audit these components for implementation-level security weaknesses. We present CLAWAUDIT, a static auditing framework for measuring vulnerability exposure in local LLM agent runtimes. CLAWAUDIT derives a five-category vulnerability taxonomy from STRIDE and develops custom static-analysis rules that target agent-specific patterns absent from established rule sets for vulnerability analysis. We instantiate the taxonomy in two backends, 47 Semgrep YAML rules and 30 CodeQL queries, and evaluate on OPENCLAWBENCH, a benchmark of 446 source-code-level advisories from the OpenClaw repository and split temporally into 229 rule-derivation (train) and 217 held-out (test) advisories. On the held-out test, CLAWAUDIT raises Semgrep recall from 21.7% (Pro baseline) to 66.8%, and CodeQL recall from 13.8% (security-extended) to 75.1%. Train/test gaps remain within 4 percentage points for all four configurations, indicating that the rules generalize to vulnerabilities unseen during rule writing. A preliminary live-code audit shows that these recall-oriented rules require manual triage, motivating semantic filtering before production deployment.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：本地 LLM 智能体（如 OpenClaw、Nanobot）作为特权软件运行时，直接操控 shell、文件系统、浏览器、凭证和消息应用等主机资源。但其实现层（提示构建器、解析器、工具调度器、技能加载器、内存写入器、网络客户端、权限门）的安全边界从未被系统审计。现有研究聚焦于提示注入、恶意技能、市场风险和黑盒行为评估，而忽略了智能体自身源码中的实现级漏洞。
- **整体含义**：智能体运行时是连接用户意图、模型输出和主机操作的关键层，其中的代码缺陷可直接导致从不可信输入到主机特权操作的路径。该层未审计是巨大的安全盲区，本工作首次打开智能体的源码树进行系统审计。

## 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：基于 STRIDE 威胁模型推导出适用于本地 LLM 智能体运行时的五类实现级漏洞分类法，并针对每类开发自定义静态分析规则，在两个后端（Semgrep 和 CodeQL）中实现，从而检测运行时代码中的安全弱点。
- **技术细节**：
  - **漏洞分类法**：从 STRIDE 中排除 DoS（运行时不可静态观察）和抵赖（与实现弱点正交），保留篡改、权限提升、信息泄露、欺骗，并将“篡改”拆分为两类（提示处理和工具/技能执行），最终形成五个类别（CAT-1 提示处理、CAT-2 工具/技能执行、CAT-3 权限与隔离、CAT-4 网络与通信、CAT-5 身份验证与授权）。
  - **规则开发**：
    - 从 OpenClaw 的已披露安全公告（GHSA）中提取漏洞模式，编写 47 条 Semgrep YAML 规则（基于 AST 语法模板）和 30 条 CodeQL 查询（基于程序关系图与谓词推理）。
    - 每条规则针对具体的运行时边界（如 B1 提示构造前的净化、B2 操作数到执行的检查、B3 动作到资源的隔离等），并包含缺失守卫的检查逻辑。
  - **检测与归属**：原始发现为 (规则ID, 文件路径, 行号, 代码片段)；采用文件级归属：若发现落在修复公告所修改的文件中，则视为检测到该公告。

- **数据集**：构建 OPENCLAWBENCH，包含来自 OpenClaw 仓库 GitHub Security Advisories 的 446 个已披露的源审计级公告。按照发布时间分为训练集（229 个，2026-04-01 前）和测试集（217 个，2026-04-01 后）。每条公告附有严重性、CWE 类别和作者标注的漏洞分类。
- **基准对比**：
  - Semgrep 基线：Semgrep Pro（约 2,815 条内置 + 社区规则）。
  - CodeQL 基线：javascript-security-extended 查询套件（104 条内置查询）。
  - 两个基线分别与 +CLAWAUDIT 规则对比。
- **评估指标**：主要指标是公告级召回率（advisory-level recall），即被检测到的公告数占总公告数的比例。分别在训练集和测试集上报告。

## 5. 实验数量与充分性

- **实验数量**：
  - 在 OPENCLAWBENCH 的 446 个公告上评估了 4 种配置（Semgrep 基线、Semgrep+CLAWAUDIT、CodeQL 基线、CodeQL+CLAWAUDIT）的训练和测试召回率。
  - 按严重性（4 个等级）、按常见 CWE 类别（>5 条公告的类别）、按长尾 CWE 类别（5-15 条公告）分别报告召回率。

- **充分性评估**：
  - **充分**：实验覆盖了规则的泛化能力（训练/测试间隙<4pp）、不同严重性/种类的漏洞、两种不同分析引擎的对比，以及实时代码的精度初步评估。

## 6. 论文的主要结论与发现

1. **通用静态分析工具检测率低**：Semgrep Pro 在测试集上召回率仅 21.7%，CodeQL 安全扩展仅 13.8%，两者并集仅 31.3%。结构失配（通用规则面向 Web 应用，而非智能体运行时组件）是主因。
2. **智能体特定规则大幅提升召回率**：CLAWAUDIT 使 Semgrep 召回率提升至 66.8%，CodeQL 提升至 75.1%。提升在各类 CWE 和严重性等级上一致，尤其在符号链接跟随（0→86.7%）、路径遍历（16→83%）等具有可识别代码形状的漏洞上效果显著。
3. **规则良好泛化**：四种配置的训练/测试召回率差距均在 ±4pp 以内（Semgrep+CLAWAUDIT 为 +1.3pp，CodeQL+CLAWAUDIT 为 -3.9pp），表明规则捕获了运行时漏洞的重复结构而非记忆训练集。
4. **实时代码精度低，需人工分类**：HEAD 扫描产生数千条发现，抽样 50 条仅 6 条为真正的模式匹配（精度 12%）。规则被调校为高召回，导致大量误报，生产部署前需语义过滤。
5. **基于规则的方法在语义定义弱点上停滞**：CWE-184（不完整拒绝列表）、CWE-200（信息暴露）、CWE-639（用户控制资源标识符）等漏洞因缺乏语法表面而难以被规则捕获。需要结合外部策略规范、跨运行时数据流分析或 LLM 辅助才能解决。

## 7. 优点：方法或实验设计上的亮点

- **系统性贡献**：首次对 LLM 智能体运行时进行源码级安全审计，定义了可复用的五类漏洞分类法（基于 STRIDE 而非直觉），填补了现有智能体安全研究（提示注入、技能审计、黑盒评估）之外的空白。
- **双引擎验证**：在 Semgrep 和 CodeQL 两种不同分析后端上实现同一分类法，比较了语法匹配与图基查询的差异，实证了规则设计对召回率提升的贡献大于引擎选择。
- **严格的评估协议**：采用时间分割的训练/测试集、一次评估测试集、文件级归属（不苛求行级匹配，更符合实际修复模式），确保泛化性结论可靠。
- **务实的精度分析**：明确承认当前规则是召回导向的，并量化实时代码的发现量和低精度（12%），指出下一步语义改进方向，而非宣称完美。

## 8. 不足与局限

- **仅针对 OpenClaw**：实验局限于一个智能体项目，未评估对其他本地 LLM 智能体（如 Nanobot、PicoClaw）的泛化性。
- **全正例基准**：OPENCLAWBENCH 仅包含已知漏洞的修复前快照，缺乏负例（无漏洞代码）对照，无法直接评估误报率。
- **精度审计样本小**：仅 50 条发现由单人标注，可能低估或高估精度，且未按规则种类分层统计精确的每规则精度。
- **语义弱点覆盖不全**：CWE-184、CWE-200 等需要外部规范的漏洞召回率较低（40-80%），规则方法存在固有天花板。
- **分类法受限于现有通告和 OpenClaw 运行时结构**：随着新的智能体组件（如多智能体协调器、持久化记忆后端）涌现，五类分类可能需要扩展。
- **DoS 处理不一致**：虽然排除通用 DoS，但保留了部分 CWE-400/CWE-770（有静态可见模式），导致分类边界稍显模糊。
- **规则维护成本**：手动编写 77 条规则需依赖公告流，自动化规则生成（LLM 辅助）尚未实现。
