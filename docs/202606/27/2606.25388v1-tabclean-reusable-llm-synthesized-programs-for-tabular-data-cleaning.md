## 摘要
可靠的分析和机器学习管道依赖于干净的表格数据，然而生产环境中的表格常包含缺失值、拼写错误、格式不一致、违反依赖关系、单位不匹配以及模棱两可的分类值。现有清洗系统做出了不同的权衡。基于约束的系统需要专家指定规则。基于学习的系统需要标签或重新训练。最近的基于LLM的清洗器减少了设置工作量，但许多方法对行、单元格或重复的工作流步骤调用LLM，因此其成本随表格大小和每一批新数据的出现而增长。我们提出TabClean，一种无需模型训练的系统，它将LLM推理编译成可复用的有防护的清洗程序。给定一个脏表格和一个小型标注的开发集，TabClean分析表格证据、诊断修复机制、合成可执行的Python转换、通过单元格级反馈验证候选方案，并提交最佳程序用于模式兼容批次的复用。关键抽象是一个基于证据的有防护修复子句。仅当满足脏模式、目标负条件、证据支持和范围约束时，确定性转换才会触发。在六个基准测试中，TabClean实现了高精度，在五个数据集上F1分数优于具有代表性的基于规则、基于学习和基于LLM的基线方法，并通过用确定性程序执行替代重复的LLM推理，大幅减少了重复运行时间和API成本。

## Abstract
Reliable analytics and machine-learning pipelines depend on clean tabular data, yet production tables often contain missing values, typographical errors, inconsistent formats, violated dependencies, unit mismatches, and ambiguous categorical values. Existing cleaning systems make different trade-offs. Constraint-based systems need experts to specify rules. Learning-based systems need labels or retraining. Recent LLM-based cleaners reduce setup effort, but many call an LLM on rows, cells, or repeated workflow steps, so their cost grows with table size and with every recurring batch.   We present TabClean, a model-training-free system that compiles LLM reasoning into reusable guarded cleaning programs. Given a dirty table and a small annotated development set, TabClean profiles table evidence, diagnoses repair mechanisms, synthesizes executable Python transformations, validates candidates with cell-level feedback, and commits the best program for reuse on schema-compatible batches. The key abstraction is an evidence-backed guarded repair clause. A deterministic transformation may fire only when its dirty pattern, target-negative condition, evidence support, and scope constraints are satisfied. Across six benchmarks, TabClean achieves high precision, improves F1 over representative rule-based, learning-based, and LLM-based baselines on five datasets, and substantially reduces recurring runtime and API cost by replacing repeated LLM inference with deterministic program execution.

## 2. 方法论

### 核心思想
- **证据驱动的有防护修复子句**：将清洗逻辑表达为一系列带守卫条件的确定性转换（guarded repair clauses）。程序由LLM合成，但执行、验证和部署过程完全由确定性组件完成。
- **有限状态机（FSM）多智能体管道**：将合成流程分解为**诊断→策略→编码→执行→评审→部署**六个阶段，每个阶段由专门智能体执行，LLM只在合成与反馈阶段调用。

### 关键技术细节
1. **证据构建**：
   - **自适应开发集构造器**：根据表格大小、错误覆盖率等条件自动确定标注规模，确保暴露主要错误机制。
   - **数据剖析器**：提取列统计、缺失率、类型签名、可解析性、候选依赖关系等结构化证据，而非传递原始表格。
   - **证据级别**：将修复机会分为“确定性”、“表内证据”、“弱/外部证据”三级，仅前两级可用于自动合成。

2. **技能引导的守卫合成**：
   - **清洗技能库**：预定义日期/时间归一化、单位缩放、多数依赖修复、别名标准化等技能合同，每个技能明确所需证据、守卫条件和转换规则。
   - **守卫族**（表III）：脏模式守卫、目标负守卫、证据守卫、范围守卫、反回归守卫，确保只在足够证据下修改单元格。

3. **约束代码合成与调试**：
   - 编码智能体必须遵循**程序合同**：保留输入模式、行序、形状；每个单元格更新必须有显式守卫；禁止硬编码开发集值；通过正则、字符串操作等确定性方式实现转换。
   - 带预算的调试循环：仅修复语法和运行时错误，不改变语义修复意图。

4. **执行引导验证与控制**：
   - 候选程序在开发集上执行，计算单元格级TP/FP/FN，跟踪最佳程序P*（基于F1）。
   - **停止规则**：达到目标分数、迭代预算耗尽或连续无改进时停止。
   - 最佳程序用于全表清洗，后续批次无需LLM调用。

5. **角色专用智能体与记忆**：
   - 诊断、策略、编码、评审智能体验收角色化上下文（角色感知记忆），避免传递全部历史导致噪声和成本增加。
   - 评审智能体产生列级动作表（KEEP/ADD/MODIFY/REMOVE），指导下一轮策略更新。

- **清洗质量**：TabClean在5/6数据集上取得最佳F1（表VI）。F1最高0.99（tax），最低0.81（flight，仍优于基线）。在hospital上低于HoloClean和IterClean（0.87 vs 0.95），说明对稀疏标识符类修复仍需更优方案。

- **消融核心发现**：
  - 去除FSM多智能体流程：平均F1从0.91降至0.77，尤其hospital和flight下降明显。
  - 去除角色记忆：平均F1降至0.73，hospital仅0.24。
  - 去除最佳程序跟踪：平均F1降至0.85，tax从0.99降至0.84。

## 7. 优点

1. **创新性**：将LLM从“值编辑器”转变为“程序合成器”，实现可复用、可审计的清洗逻辑，显著降低长期成本。
2. **设计严谨**：有限状态机分离随机推理与确定性执行，防止LLM生成不可控的编辑；证据级别和多重守卫机制确保高精度（多数数据集精确率1.00）。
3. **实用性强**：单次合成后，后续清洗只需普通Python执行，无需任何LLM调用；程序可版本化、缓存，适合持续数据管道。
4. **实验全面**：消融实验覆盖各个关键组件，开发集和模型敏感性分析验证了设计鲁棒性。
5. **开源可复现**：提供代码仓库，细节可复现。

## 8. 不足与局限

1. **保守性导致召回损失**：对需要外部知识或稀疏证据的修复（如hospital中的标识符/地址字段），TabClean无法支持，召回低于某些基线。
2. **开发集标注成本**：虽然比全表标注小得多，但仍需1-2小时人工标注（表V），对于无标注历史的场景仍是障碍。
3. **跨模式适应性有限**：当前仅支持同一模式的批次复用，未处理模式漂移或分布偏移后的程序自适应更新；需人工介入或重新合成。
4. **未与最新大模型深度集成**：实验模型版本较新（如gpt-5-mini，gpt-5.3-codex），但可能未使用当前最先进模型（如GPT-4o等），评估结果可能随时间变化。
5. **对外部知识依赖不足**：未利用外部知识库、词典或本体来支持模糊修复，限制了在复杂语义错误（如地名消歧）上的表现。
6. **实验未覆盖所有错误类型**：当前聚焦于格式、依赖、缺失等，对逻辑一致性错误（如违反多列联合约束）的修复能力未单独评估。
