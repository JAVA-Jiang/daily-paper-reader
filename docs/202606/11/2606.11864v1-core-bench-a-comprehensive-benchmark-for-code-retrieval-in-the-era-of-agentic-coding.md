## 摘要
代码检索正逐渐成为编程智能体的核心，但智能体编程需要的不仅仅是自然语言查询与孤立代码片段之间的匹配。给定一个用户请求，编程智能体需要导航具体的仓库状态，定位相关文件和函数，收集支持的上下文，并过滤仓库内相似的干扰项。现有的代码检索基准主要评估文档字符串到函数或代码片段级别的匹配，因此忽略了这种需求驱动的仓库搜索问题。为弥补这一空白，我们引入了CORE-Bench，一个智能体编程时代代码检索的综合基准。CORE-Bench在三个层面评估代码检索能力：代码理解、问题到编辑的定位以及更广泛的上下文检索。基于精心设计的代码搜索任务和SWE-bench系列实例构建，CORE-Bench包含超过18万个查询和10.6万个更广泛上下文的相关性标签。与代表性嵌入模型的实验表明，在智能体编程设置中，从传统代码搜索到代码检索的性能急剧下降。对现有嵌入模型进行简单的监督微调在此设置中显著提高了性能，表明仍有很大的进步空间。

## Abstract
Code retrieval is becoming central to coding agents, but agentic coding requires more than matching a natural-language query to an isolated snippet. Given a user request, a coding agent needs to navigate a concrete repository state, locate relevant files and functions, gather supporting context, and filter similar in-repository distractors. Existing code retrieval benchmarks mainly evaluate docstring-to-function or snippet-level matching, thereby missing this requirement-driven repository search problem. To address this gap, we introduce CORE-Bench, a comprehensive benchmark for code retrieval in the era of agentic coding. CORE-Bench evaluates code retrieval ability at three levels: code understanding, issue-to-edit localization, and broader context retrieval. Built from curated code-search tasks and SWE-bench-series instances, CORE-Bench contains over 180K queries and 106K broader-context relevance labels. Experiments with representative embedding models show a sharp drop from traditional code search to code retrieval in agentic coding settings. Simple supervised fine-tuning of existing embedding models significantly improves performance in this setting, suggesting substantial room for further progress.

## 一、核心问题与整体含义（研究动机和背景）

- **研究动机**：智能体编程（Agentic Coding）场景下，代码检索已从孤立代码片段匹配转变为“需求驱动的仓库搜索”（requirement-driven repository search）。现有编码智能体（如OpenHands、SWE-agent）通常依赖`ls`、`grep`、`find`等命令行探索来定位相关代码，而非简单的嵌入查找。然而，当前主流代码检索基准（如CodeSearchNet、MTEB、CoIR）主要评估解上下文的片段级匹配，忽视了以下关键挑战：
  1. 真实开发请求的“意图-实现差距”较大（即用户用自然语言描述需求，但实现代码分散在多个文件中）；
  2. 相关证据是异构的，可能分布在代码、配置文件、依赖项等仓库构件中；
  3. 候选文档（函数级代码块或文档片段）较长，可能稀释单一嵌入的证据信号；
  4. 单个请求可能需要多个编辑片段和相关上下文；
  5. 真实仓库中存在密集的本地干扰项（如相似的包装器、适配器、配置片段）。

- **整体含义**：现有代码检索模型在传统基准上表现良好，但在智能体编程场景中可能实际效用有限。因此需要一个专门针对智能体编码中需求驱动仓库搜索的基准，以暴露差距并推动进展。

## 二、方法论：核心思想、关键技术细节

### 2.1 CORE-Bench的三层级结构

- **Level-1：代码理解（Code Understanding）**
  - 保留具有挑战性的传统检索任务，作为基础代码理解能力评估的参考点。
  - 包含Text-to-Code、Code-to-Text、Code-to-Code、混合检索以及竞赛编程检索等子任务，源自APPS、CoSQA、SyntheticText2SQL、CLARC、CodeSearchNet、CodeTransOcean、CodeFeedback-ST、CPRet等。

- **Level-2：问题到编辑定位（Issue-to-Edit Localization）**
  - 评估模型能否检索到必须修改的文件或代码块（即补丁对齐的编辑片段）。
  - 基于SWE-bench系列数据集（SWE-bench_Verified、SWE-bench_Pro、SWE-bench_Live、SWE-bench++、SWE-bench+、Multi-SWE-bench、SWE-bench Multilingual）构建。
  - 构建流程（5步）：
    1. 收集PR/Issue元数据；
    2. 将仓库检出到PR之前的提交，使检索语料库与实际代码状态匹配；
    3. 使用AST和LangChain分块器对源码和文档文件分块，保留文件路径和行范围；
    4. 将PR补丁反向对齐到预PR的分块（通过匹配修改文件和编辑行范围）；
    5. 将PR/Issue描述作为查询，补丁对齐的分块作为相关文档。

- **Level-3：更广泛的上下文检索（Broader Context Retrieval）**
  - 评估能否检索到辅助代码、文档、测试等有助于理解和完成变更的支持性上下文。
  - 使用自动注释流水线（三个阶段）：
    - **阶段1：精确上下文注释**：用Mini-SWE-Agent（基于Qwen3.5-397B-A17B）重新执行任务，提取浏览操作（`cat`、`grep`、`head`、`sed`）中的代码片段，并与Level-2分块方案对齐；然后用三个LLM投票（两个Qwen3.5-397B-A17B投票 + 一个Claude Sonnet 4.6投票）进行相关性判断。
    - **阶段2：质量验证**：修改Mini-SWE-Agent为允许列表模式（仅允许读取注释得到的文件），分别构建Level-2允许列表和Level-3允许列表，比较两者的任务解决率。若Level-3允许列表下的解决率更高，说明添加的上下文并非仅文本相关，而是功能上有用。
    - **阶段3：反馈迭代**：对注释不足的案例重新运行，将新浏览的上下文片段对齐、判断并添加为补充标签。不要求每条轨迹都最终解决任务，因为已解决的运行倾向于较简单的任务。

### 2.2 查询重写变体

- 将原始PR/Issue描述转换为更简短、更口语化的开发者风格查询，适合用户向AI编码助手提问。保留关键技术术语、错误消息、代码线索，移除模板噪音和冗余。用Qwen3.5-397B-A17B完成。

### 2.3 训练数据构建（in-domain SFT）

- 从非SWE-bench家族的GitHub PR中收集，共628个仓库、53,301个查询、1,218,875个相关性标签、29,171,451个分块。每个查询平均22.87个相关块，查询平均长度375.1字符，块平均长度2188.4字符。
- 训练目标：多正例InfoNCE损失：
  \[
  L(q) = -\log \frac{\sum_{d\in P} \exp(s_\theta(q,d)/\tau)}{\sum_{d\in P\cup N} \exp(s_\theta(q,d)/\tau)}
  \]
  其中每个查询从同一仓库采样64个非正例作为负样本，训练时正负比例为1:8。微调Qwen3-Embedding家族模型三个epoch。

## 六、主要结论与发现

1. **传统代码检索能力急剧下降**：许多强代码搜索模型（如Qwen3-Embedding-8B）在Level-1上NDCG@10达71.7，但在Level-2骤降至20.3/48.0，Level-3为34.4/41.5。表明智能体代码检索不是传统代码搜索的简单放大，而是存在本质困难。

2. **领域内SFT显著提升性能**：即使只有0.6B参数的Qwen3-0.6B-SFT在Level-2/3上超越更大模型，8B-SFT达到最佳水平（Level-2 NDCG@10=32.8, Recall@100=66.4；Level-3 NDCG@10=50.2, Recall@100=61.4）。但仍与Level-1性能有差距，说明问题尚未完全解决。

3. **查询重写并不总是有帮助**：重写后的查询（Rw列）往往降低性能，提示简洁的查询可能丢失关键仓库锚点（如具体URL、错误字符串、API名称）。

4. **语言间性能不均**：Python、Go、JS表现较好，Java、C++、Ruby、PHP、Swift相对困难。SFT能跨语言提升，但仍有差距。

5. **仓库难度的影响**：在“密集-大”设置（Dense-Large）中Recall@100最容易丢失，表明干扰项多、候选池大时，相关编辑块可能被推出100位之外。SFT模型在NDCG@10上相对稳定，但Recall仍需提升。

6. **跨层级相关性**：Level-1平均值仅中等程度预测Level-2性能（Spearman约0.7）；Code-to-Text任务最弱，Hybrid任务最强。说明Level-2/3引入了传统基准未覆盖的额外挑战。

## 七、优点

### 7.1 方法设计的亮点

- **三层级结构**：将传统代码理解、精准编辑定位、广阔上下文检索分离，全面评估智能体编码中的不同检索需求。
- **时间敏感的仓库状态**：通过检出PR前提交，确保语料库反映请求实际发生时的代码状态，避免后见之明。
- **自动注释+质量验证循环**：Level-3注释不仅基于LLM相关性判断，还通过允许列表实验验证上下文的“功能性有用”，而非仅文本相似性。
- **查询重写变体**：提供了更贴近真实用户交互的查询样式，暴露了简洁查询可能丢失检索线索的问题。
- **训练数据构建**：从外部GitHub PR构建领域内SFT数据，保证与测试集来源不重叠，且覆盖大量仓库。

### 7.2 实验设计的亮点

- **多维消融**：从语言、难度、意图、重写等多个维度分解性能，诊断模型能力的短板。
- **跨层级相关性分析**：揭示了传统基准与智能体任务之间的关联性不足，支撑了“需要新基准”的动机。
- **全面对比基线**：涵盖通用嵌入、代码专用嵌入、稀疏检索和微调变体，从<1B到8B多种规模。
- **论文和代码开源**：数据集和评估代码公开，便于复现和扩展。

## 八、不足与局限

### 8.1 实验覆盖

- **仅评估检索阶段**：未评估重新排序、交互式检索或多步检索，也未评估检索对下游代码生成任务的影响。
- **SFT数据源单一**：仅使用PR补丁对齐的查询-块对，未尝试其他监督（如issue注释、代码审查评论、提交消息）。
- **未探索模型架构创新**：实验仅聚焦现有嵌入模型的微调，未尝试为智能体检索设计的定制模型（如基于图、基于记忆的检索器）。
- **未测试检索增强生成（RAG）中的流水线**：没有将检索器与编程智能体结合运行端到端评估。

### 8.2 偏差风险

- **SWE-bench-derived数据偏差**：Level-2/3主要基于SWE-bench系列，这些实例本身可能偏向正确性修复而非新功能开发；bug报告和功能请求占92%以上，文档、重构、问题类占比较少。
- **语言分布不均**：Python占据48.7%/16.5%的查询分布，长尾语言（Ruby、PHP、Swift）样本很少，结论对这些语言可能不稳健。
- **注释流水线偏差**：Level-3注释依赖Mini-SWE-Agent的执行轨迹，而该代理本身可能更倾向于探索某些文件类型或路径，导致覆盖不全。
- **时间与生态偏差**：可能无法反映快速演进的仓库或全新项目中的检索场景，缺乏新鲜度（freshness）指标。

### 8.3 资源与应用限制

- **计算资源不透明**：未提供训练/评估所需的GPU型号、数量、时长，影响实用性评估。
- **单一评测视角**：仅使用嵌入相似度计算检索排名，未考虑交互式、多轮或上下文感知的检索策略。
- **未解决长代码块的证据稀释问题**：虽然分块是必要的，但部分块可能长达1000+字符，单一嵌入可能丢失关键信号。
- **未探索多模态或混合检索**：未涵盖基于稀疏/稠密混合（如SPLADE+ColBERT）的方法。
