## 摘要
在原始代码上进行预训练可以学习语法，但对于多样化的真实世界任务格式提供的信号稀疏。尽管合成数据已被证明对语言模型具有变革性，但代码领域在很大程度上仍未得到充分探索，仅限于有限的质量改进。我们提出了CodeAlchemy，一个合成数据生成框架，通过5种策略将公开来源的代码转化为语义丰富的训练数据：CodeEnhance（质量感知重写）、CodeQA（基于模板的问题）、CodeDev（开发者任务）、CodeDialogue（多轮对话）和CodeTrace（执行轨迹）。我们处理了涵盖15种编程语言的3个语料库，生成了超过5000亿tokens的合成数据以及3500亿推理tokens，比之前的努力高出数个数量级。CodeTrace对14种语言和5000个库的130万+文件进行了插桩和执行，捕获了控制流、状态跟踪和库知识。我们引入了DevEval（开发者任务）和TraceEval（执行预测）基准测试；像Claude Sonnet 4.5这样的前沿模型在TraceEval上的精确匹配率仅为5.6%，揭示了语义理解的关键差距。我们的3B模型在HumanEval上达到83.5%，MBPP上63.2%，DevEval上8.09%的胜率，TraceEval上15.36的ROUGE-2，超越了10倍大小的前沿模型，包括27B的Gemma-3和32B的Granite-4.0。

## Abstract
Pre-training on raw code teaches syntax but provides sparse signal for diverse real-world task formats. While synthetic data has proven transformative for language models, code remains largely unexplored beyond limited quality improvements. We present CodeAlchemy, a synthetic data generation framework that transforms publicly sourced code into semantically-rich training data through 5 strategies: CodeEnhance (quality-aware rewriting), CodeQA (template-based problems), CodeDev (developer tasks), CodeDialogue (multi-turn conversations), and CodeTrace (execution traces). We process 3 corpora across 15 languages to generate 500B+ tokens of synthetic data plus 350B reasoning tokens, orders of magnitude more than prior efforts. CodeTrace instruments and executes 1.3M+ files across 14 languages and 5K libraries, capturing control flow, state tracking, and library knowledge. We introduce DevEval (developer tasks) and TraceEval (execution prediction) benchmarks; frontier models like Claude Sonnet 4.5 achieve only 5.6% exact match on TraceEval, revealing critical gaps in semantic understanding. Our 3B models achieve 83.5% on HumanEval, 63.2% on MBPP, 8.09% win rate on DevEval, and 15.36 ROUGE-2 on TraceEval, outperforming frontier models 10x the size including 27B Gemma-3 and 32B Granite-4.0.

## 1. 核心问题与整体含义（研究动机和背景）

- **问题**：现有代码大语言模型（LLM）主要依赖大规模公开代码进行预训练，但存在三大局限：
  - 高质量代码稀缺，低质量代码损害性能；
  - 原始代码提供的信息对多样化用户交互（如调试、重构、解释）的信号稀疏；
  - 下一词预测只能学习语法模式，无法理解代码的执行语义（如控制流、状态演化）。
- **背景**：合成数据在文本领域已被证明具有变革性（如 K2、Nemotron-CC），但在代码领域的预训练数据合成尚未充分探索，现有工作（SwallowCode、Nemotron-Pretraining-Code-v2）覆盖范围有限（仅 Python 或少数任务）。
- **整体含义**：CodeAlchemy 提出大规模、多策略的合成代码数据生成框架，以填补代码预训练在语义理解、任务多样性和格式对齐方面的空白，验证合成数据对代码模型的显著提升。

## 2. 方法论

- **核心思想**：通过五种互补的合成策略，将公共代码转化为语义丰富的训练数据，生成 500B+ tokens 合成数据及 350B 推理 tokens。
- **关键技术细节**：
  - **CodeEnhance**：使用 LLM 对代码进行质量评分（0-10），对低分代码（≤6）进行重写，添加单元测试、文档、桩模块、样式修正等。处理约 120B tokens，将质量提升至 ~8 分。
  - **CodeQA**：手动设计 5 类与基准测试格式匹配的模板（编程问题、竞赛编程、函数执行、代码补全、轨迹预测），基于源文件模式生成 QA 对，经沙箱执行验证。产出 22M 对 / 13B tokens。
  - **CodeDev**：基于源文件生成具体的开发者任务（调试、重构、跨语言移植等），每个文件生成 10-15 个 prompt，并用 LLM 生成响应。经过难度演化和质量过滤后得到 62M 对 / 207B tokens + 68B 推理 tokens。
  - **CodeDialogue**：将 CodeDev 对扩展为多轮对话（平均 3.6 轮），识别前一回答的缺陷、引入约束或推进任务。产出 31M 对话 / 150B tokens + 271B 推理 tokens。
  - **CodeTrace**：构建执行轨迹基础设施：对 4M 文件（14 种语言、5K 库）进行插桩，注入 15-25 个结构化 trace 点（类型包括 IN/OUT/VAR/BRANCH/LOOP/ERR/TRANSFORM）；生成测试输入；在隔离沙箱中执行；过滤非确定性代码（约 75% 被移除）。最终得到 1.3M (code, trace) 对。
- **数据规模**：总计 500B+ tokens 合成数据 + 350B 推理 tokens，远超先前工作。

## 6. 主要结论与发现

- **合成数据显著提升性能**：3B 模型在 HumanEval 达 83.5%，MBPP 63.2%，胜过 10 倍大的模型（27B Gemma-3、32B Granite-4.0）。
- **各组分互补**：CodeTrace 对执行推理最关键，CodeQA 桥接增强与多样性，CodeDev/CodeDialogue 适合开发者任务。
- **多样性优于重复**：单 epoch 多样化合成数据优于多 epoch 重复同质数据。
- **推理轨迹有用**：预训练中加入推理轨迹改善生成和跨语言表现。
- **生成器模型质量重要但非绝对**：中等质量生成器（gemma-3-4b）在 MBPP 上反而优于强生成器，因保留了命名风格多样性。
- **前沿模型执行理解薄弱**：Claude Sonnet 4.5 在 TraceEval 上精确匹配仅 5.6%，显示语义理解巨大缺口。

## 7. 方法或实验设计的亮点

- **全面性**：五种策略覆盖代码质量、格式对齐、任务多样性、对话交互和执行语义，远超现有工作。
- **规模化**：处理 120M 文件评分、1.3M 文件执行，远超前人（SwallowCode 仅 Python，Nemotron 仅 11 语言且有限任务）。

- **严谨分析**：深入探讨了标准化与多样性的 trade-off（如 CodeEnhance 伤害 MBPP）；揭示了命名约定不匹配等非能力因素。
- **LLM 评审**：通过三个不同 LLM 评审员对数据质量进行多维比较，增强数据质量评估的可信度。
- **开源**：数据和代码均以 Apache 2.0 协议开源，促进复现。

## 8. 不足与局限

- **覆盖范围**：CodeTrace 仅覆盖软件生态的一小部分（14 种语言、5K 库），未包含 Web 开发和 ML 框架等常见领域。
- **文件粒度**：所有合成数据基于单文件，无法处理多文件重构、测试执行、依赖管理等真实 agentic 任务。
- **非确定性过滤**：约 75% 的文件因非确定性被移除，可能损失有益案例；执行层面仍有噪音。
- **评估局限**：DevEval 和 TraceEval 均来自自动合成和 LLM 评审，可能存在人工审核偏误；未进行人类评估。
- **计算资源细节不足**：未明确 GPU 小时数、训练总预算等，难以量化成本。
- **基座模型单一**：仅使用 3B 模型进行预训练，未验证更大模型上的可迁移性。
- **语言覆盖不均衡**：主要语言（Python/Java）数据丰富，而小众语言（如 Swift/Rust/SQL）数据相对较少。
- **潜在过拟合风险**：数据完全来自公开代码语料库，可能在特定分布上过拟合；未测试分布外任务。
