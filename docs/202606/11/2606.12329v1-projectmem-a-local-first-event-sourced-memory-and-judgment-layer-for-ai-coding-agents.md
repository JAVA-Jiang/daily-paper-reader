## 摘要
AI编码助手现在支持越来越多的软件工作，从快速脚本到生产应用。然而，这些代理仍然大多是无状态的：每个新会话都会重新读取项目文件，重新推导先前的决策，并且——最昂贵的——可能会重复已经失败的调试尝试。重建这种上下文每个会话估计会消耗5,000-20,000个token；瓶颈通常不是模型能力，而是缺失的项目记忆。我们提出了projectmem，一个开源的、本地优先的记忆与判断层，用于AI编码代理。projectmem将开发记录为一个仅追加的纯文本事件日志，包含类型化事件——问题、尝试、修复、决策和笔记——并确定性地将该日志投影为紧凑的、AI可读的摘要，通过模型上下文协议（MCP）提供。除了存储外，projectmem还添加了一个确定性的动作前门控，在代理重复之前失败的修复或编辑已知脆弱文件之前警告它。我们将其定义为记忆即治理：记忆不仅仅回答代理，而是影响其下一步行动。该系统完全离线运行，无遥测；其不可变日志也作为可重现、可审计的AI辅助开发的溯源追踪。projectmem作为一个包含三个依赖的Python包发布（14个MCP工具，19个CLI命令，37个自动化测试），并通过为期两个月的自我研究进行评估，涉及10个项目，包含207个记录事件。源代码：https://github.com/riponcm/projectmem。

## Abstract
AI coding assistants now support a growing share of software work, from quick scripts to production applications. Yet these agents remain largely stateless: each new session re-reads project files, re-derives prior decisions, and - most costly - may repeat debugging attempts that already failed. Reconstructing this context can consume an estimated 5,000-20,000 tokens per session; the bottleneck is often not model capability but missing project memory. We present projectmem, an open-source, local-first memory and judgment layer for AI coding agents. projectmem records development as an append-only, plain-text event log of typed events - issues, attempts, fixes, decisions, and notes - and deterministically projects that log into compact, AI-readable summaries served through the Model Context Protocol (MCP). Beyond storage, projectmem adds a deterministic pre-action gate that warns an agent before it repeats a previously failed fix or edits a known-fragile file. We frame this as Memory-as-Governance: memory that does not merely answer the agent but acts on its next action. The system runs fully offline with no telemetry; its immutable log also serves as a provenance trail for reproducible, auditable AI-assisted development. projectmem ships as a three-dependency Python package (14 MCP tools, 19 CLI commands, 37 automated tests) and is evaluated through a two-month self-study across 10 projects comprising 207 logged events. Source code: https://github.com/riponcm/projectmem.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **核心问题**：当前大语言模型（LLM）驱动的 AI 编码代理（如 Claude、Cursor 等）在单个会话内表现强大，但跨会话时完全无状态。每个新会话都需要重新读取项目文件、重新推导先前做出的决策，并可能重复执行已经失败过的调试尝试。这种重复行为不仅浪费大量 token（每个会话估计消耗 5,000–20,000 token），而且本质上是架构问题而非模型能力问题。
- **研究背景**：已有实证研究（Ehsani et al.，2026；Zhu et al.，2025）指出失败的代理 pull request 中存在“重复应用相同修复而不经过适当测试或演进”的常见失败模式，以及单个根因错误会传播导致级联任务失败。调查也确认跨会话记忆和上下文追踪是开放挑战。
- **整体含义**：作者提出需要一种**不仅“存储”记忆，还能主动“制约”代理行为**的记忆层，即 Memory-as-Governance（记忆即治理）。通过建立不可篡改的项目历史日志，并基于此进行确定性预操作门控，可从源头阻止重复失败，提升 AI 辅助开发的效率和可审计性。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 核心思想

- **Memory-as-Governance**：区别于传统的被动检索（Memory-as-Tool）或主动推理（Memory-as-Cognition），本系统的记忆不仅回答代理的查询，还能在代理执行动作前**主动判断并发出警告**。该警告基于项目自身记录的失败历史，是确定性的（不依赖 LLM 调用），因此可复现、可审计。
- **事件溯源（Event Sourcing）**：所有开发活动记录为一个**仅追加的纯文本事件日志**，绝不原地编辑，保证了数据的不可变性和可回放性。
- **本地优先（Local-First）**：所有状态存储在本地机器和仓库中，无网络依赖，无遥测，支持离线运行。

### 2.2 关键技术细节

- **事件模式**：定义了五种核心事件类型——`issue`（问题）、`attempt`（尝试，含结果 `worked/failed/partial`）、`fix`（修复）、`decision`（决策）、`note`（笔记）。每条事件包含时间戳、可选的 `location`（文件:行号）和自由文本。
- **确定性投影**：从事件日志通过纯函数折叠（fold）生成 `summary.md`，该文件是代理实际读取的摘要。投影是幂等的，可随时重建，不会与历史偏离。
- **判断门控**：`precheck_file(path)` 函数在代理即将修改文件前进行确定性查找：检查事件日志中与该路径相关的失败尝试、未解决问题和高变更率记录，返回警告信息（例如“你两天前试过这个，失败了”）。该检查不读取文件内容，不调用 LLM，是纯粹的内存查找。
- **MCP 接口**：通过 Model Context Protocol (MCP) 暴露 14 个类型化工具（9 个读工具、5 个写工具），实现工具无关性（同一服务可被 Claude、Cursor、Codex 等多个 MCP 客户端消费）。同时提供 Markdown 桥接用于非 MCP 工具。
- **跨项目记忆**：机器级全局存储收集库级别的经验教训（如“这个日期库必须用 UTC 构造”），在检测到栈匹配时自动注入到其他使用相同库的项目中。推广由信号过滤器控制：仅失败/部分尝试和显式标记的“gotcha”事件会进入全局库。
- **安全设计**：默认启用秘密脱敏（secret redaction），在写入日志前扫描并替换已知的密钥模式（OpenAI、Anthropic、GitHub、AWS 等），防止敏感信息泄漏。
- **实现细节**：Python 包（>=3.10），三个运行时依赖，<5MB。存储布局：`.projectmem/events.jsonl`（源文件）、`summary.md`（投影结果）、`PROJECT_MAP.md`（项目结构）、`issues/`（每个 issue 的详细文件）等。MCP 服务器基于 FastMCP，具有异常安全和 stdout 抑制保障。Git 钩子（post-commit, post-merge）自动捕获事件。

## 6. 论文的主要结论与发现

- **事件日志在现实开发中可有效累积结构化记忆**：在两个月内 10 个项目中收集了 207 个事件，证实该系统能在较低负担下持续记录项目知识。
- **记忆单调累积**：图 4 显示记忆随工作进展单调增长，永远不会重置（区别于无状态代理每次会话从零开始）。
- **记忆类型分布合理**：笔记/决策占多数（61%+25%），这正是无状态代理每次丢失的关键知识。
- **跨客户端可用性**：通过 MCP 接口，同一项目记忆可被不同 AI 工具消费。
- **潜在 token 节省**：MCP 模式下每次会话仅需 800-1500 token 即可加载上下文，相比无记忆层的 5000-20000 token 有显著降低（估计超过 50%）。
- **可审计性**：不可变的纯文本日志可作为 AI 辅助开发的溯源追踪，支持可重现性。

## 7. 优点：方法或实验设计上的亮点

- **设计原则简洁有力**：不可变、纯文本、本地、确定性——这些原则直接解决了现有记忆系统（向量库、LLM 调用、云端）的弱点，使得系统可审计、可审查、低开销、离线可用。
- **Memory-as-Governance 概念新颖**：将记忆从被动“回答”升级为主动“干预”，尤其针对编码任务中重复失败这一真实痛点。
- **判断门控确定性**：不依赖 LLM 判断，完全基于文本模式查找，因此无运行时模型成本、无随机性、可复现。这与其他安全防护系统（如 AGrail）的非确定性门控形成鲜明对比。
- **跨项目记忆**：通过全局库和栈检测，实现了库级知识跨项目复用，这是一个非常实用的功能，且设计得当（信号过滤，来源标注）。
- **系统实现完整且工具化**：MCP 服务器、CLI、Git 钩子、可视化仪表板、钩子路径自动解析（解决 conda/pyenv 环境问题）等细节展示了工程成熟度。
- **安全设计周到**：默认秘密脱敏，且专门编写了真假阳性测试，表明对隐私问题的重视。
- **实验中的真实性**：尽管缺乏对照，但使用真实项目、真实事件日志，比合成任务更贴近实际使用。

## 8. 不足与局限

- **实验覆盖不足**：
    - 仅单用户自我研究，缺乏多用户、多团队、跨组织的验证。结果存在确认偏差风险。
    - 没有在标准化基准（如 SWE-bench、AgentBench 等）上测试。论文中没有提供一个可复现的“失败阻止率”指标。
- **判断门控未量化验证**：论文承认“警告是建议性的”，但未测量其阻止了多少真正的重复失败，也未量化假阳性（误报警告）或假阴性（漏过危险操作）的比例。这是一大缺失。
- **冷启动问题**：对于新项目（无事件日志），判断门控形同虚设。虽然提供了 git 回填缓解，但不彻底。
- **无语义检索**：系统明确放弃了向量嵌入和模糊语义匹配，因此无法进行本质相似但措辞不同的事件发现。作者将其视为互补，但也限制了在某些场景下的召回能力。
- **单用户本地限制**：目前不支持多用户协作共享记忆。虽然提出未来使用 CRDT 合并冲突，但尚未实现。
- **token 成本为估计值**：论文承认 token 数字是“usage estimates over ranges, not a controlled benchmark”。在没有严格控制实验的情况下，这些数字的说服力有限。
- **与已有系统的对比缺乏定量依据**：Table 1 的对比是设计属性对比，但读者无法知道在实际任务中 projectmem 是否优于其他系统。例如，Codified Context 在简单被动上下文提供方面可能更便于代理接受，而 projectmem 的强制干预可能被代理忽略。
- **缺少对代理行为影响的量化分析**：比如，判断门控触发后，代理在多大比例上遵从警告？其行为改变如何影响最终产出？论文未报告这些。
- **论文发表为 arXiv 预印本（2026年6月）**，尚未经过同行评审，因此结果需谨慎对待。
