# CodeAlchemy: Synthetic Code Rewriting at Scale 

Ankit Gupta , Aditya Prasad , Rameswar Panda 

MIT-IBM Watson AI Lab, IBM Research Pre-training on raw code teaches syntax but provides sparse signal for diverse real-world task formats. While synthetic data has proven transformative for language models, code remains largely unexplored beyond limited quality improvements. We present CodeAlchemy , a synthetic data generation framework that transforms publicly sourced code into semantically-rich training data through 5 strategies: 

CodeEnhance (quality-aware rewriting), CodeQA (template-based problems), CodeDev (developer tasks), CodeDialogue (multi-turn conversations), and CodeTrace (execution traces). We process 3 corpora across 15 languages to generate 500B+ tokens of synthetic data plus 350B reasoning tokens, orders of magnitude more than prior efforts. CodeTrace instruments and executes 1.3M+ files across 

14 languages and 5K libraries, capturing control flow, state tracking, and library knowledge. We introduce DevEval (developer tasks) and TraceEval (execution prediction) benchmarks; frontier models like Claude Sonnet 4.5 achieve only 5.6% exact match on TraceEval , revealing critical gaps in semantic understanding. Our 3B models achieve 83.5% on HumanEval, 63.2% on MBPP, 8.09% win rate on DevEval , and 15.36 ROUGE-2 on TraceEval , outperforming frontier models 10 × the size including 27B Gemma-3 and 32B Granite-4.0.

# 1 Introduction 

Large language models (LLMs) for code have advanced through scaling on publicly sourced code (Lozhkov et al., 2024), but this paradigm faces 3 limitations: (1) high-quality data is scarce and low-quality code harms performance (Allal et al., 2025), (2) raw code provides sparse signal for diverse user interactions (debugging, refactoring, explanations), and (3) next-token prediction teaches syntax but not semantics; a model predicting 

for i in range(n): learns the pattern but not execution behavior, loop values, or termination conditions. LLM-based data rewriting has proven transformative for text models (Maini et al., 2024). Kimi K2 rewrites low-quality documents to improve quality and diversity (Bai et al., 2025), while Nemotron-CC and Rewire extract structured QA pairs from documents, boosting MMLU scores (Su et al., 2024; Nguyen et al., 2025). Despite these successes, synthetic code data for pretraining remains under-explored. SwallowCode focuses exclusively on Python quality enhancement (Fujii et al., 2025), while Nemotron-Pretraining-Code-v2 provides QA generation across 11 languages but limits quality rewriting to Python and cross-language tasks to Python →C++ only (NVIDIA, 2025) (detailed comparison in Table 1). This leaves critical gaps: (1) Quality: 

most code lacks tests, documentation, and error handling; (2) Format Alignment: benchmark formats (docstrings, signatures, test cases) are underrepresented in raw code; (3) Task Diversity: raw code doesn’t capture realistic developer workflows or multi-turn conversations; (4) Reasoning: complex QA instances contain implicit reasoning steps; (5) Semantics: next-token prediction teaches syntax but not execution semantics (control flow, state tracking, etc). To address these, we propose CodeAlchemy , a multi-faceted pipeline transforming raw code into diverse, semantically-rich training data (Figure 1). 

CodeEnhance Publicly sourced code often contains errors, poor naming, and lacks tests, documentation, and error handling (Fujii et al., 2025). We score files 0-10 using an LLM, then selectively rewrite low-quality code ( ≤ 6) to add: unit tests with edge cases, documentation, stubs/mocks for dependencies, style guide adherence, etc. Quality scores improve to ∼8 regardless of original quality (Section 2.1), yielding 120B tokens across 15 languages.

CodeQA Benchmarks use specific formats (function signatures, docstrings, test cases) rarely seen in raw code. In the text domain, training on QA pairs extracted from documents significantly boosts MMLU performance (Maini et al., 2024; Su et al., 2024; Nguyen et al., 2025). To investigate whether similar patterns hold for code, we hand-craft 5 QA templates with reference examples, then prompt an LLM to generate instances per source file that match the template format while being inspired by source code patterns. Grounding generation in diverse files naturally introduces variation, yielding 22M novel QA pairs. 

CodeDev Raw code provides sparse signal for realistic developer requests. We prompt an LLM to generate diverse developer tasks grounded in each source file: debugging, refactoring, porting, explanations, etc (Table A3). Each task references actual code elements , ensuring specificity and avoiding artificiality of purely prompt-based generation. This yields 215B tokens of 62M prompt-response pairs across 15 languages, plus 68B reasoning tokens. 

CodeDialogue Real developer interactions require multiple turns to refine requirements, debug issues, and explore alternatives. We extend CodeDev into multi-turn conversations by prompting an LLM to generate follow-up turns that identify gaps in previous responses, introduce constraints, or progress tasks naturally. This produces diverse interaction patterns: clarification requests, iterative refinements, debugging sessions, code reviews, yielding 150B tokens across 31M conversations (3.6 rounds average), plus 271B reasoning tokens. 

CodeTrace Next-token prediction provides sparse signal for semantics. Given x = foo(y) , models learn syntax but not what values x takes, which branches execute, or how state evolves. Publicly sourced code cannot be executed directly due to unresolved imports, missing dependencies, and lack of instrumentation. We build execution tracing infrastructure that: (1) instruments 4M files across 14 languages and 5K libraries to emit structured trace events, (2) generates test inputs, (3) executes in isolated containers, (4) filters non-deterministic code ( ∼75%). This yields 1.3M (code, trace) pairs capturing control flow, state evolution, and library behavior. Critically, frontier models struggle : Claude Sonnet 4.5 achieves only 30.8% line bigram F1, validating task difficulty. While execution traces have been used to evaluate state tracking abilities of new architectures, prior work uses only toy grammars or simple Python functions (Sun et al., 2025; Ding et al., 2024; Armengol-Estapé et al., 2025). 

New Benchmarks CodeAlchemy framework also reveals a gap in how models are evaluated. Existing benchmarks measure algorithmic problem-solving (HumanEval, MBPP, CodeContests) but not whether a model can handle a developer’s concrete goal given a source file, or mentally simulate what code does when it runs. To target these gaps we introduce two benchmarks. DevEval contains 1488 diverse developer tasks across 12 languages (debugging, feature extension, porting, etc), evaluating practical abilities beyond isolated function completion. # 2 Method 

We construct CodeAlchemy from 3 code corpora (stack-edu, the-stack-v2-train-smol-ids, RefineCode) across 15 languages: Java, Python, JavaScript, PHP, C, C++, C#, Typescript, Shell, Go, Markdown, Ruby, Rust, Swift, and SQL (Allal et al., 2025; Lozhkov et al., 2024; Huang et al., 2024). 

2.1 Enhancing the quality of raw code 

Quality Scoring To enable targeted rewrites, we prompted gpt-oss-20b 1 to score stack-edu files from 0-10 using Prompt C1 (OpenAI, 2025). For faster processing, we uniformly sampled 10K scored files per language (except SQL, Markdown) and finetuned SmolLM2-360M on (code, score) pairs to obtain a fast quality scorer (Allal et al., 2025). Figure A1 and Table A2 show the score distribution of stack-edu: a significant fraction scores 0, and most languages average below 5, indicating the data is far from production quality. We used tree-sitter 2 to tag syntax errors but, unlike SwallowCode and SeedCoder, avoided syntax-based filtering due to high false positives in SQL, C, C++, and C# (Fujii et al., 2025; Seed et al., 2025). 

CodeEnhance We enhanced code quality using gpt-oss-20b with Prompt C2 and used specialized prompts for Markdown, SQL, Shell. Due to compute constraints, we focused on bins 4-6, which have highest improvement potential. We processed 45.7M deduplicated files, yielding 112B tokens. To evaluate effectiveness, we uniformly sampled 500 files per language-quality bin and scored both raw and rewritten versions using 

gpt-oss-120b as judge. Figure A2 shows rewriting improves quality to ∼8 regardless of original score, with mass concentrated above the diagonal.

32.2 Template-based QA Generation 

Raw code repositories provide limited signal for benchmark formats. While functions may implement sophisticated algorithms, they rarely include formal problem statements, signatures, docstrings, or test cases; creating format mismatch for models trained on raw code. We manually crafted 5 QA templates inspired by prominent benchmarks (basic programming, competitive programming, function execution, code completion, trace prediction), each with 5-6 reference examples demonstrating desired format, style, and difficulty. Unlike purely prompt-based synthesis that produces repetitive problems, we ground generation in actual source code. For each (source file, template) pair, Prompt C3 generates instances that match the template format while drawing inspiration from algorithmic patterns in the source file. We applied this pipeline to quality-scored Python files (score ≥7), generating 2 instances per file-template pair using gpt-oss-20b (high). For competitive programming, we used gpt-oss-120b (high) with separate problem and solution generation steps. Each instance is sandbox-executed to verify correctness, eliminating ∼28% of samples. We translated basic programming samples to 6 additional languages using dedicated templates per language. This yielded the CodeQA dataset: 22M QA pairs spanning 13B tokens across 7 languages, with diverse problem types and difficulty while maintaining benchmark-quality formats. 

2.3 Developer Tasks 

For 12.6M stack-edu source files spanning 15 languages, we generate realistic developer prompts and responses.  

> Prompt Generation.

Using gpt-oss-20b and Prompt C4, we generate 10-15 diverse prompts per file. The prompt requires concrete references to code elements and targets 12 task categories (code comprehension, debugging, feature extension, cross-language, etc) with diversity across 7 dimensions (scope, scenario, constraints, audience, format, style, difficulty).  

> Response Generation.

Each prompt-code pair is answered using gpt-oss-20b with Prompt C5, instructing expert-level responses, yielding 153M (prompt+code, response) pairs.  

> Difficulty Evolution.

To increase complexity, we apply Prompt C6 to “Complex”-tagged prompts using 4 strategies: Mutation (constraint stacking, adversarial twists), Crossover (fusing prompts into workflows), 

Hybrid (combining both), and Invention (generating new prompts). This produces 112M additional pairs: total 265M pairs spanning 685B tokens with 230B reasoning tokens.  

> Quality Filtering.

To keep the average data quality high, we use gpt-oss-20b (high) with Prompt C7 to score prompts on three 0-9 scales ( validity , difficulty , training value ), retaining prompts with validity ≥8, and training value ≥8 or (training value =7 and difficulty ≥7). The CodeDev dataset comprises 62M pairs spanning 207B tokens plus 68B reasoning tokens. 

2.4 Developer-Assistant Conversations 

Real developer interactions require multiple turns to refine requirements and debug issues. We extend 

CodeDev pairs (with difficulty ≥7) into multi-turn conversations using gpt-oss-20b (high). Starting from a CodeDev pair as the initial exchange, we iteratively generate conversation turns. For each conversation history, Prompt C9 generates the next developer turn by identifying gaps or issues in the previous assistant response and building progressively on the discussion, enforcing diverse follow-up types: clarification requests, iterative refinements, debugging, testing, extensions, and code review. Each developer turn is answered using Prompt C10, which generates expert responses that address the user’s request. Conversations exceeding 100K characters are not extended any further. 2.5 Code Tracing 

Next-token prediction provides sparse signal for program semantics. Given x = foo(y) , models learn syntactic patterns but not what values x can take, which branches foo executes, or how state evolves. To address this, we build a large-scale execution tracing infrastructure.  

> Instrumentation.

We use Prompt C11 to transform 4M quality-scored files from stack-edu (score ≥7) across 14 languages into deterministic, instrumented programs. The prompt inserts 15-25 trace emission points outputting structured events to STDERR as TRACE:<TYPE>:<LOC>:<STATE> , where TYPE ∈ {IN, OUT, VAR, BRANCH, LOOP, ERR, TRANSFORM}, LOC identifies the function/block/line, and STATE captures program state. The prompt enforces 15 complex trace patterns: checkpoint thresholds ( sum > checkpoint+500 ), stack deltas ( |len(stack)-prev| > 5 ), statistical conditions ( median(buf)-mean(buf) > std(buf) ), etc designed to challenge semantic understanding rather than test memorization. Only popular mainstream libraries are retained for executability.  

> Test Input Generation.

For each instrumented file, Prompt C12 generates a bash script with 3-5 tests producing structurally distinct traces via CLI arguments, stdin, or heredocs. The prompt prescribes 10K-15K stderr characters to keep traces predictable.  

> Execution.

We execute instrumented files and test scripts in isolated sandboxes that install dependencies on the fly through standard package managers and capture structured trace events from STDERR (sandbox details in Appendix B). To filter non-deterministic code, each file is executed thrice with identical seeds. Files producing empty or inconsistent traces are removed ( ∼75% filtered). This constitutes CodeTrace : 1.3M (code, trace) pairs across 5430 libraries, 14 languages, and 7.4B tokens. Traces capture control flow (BRANCH, LOOP), state evolution (VAR), function boundaries (IN, OUT), data transformations (TRANSFORM), error conditions (ERR), and library API behavior, providing rich signal for teaching program execution, not just syntax. 

2.6 Evaluating Developer Knowledge 

To evaluate LLMs on developer tasks, we created DevEval using the CodeDev pipeline (Section 2.3) on 150K RefineCode files not in stack-edu. We generated 1.8M prompts using gpt-oss-20b (high), retaining only “Complex” prompts with difficulty ≥ 6.  

> Ensuring Diversity.

Following (Luo et al., 2024), we embedded prompts (without the source code) using 

embeddinggemma-300m and clustered into 100 clusters per language-difficulty bin (Vera et al., 2025). For each language, we sampled 41 hardest samples round-robin across clusters (starting from bin 9 →6), then 30 samples each from bins 6-8 (round-robin across clusters), yielding 1488 prompts across 12 languages. The prominent task categories are shown in Table A3.  

> Evaluation Protocol.

We generated reference responses using Claude 4.5 Sonnet (50K thinking tokens), then evaluated model responses via preference scoring with gpt-oss-20b (high) as judge (Prompt C8). We also experimented with using Claude 4.5 Sonnet itself as the judge but it did not change the rankings. 2.7 Evaluating Mental Execution Abilities of LLMs 

To evaluate LLMs’ mental execution abilities, we created TraceEval using the CodeTrace pipeline (Section 2.5) on held-out stack-edu files, generating 94K candidate tasks. To ensure challenging but predictable traces, we applied multiple quality filters.  

> Filtering for Predictability.

We removed samples requiring external packages, then used Prompt C13 with 

gpt-oss-20b (high) to filter unpredictable elements (non-determinism, runtime-dependent values, external state) and computationally intensive operations (cryptographic hashes, seeded PRNGs). Moreover, we used Prompt C14 to remove traces with system-generated noise (compiler warnings, errors, deprecations) and removed samples exceeding 300 TRACE: lines.  

> Difficulty Calibration.

We evaluated gpt-oss-20b , gpt-oss-20b (high), and gemma-3-27b-it on remaining samples using line-level ROUGE-2 F1 scores (bigram overlap between predicted and ground truth traces) (Lin, 2004). Samples where all models scored < 5% were removed as excessively difficult. For 14 languages, we selected the 75 hardest samples per language (lowest maximum score across models), yielding 1050 samples comprising TraceEval . Performance of models on TraceEval is included in Table 3 with frontier models like Claude Sonnet 4.5 scoring only 5.6% exact match. 

# 3 Experiments 

We systematically investigate the utility of each constituent of CodeAlchemy by investigating 10 Research Questions (RQs) that can be grouped into three questions: (1) is each component necessary and complementary? (RQ1-2); (2) how should components be combined, and how much data is needed? (RQ3-5); (3) how does CodeAlchemy stand relative to other open alternatives? (RQ6-10). As our default setup, we perform continual pretraining of a 3B parameter base checkpoint trained on 12 trillion tokens from a mixture of natural language, code, academic text, math and multilingual data. In each RQ, we differ only the data mixtures holding all other hyperparameters constant. Evaluation is performed on standard coding benchmarks such as HumanEval, HumanEval+, MBPP, MBPP+, CruxEval, MultiPL-E as well as our new benchmarks DevEval 

and TraceEval which we introduce in this work (Chen et al., 2021; Liu et al., 2023; Austin et al., 2021; Gu et al., 2024; Cassano et al., 2022). Training and evaluation hyperparameters are included in Appendix A.

This suggests that standardization in CodeEnhance ,due to adherence to official style guides, helps on HumanEval but reduces the diversity needed for MBPP, which contains varied documentation styles and naming conventions. RQ2: Do individual constituents of CodeAlchemy provide complementary benefits? We an-neal the base model on individual subsets of CodeAlchemy for 1 epoch each without accounting for size differences. As shown in Table 4, each constituent exhibits distinct strengths. CodeTrace (10B tokens) dramatically outperforms all others on TraceEval (13.55 ROUGE-2); even outperforming a much larger 27B gemma-3-27b-it (Table 3). CodeQA achieves strong HumanEval performance (42.7) and partial MBPP recovery (34.7), suggesting its QA format bridges the gap between code enhancement and diverse coding patterns. CodeDev and CodeDialogue lead on developer task benchmarks with DevEval scores of 6.73% and 6.25% respectively; even outperforming a much larger 32B granite-4.0-h-small (Table 2). Notably, 7CodeEnhance alone (125B tokens) continues to exhibit the MBPP degradation pattern (11.9), reinforcing findings from RQ1 that standardization trades diversity for style consistency. CodeAlchemy constituents provide complementary benefits: CodeTrace for execution rea-soning, CodeQA for bridging enhancement and diversity, and CodeDev /CodeDialogue 

for developer tasks. 

RQ3: Does mixing diverse types of data yield balanced performance across benchmarks? 

We train on 3 mixtures of CodeAlchemy constituents at 100B tokens each, progressively increasing raw code from 0% (Mix1) to 10% (Mix2) to 20% (Mix3) (see Table A1). As shown in Table 4, all mixtures substantially outperform raw-only training on HumanEval ( ∼40 vs 28.7), demonstrating that quality-enhanced and specialized data provide clear benefits. However, MBPP performance reveals a trade-off: Mix1 with no raw code achieves only 38.6, while Mix3 with 20% raw code recovers to 52.9, approaching the raw-only baseline of 58.7. This mirrors the findings from RQ1 that raw code diversity is essential for MBPP. All mixtures achieve strong DevEval and TraceEval scores compared to individual constituents (RQ2), demonstrating that combining diverse data types improves coverage across benchmarks. Mix3 provides the most balanced performance, maintaining HumanEval gains (40.2) while best preserving MBPP scores (52.9) and achieving competitive multilingual results (73.7 on Go, 44.3 on C++). Mixing diverse data types retains the strengths of individual constituents, enabling balanced performance across all benchmarks. 

RQ4: Does more training budget help and does data repetition across epochs hurt performance? 

We compare training with 600B tokens using 3 approaches: 5 epochs over CodeEnhance (112B tokens), 5 epochs over raw code (120B tokens), and 1 epoch over Mix1 (590B tokens). As shown in Table 4, Mix1 trained for 1 epoch substantially outperforms both CodeEnhance and raw code trained for 5 epochs on HumanEval (46.3 vs 35.4 and 31.1), demonstrating that diversity in data types and rephrasing styles is more valuable than repeated exposure to homogeneous data. The MBPP results further support this finding: while raw code at 5 epochs achieves the highest MBPP score (52.9), Mix1 maintains competitive performance (43.9) despite seeing each example only once. Notably, CodeEnhance at 5 epochs shows severe MBPP degradation (4.0), suggesting that repeated exposure to standardized code exacerbates the diversity loss observed in RQ1 and RQ3. Mix1 also achieves the strongest DevEval (8.09) and TraceEval performance (15.36), further evidencing the benefits of diverse data sources over repetition. This echoes the findings of Kimi K2 (Bai et al., 2025) who also made similar observation in the context of natural language QA. Diversity in rephrasing styles over a single epoch is more beneficial than repeated exposure to homogeneous data.

RQ7: How important is the quality of the model used for data generation? We examine whether the capability of the model used to generate CodeEnhance affects downstream performance by regenerating the Python subset of CodeEnhance using gemma-3-4b-it and gemma-3-1b-it and annealing on 10B tokens. We include SwallowCode and Nemotron-Pretraining-Code-v2 Python rewrite, two state-of-the-art synthetic data generation approaches, as baselines. As these works are limited to Python , we use the Python subset of our data. Surprisingly, as shown in Table 6, the smaller gemma-3-4b-it generator produces the best overall results, outperforming Nemotron on MBPP+ (52.1 vs 46.6), CruxEval-I (33.8 vs 32.3), and CruxEval-O (34.5 vs 31.9) and matching it on MBPP (63.0 vs 64.0). Even gemma-3-1b-it outperforms the default CodeEnhance 

(gpt-oss-20b ) on MBPP (57.7 vs 5.6) while maintaining comparable HumanEval scores (32.9 vs 34.2). This counterintuitive result suggests that smaller models introduce beneficial variation in their rewrites, avoiding the over-standardization that occurs with larger, more capable models. While larger generators produce more technically correct and standardized code, smaller models preserve style variation crucial for performance across benchmarks. 

RQ8: How important is the quality of the seed data? We investigate whether the quality of seed code affects final model performance by partitioning the Python subset of CodeEnhance into high-quality ( >4rating) and low-quality ( ≤4 rating) samples based on quality score of the seed code (Section 2.1). As shown in Table 4, for raw code, higher-quality seeds yield better HumanEval performance (29.9 vs 26.2), validating our quality scoring methodology. However, for CodeEnhance , seed quality makes minimal difference: models trained on high-quality seeds (HumanEval: 38.4) perform only marginally better than those trained on low-quality seeds (HumanEval: 36.6). This aligns with our observations in Section 2.1 that the rewriting process consistently elevates code quality to ∼8 regardless of the original seed quality. Seed data quality matters for raw code training but becomes less critical for CodeEnhance ,as the rewriting process normalizes output quality regardless of input quality.

# 4 Related Work 

Code Pretraining Data Early code LLMs were trained predominantly on raw GitHub data (Lozhkov et al., 2024), but raw code is noisy, redundant, and skewed toward low-quality files. Recent work has shown that targeted quality filtering significantly improves downstream performance (Allal et al., 2025; Huang et al., 2024; Fujii et al., 2025). SwallowCode-v2 focuses on quality-based rewriting but restricts enhancements to Python (Fujii et al., 2025), while Nemotron-Pretraining-Code-v2 extends QA generation to 11 languages but limits quality rewriting to Python and cross-language tasks to Python →C++ (NVIDIA, 2025). CodeAlchemy addresses these gaps with quality scoring, rewriting, and diverse synthesis across 15 languages. 11 Instruction Tuning Data for Code A parallel line of work focuses on synthesizing instruction-tuning data rather than pretraining data. Magicoder introduces OSS-Instruct, which seeds an LLM with open-source snippets to generate diverse coding problems, achieving strong results on function-level Python benchmarks (Wei et al., 2024). WaveCoder extends this with a generator-discriminator framework targeting four code-related tasks (Yu et al., 2024). EpiCoder replaces code seeds with hierarchical feature trees, enabling controlled complexity from function-level to multi-file scenarios, but is limited to Python (Wang et al., 2025). SemCoder augments instruction tuning with monologue-style execution reasoning, but is limited to single Python functions (Ding et al., 2024). 

Execution Traces as Training Signal Similarly, existing works on trace prediction are limited to toy grammars and Python functions with limited external dependencies (Sun et al., 2025; Armengol-Estapé et al., 2025). NExT (Ni et al., 2024) bootstraps execution-aware chain-of-thought (CoT) reasoning from variable states of executed lines to improve program repair. CodeI/O++ (Li et al., 2025a) transforms programs into input/output prediction tasks expressed in natural language CoTs, exposing models to reasoning primitives such as logic flow planning and state-space search. CodeAlchemy’s CodeTrace is also built with the motivation that execution semantics provide richer signal than next-token prediction over static code but differs significantly in scope: rather than rationales over simple Python programs, CodeTrace instruments and executes 1.3M real-world files across 14 languages and 5K libraries, capturing structured trace events for control flow, state evolution, and library API behavior, beyond the scope of prior works. 

Synthetic Data via LLM Rewriting In the text domain, LLM-based rewriting has proven transformative: Kimi K2 rewrites low-quality documents to improve quality and diversity (Bai et al., 2025), while Nemotron-CC and Rewire extract structured QA pairs from documents to boost factual performance (Su et al., 2024; Nguyen et al., 2025). CodeAlchemy brings this paradigm to code with CodeEnhance , which rewrites low-quality files to add tests, documentation, and error handling, and CodeQA , which grounds QA generation in actual source files to avoid the common low diversity issues with prompt-only synthesis. 

Realistic Developer Tasks and Multi-turn Data Raw code corpora provide little signal for the diverse tasks developers actually perform. Nemotron-Pretraining-Code-v2 includes multi-turn data but restricts it to Python and C++ (NVIDIA, 2025). Table 8 shows that Nemotron’s conversation samples (Synthetic-Student-Teacher, Synthetic-Code-Review) are substantially shorter (mean 653-957 tokens vs 8897 for CodeDialogue )and lower quality, with CodeDialogue achieving over 90% win rates against all Nemotron subsets across 3 independent judges (Table 7). CodeDev and CodeDialogue include multi-turn data in 15 languages, generating grounded developer tasks and conversations that draw on the diversity of source files to ensure specificity and depth. A related work by Zeng et al. (2026) synthesizes 300k agentic developer trajectories (4B tokens) via multi-agent simulation grounded in file hierarchies and dependency graphs, with search-based CoT optimization against ground-truth code perplexity. In the resulting data, there is a single long monolithic trajectory per repository. CodeDev operates at a significantly larger scale producing 62M diverse task-response pairs (207B tokens) spanning numerous task categories (Table A3), and applies explicit difficulty evolution and filtering. 

Code Evaluation Benchmarks Standard benchmarks such as HumanEval and MBPP evaluate isolated function synthesis but do not capture practical developer workflows or semantic understanding. BigCodeBench broadens evaluation to multi-library function calls and complex natural language instructions (Zhuo et al., 2025), while LiveCodeBench provides continuously updated, contamination-resistant competition problems (Jain et al., 2025). Our DevEval and TraceEval complement these by targeting practical multi-language developer tasks and execution prediction respectively - dimensions largely absent from existing benchmarks. At the repository level, evaluation has been driven by SWE-bench (Jimenez et al., 2024), FEA-Bench (Li et al., 2025b), and SWE-bench Pro (Deng et al., 2025), which progressively increase task complexity toward realistic enterprise-level software engineering. CodeAlchemy does not include repository-level tasks and we leave this as future work. 

# 5 Conclusion 

We present CodeAlchemy, a synthetic data generation framework that produces 850B+ tokens across 5 complementary strategies, orders of magnitude beyond prior work, including the largest code execution 12 dataset to date with 1.3M traced files across 5K libraries and 14 languages. Our 3B models achieve 83.5% on HumanEval and 63.2% on MBPP, outperforming frontier models 10 × larger, while our new benchmarks reveal critical gaps where Claude Sonnet 4.5 achieves only 5.6% exact match on execution prediction. These results demonstrate that large-scale, semantically-grounded synthetic data is more effective than simply scaling on raw code repositories. 

Limitations and Future Work While CodeTrace represents the largest code execution dataset to date, it covers only a fraction of the software ecosystem; we plan to improve execution yields and expand library coverage, particularly for web development and machine learning frameworks. Additionally, CodeAlchemy currently focuses on single-file code generation, whereas real-world agentic coding requires multi-file refactoring, test execution, debugging, and dependency management (Jimenez et al., 2024; Deng et al., 2025). Future work will extend CodeAlchemy to generate large-scale data for these agentic workflows across complex codebases.

# A Additional Experiment Details & Hyperparameters 

Our data generation and validation experiments were performed on NVIDIA H100 GPUs. For inference, we used vLLM and top-p sampling with p = 0 .95 and temperature 0.7 (Kwon et al., 2023). For the continual pretraining experiments (Section 3), we train with a batch size of 4M tokens and context length of 4096 tokens. We use AdamW optimizer with learning rate 0.01, β1 = 0 .9, β2 = 0 .95 , ϵ = 10 −10 , and weight decay 0.1. We apply exponential LR scheduler throughout the training budget with a decay factor of 0.1. We used 0.5 as the fill-in-the-middle (FIM) rate for all experiments except for RQ2 CodeTrace (FIM 0.1) and RQ2 CodeDialogue (FIM 0.3) (Loshchilov and Hutter, 2017; Bavarian et al., 2022). For the SFT experiments in RQ6, we use the AdamW optimizer with β1 = 0 .9, β2 = 0 .95 , ϵ = 10 −8, and weight decay of 0.1 with 5% warmup. We apply cosine LR scheduler with a decay factor of 0.1. For HE, HE+, MBPP, MBPP+ we use Evalplus to report pass@1 scores with the responses generated using greedy decoding (Liu et al., 2023). For CruxEval we use the official repo 3 and report pass@1 for both input and output tasks, with responses generated using temperature 0.2, n_samples=10 and max_length_-generation=1024. For MultiPL-E, we use Bigcode Evaluation Harness and report pass@1 scores (Ben Allal et al., 2022). The responses are generated using temperature 0.2, n_samples=20 and max_length_generation=4096.

# B Sandboxed Execution 

To safely execute millions of instrumented code files with diverse external dependencies, we developed a custom sandboxing framework built on bubblewrap ,4 a Linux container runtime that provides namespace-based isolation without requiring root privileges. 

Filesystem isolation. The sandbox provides read-only access to the host filesystem but redirects all writes to in-memory tmpfs mounts. Specifically, we overlay tmpfs on all potentially writable directories including 

/tmp , /var , /home , /usr/local , and /opt , ensuring that no modifications persist to disk. Additionally, we blacklist sensitive system paths such as /root to prevent information leakage. As a result, the only way to extract information from sandboxed execution is through stdout and stderr, which we capture for parsing the execution traces. 

Two-stage execution with network control. Many code files require external packages that must be installed before execution. To handle this safely, we implement a two-stage execution model: 1. Setup stage: When dependencies are needed, we provide controlled network access through a custom SOCKS5 proxy that enforces a whitelist of trusted package registries including PyPI, npm, Maven Central, crates.io, RubyGems, and others. The proxy pre-resolves DNS entries and blocks all non-whitelisted domains. The package caches (pip, npm, cargo, Maven, etc.) are stored in temporary directories within the sandbox’s tmpfs, allowing the packages to be accessible during the main stage. 2. Main stage: After package installation, we terminate all processes from the setup stage and remove network access entirely using unshare –net , creating a fresh network namespace with no connectivity. The instrumented code then executes in complete isolation. 

Resource limits. We enforce strict resource constraints using prlimit : 30GB maximum RAM (both virtual and resident), 30 maximum processes, 1000 maximum file descriptors, and a 30-second CPU time limit.
