## 摘要
在现代云架构中，多个应用通常运行在同一集群环境中，共享底层资源。这种资源共享会导致应用间的干扰，从而造成延迟恶化与系统稳定性下降。随着容器化微服务在云原生应用中日益成为核心，其性能可能因复杂的资源竞争干扰场景而受损。同时，现有大多数微服务方法要么通过检测和定位性能问题来应对干扰，要么仅优化延迟，而未解释为何特定共存会引发跨应用干扰，以及如何将其用于服务部署优化。本研究通过构建一种捕获跨应用干扰因果效应的时空数据结构来弥合这一空白。这些因果效应被数学形式化为必要且充分的条件概率，并用于指导多目标优化器（Optuna）。利用跨应用剖析来模拟踪迹并估计干扰概率，同时通过性能数据（如95百分位响应时间p95）提供每服务延迟基线。我们的方法支持网络惩罚、应用隔离需求以及必要与充分因果度量的可调权重。在真实多应用工作负载上的实验表明，感知干扰的部署能显著降低跨应用干扰并提升响应性能。最终，因果驱动的多目标公式使云操作员在配置服务部署时能够对干扰、延迟和通信开销进行显式控制。

## Abstract
In modern cloud architectures, multiple applications often run within the same clustered environment, sharing underlying resources. This resource sharing can cause interference among applications, leading to degraded latency and reduced system stability. As containerized microservices become increasingly central to cloud-native applications, their performance can suffer from complex interference scenarios related to resource competition. Meanwhile, most existing microservice approaches address interference either by detecting and localizing performance issues or by optimizing latency alone, without explaining why specific co-locations cause cross-application interference, and how this can inform service placement optimization. This work closes that gap by building a spatio-temporal data structure that captures the causal effects of cross-application interference. These causal effects are mathematically formalized as necessary and sufficient conditional probabilities that inform a multi-objective optimizer (Optuna). Cross-application profiling is used to simulate traces and estimate interference probabilities, while per-service latency baselines are provided by performance data, such as 95th-percentile response times (p95). Our approach supports network penalties, application isolation requirements, and adjustable weighting of necessary and sufficient causal metrics. Experimental results on real multi-application workloads show that interference-aware placements significantly reduce cross-application interference and improve response performance. Ultimately, the causality-driven multi-objective formulation gives cloud operators explicit control over interference, latency, and communication overhead when configuring service placements.

- **背景**：现代云环境中，多个微服务应用（如电商、社交、媒体）常共享同一集群的底层资源（CPU、内存、I/O）。这种资源竞争会引发跨应用干扰（interference），导致延迟飙升、SLO/SLA 违例，甚至系统不稳定。容器化微服务架构加剧了此类问题的复杂性，因为服务间除了显式的调用关系外，还存在隐式的资源争用。
- **核心问题**：现有方法存在三大空白：
  - 多数工作只关注**检测或局部化**性能问题，或者**仅优化延迟**，而未解释为何特定的服务共存会引发干扰，以及如何利用这种因果知识来指导放置决策。
  - 缺乏对**干扰的因果机制**（必要性与充分性）的形式化刻画，导致放置策略难以主动预防干扰。
  - 已有放置优化往往采用**单目标**（如仅最小化延迟），无法同时权衡干扰、延迟与通信开销。
- **论文目标**：提出一种**因果驱动的多目标优化放置方法**，通过构建时空干扰图（Spatio-Temporal Interference Graph, STIG）和因果概率（PN/PS/PNS），让云操作员能显式控制干扰、延迟与通信开销之间的权衡。

### 2. 论文提出的方法论

#### 2.1 核心思想
- 基于**反事实因果关系**（Pearl 因果框架），将干扰形式化为**充分性**（某服务的资源消耗总能引起另一服务性能退化）和**必要性**（若移除某服务，则另一服务的干扰消失）。
- 利用运行时轨迹数据，通过 STIG 捕获服务间的时空干扰模式，并计算**必要性概率（PN）**、**充分性概率（PS）** 和**必要且充分概率（PNS）**。
- 将因果概率与 STIG 的边权重结合，形成**期望干扰分数**，并融入**多目标优化器 Optuna**，同时优化总干扰和总延迟（含跨节点通信惩罚）。

#### 2.2 关键技术细节
- **STIG 构建**：动态图结构 G = (V, E, X_v(t), X_e(t))，其中节点为服务，边表示干扰关系，节点特征为资源使用，边特征为干扰概率。
- **因果概率计算（Algorithm 1）**：
  - 输入：清理后的分布式追踪数据（含开始时间、持续时长、错误标记）。
  - 步骤：
    1. 计算每个服务的均值 μ 和标准差 σ，定义异常阈值 τ = μ + z·σ。
    2. 提取异常跨度（持续时间超阈值或报错）。
    3. 对跨应用服务对 (X, Y)，统计在 X 异常时间窗口内 Y 也异常的次数，得到 P(Y|X)；统计 Y 异常但不在任何 X 窗口内的比例，得到 P(Y|¬X)。
    4. 计算 PNS = max(0, P(Y|X) - P(Y|¬X))；PN = PNS / P(Y|X)（若分母>0）；PS = PNS / (1 - P(Y|¬X))（若分母>0）。
- **放置优化器（Algorithm 2 – SPO）**：
  - 输入：因果概率表 P、响应时间日志 R、STIG 图目录 G、节点集合 N、优化试验次数 T。
  - 步骤：
    1. 从 R 中提取每个服务的 p95 延迟 L(s)。
    2. 合并 P 与 STIG 权重，计算每对服务 (s,t) 的因果因子 α(s,t) = PN + PS - PNS，期望干扰 E(s,t) = α × w_STIG。
    3. 计算每个服务优先级 Priority(s) = 所有 t 的 E(s,t) 之和（识别关键服务）。
    4. Optuna 进行 T 次试验：每个试验提出一个放置 π：S→N；计算总干扰 I = 对所有 co-located 的 (s,t) 求和 E(s,t)；计算总延迟 L = ∑L(s) + 跨节点通信惩罚。
    5. 从 Pareto 前沿中选择一个放置（缺省偏好低干扰）。

#### 2.3 算法流程
- **Algorithm 1**：遍历所有跨应用服务对，计算 P(Y|X)、P(Y|¬X)，进而导出 PN、PS、PNS。
- **Algorithm 2**：聚合因果知识（PN/PS/PNS）与 STIG 权重，定义目标函数；使用 Optuna 多目标采样；输出 Pareto 最优放置。

### 6. 论文的主要结论与发现

1. **感知干扰的放置显著降低跨应用干扰**：全因果 Optuna 相比无因果基线（GA/RL/延迟-only）降低干扰约 **43%**（干扰分数从 1763 降至 997）。

3. **TeaStore 性能大幅提升**：p95 延迟从 166.68 ms 降至 8.78 ms（降低 94.73%），但 HTTP 错误率从 24.63% 升至 32.69%。作者解释为“快速失败”而非真正的性能恶化，但未完全解决此 trade-off。
