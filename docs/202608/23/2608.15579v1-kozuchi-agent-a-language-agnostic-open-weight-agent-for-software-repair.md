## 摘要
工业软件工程团队越来越需要能够将错误报告转化为正确补丁的LLM代理，然而基准规模的运行增加了长周期、工具使用纪律、上下文持久性、异构集群和评估复用等挑战。我们提出了Kozuchi Agent，一种语言无关的开源权重修复代理和CI驱动的评估流水线。明确的阶段、持久状态、确定性工具、模型无关的动作接口以及跨代理的测试时选择使得运行可审计且可重复。使用本地托管的Qwen3.5-27B，无需微调，在官方评估器上TTS@8，Kozuchi在SWE-bench Verified的500个实例中解决了374个。在Multi-SWE-bench Java上不变，同一个27亿参数代理解决了41/128个实例（32.03%），在严格开源权重提交中排名第一，在总共42个中排名第四；在Python上排名第12/135，并在开源权重系统中排名第一。各阶段行为在语言间保持±5个百分点以内。剩余失败主要反映语义正确性、Java特定的harness问题和选择错误。在两条轨道上，按参数数量计算，结果与开源/本地同行相比具有竞争力。对候选多样性、选择器遗憾和补丁可靠性的分析表明，剩余差距主要是语义正确性和选择，而非编辑格式或专有模型访问。在操作上，可复用的CI阶段将跨异构内部集群的操作员接触点从五个减少到一个。

## Abstract
Industrial software-engineering teams increasingly need LLM agents that turn bug reports into correct patches, yet benchmark-scale operation adds long horizons, tool-use discipline, context persistence, heterogeneous clusters, and evaluation reuse. We present Kozuchi Agent, a language-agnostic open-weight repair agent and CI-operated evaluation pipeline. Explicit phases, persistent state, deterministic tools, a model-independent action interface, and cross-agent test-time selection make runs auditable and repeatable. With locally hosted Qwen3.5-27B, no fine-tuning, and TTS@8, Kozuchi resolves 374/500 SWE-bench Verified instances on the official evaluator. Unchanged on Multi-SWE-bench Java, the same 27-billion-parameter agent resolves 41/128 instances (32.03%), ranking first among strict open-weight submissions and fourth of 42 overall; on Python it ranks 12th of 135 and first among open-weight systems. Per-phase behavior remains within +/-5 percentage points across languages. Remaining failures mainly reflect semantic correctness, Java-specific harness issues, and selection errors. Across both tracks, results compare favorably with open/local peers by parameter count. Analysis of candidate diversity, selector regret, and patch reliability shows that the remaining gap is primarily semantic correctness and selection rather than edit formatting or proprietary-model access. Operationally, reusable CI stages reduce operator touch-points from five to one across heterogeneous internal clusters.

# Kozuchi Agent：语言无关的开源权重软件修复代理——论文总结

## 1. 核心问题与整体含义

工业软件工程团队越来越需要一种 LLM 代理，能够接收 issue 描述和仓库状态，自动生成正确、可通过测试的补丁。论文指出，在 SWE-bench 类基准规模下，实现这一目标远比选择模型本身复杂，面临四大操作痛点：

- **长周期运行**：真实修复涉及复现 bug、生成回归测试、定位根因、编辑多文件、验证结果，往往需要数十甚至数百轮 LLM 调用，自由式规划在长时域下容易退化（跳过复现、重复分析、修复未理解的代码）。
- **工具语法漂移**：不同模型家族的工具调用语法不一致，小的语法错误会使合理动作失效，导致大量轮次浪费。
- **多集群异构性**：内部集群（GPU 推理、VM 测试、Docker 评分）运维需求不同，需要统一运行时。
- **评估成本**：完整重跑 SWE-bench Verified 的 Docker 评分开销极高，需要可复用的 CI 流水线。

论文的核心主张是：**在可审计、可重复的修复 harness 和跨代理测试时选择机制下，一个本地托管的 27B 开源权重模型也能达到极具竞争力的修复性能**，同时将工业评估管线的操作成本大幅降低。

## 2. 方法论

### 2.1 核心思想
Kozuchi Agent 建立在 mini-swe-agent 基础运行时之上，通过多种 harness 机制实现“可审计性”和“可重复性”：

- **显式阶段（Phases）**：将问题解决分解为 8 个语义明确的阶段（复现、测试合成、定位、修复、验证、报告等），通过配置化的阶段图和 15 条有向边连接，成功或放弃均有明确路径。
- **持久共享状态**：使用文件系统而非原始对话作为持久记忆，阶段交接（handover）时写入简洁 memo 和关键工件，避免上下文压缩导致证据丢失。
- **确定性工具沙箱**：仅提供三个确定性 SE 工具——`line_trace`（动态行跟踪）、`caller_trace`（调用者发现）、`line_edit`（有保护的编辑），按阶段门控注入，保证可审查性。
- **模型无关动作接口**：将“每个回合一个可执行动作”的逻辑合约与模型特定语法分离，支持 4 种表面格式，切换模型族时只需改配置而非 fork 代理。
- **Orchestra 运行时**：每个回合由“规划者”和“格式化者”两个角色处理，都使用同一本地模型；格式化者仅重写可执行动作，降低格式失败率。

### 2.2 跨代理测试时选择（Cross-Agent Test-Time Selection）
这是论文最重要的方法贡献：

- 使用 **K=8** 次独立运行同一模型，每次产生候选补丁和其自选的测试（FAIL_TO_PASS 和 PASS_TO_PASS）。
- 选择器不接触隐藏测试，而是将每次运行的测试交叉应用到所有候选补丁上，形成 K×K 执行矩阵。
- 得分公式（文字描述）：候选 i 的得分 = 对 j 求和 (w_B × 候选 i 在 run j 的 bug 揭示测试上的通过率 + w_R × 候选 i 在 run j 的回归测试上的通过率)，再除以 K。
- 权重固定为 **w_B=0.3, w_R=0.7**（非学习的工程先验，回归比 bug 测试更重要），平票时选更短补丁。

## 6. 主要结论与发现

- **Python 性能**：374/500（74.80%，Wilson 95% CI [70.82, 78.41]），在 135 个提交中排名第 12，**开源权重系统中排名第 1**；显著优于 16/17 个开源同行（BH-FDR q≤0.05），比 480B Qwen3-Coder 多解 26 个实例。
- **Java 性能**：41/128（32.03%），总体排名第 4/42，**严格开源权重中排名第 1**；显著优于 34/41 个 Java 同行；与 71B 级 Qwen2.5-72B 相比多解 38 个实例。
- **选中器价值**：cross-agent selector 比 order baseline 多解 14 个实例（376 vs 362）；达到 oracle ceiling（408）的约 92%。
- **失败模式**：未解决实例中 91.3% 是补丁能干净应用但不翻转隐藏测试（WRONG_FIX），0% 是 diff 格式错误或空补丁——**剩余差距主要是语义正确性而非编辑能力**。
- **可靠性**：495 个轨迹全部正常提交，494/495 补丁干净应用；补丁 LOC churn 是与结果相关性最强的单特征（r=-0.197, p=1.1×10⁻⁵）。
- **跨语言迁移**：阶段分解、动作接口、持久状态和选择器从 Python 迁移到 Java 不变；逐阶段消息占比差异在 ±5 个百分点内。
- **运营改进**：CI 复用使每个评估周期的操作接触点从 5 个降到 1 个，估计操作时间从约 75 分钟降到约 5 分钟（注：这是量级估计而非受控前后对照）。

## 7. 优点

- **强可审计性**：显式阶段图、持久文件系统、确定性工具和公开的 495 条轨迹，使长时域代理行为可事后审查、可恢复。
- **模型不可知设计**：动作格式抽象层避免为每个模型族 fork 代理，降低集成成本。
- **统计严谨**：使用配对 McNemar 检验、FWER/FDR 多重校正、仓库级聚类 bootstrap，避免仅凭聚合率排名下结论。
- **创新选择机制**：跨代理测试交叉应用是一种不依赖学习验证器、不泄漏隐藏测试的纯执行式选择方法，并给出清晰的 oracle 上界和遗憾分析。
- **跨语言实证**：同一 27B 模型在 Python 和 Java 上同时获得开源第一，提供了语言无关 harness 的强证据。

## 8. 不足与局限

- **机制归因不足**：phase graph、formatter、持久状态、工具沙箱、CI 复用等核心组件未做受控消融，只能依靠操作性签名推断，论文自己也承认这一点。
- **算力测量不精确**：GPU 小时数仅为墙钟推导的上界，未采集 GPU 利用率，无法精确量化成本。
- **选择器权重非学习**：w_B=0.3、w_R=0.7 是手工设定的工程先验，虽做了 7 组敏感性扫描，但未在留出数据上系统搜索最优权重。
- **Java 实验受限**：Multi-SWE-bench Java 只发布 xcheck 选择后的源运行统计，缺少完整的逐 leg pass@1 报告；且 elastic/logstash 占 38/128 实例，Kozuchi 全部未解决，说明语言/仓库特定因素仍需细分。

- **对比快照的时效性**：Python 排名基于 2026-04-28 的冻结快照，后续新提交可能改变排名；闭源模型的具体配置和运行细节也无法完全核实。
