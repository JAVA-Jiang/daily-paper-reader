## 摘要
我们提出了OPENHARMONY BENCH，一个应用级编码基准，用于评估基于LLM的编码代理在OpenHarmony ArkTS应用上的表现。与函数级基准不同，它评估完整的应用级更改：每个任务要求代理修改一个可构建的ArkTS项目，使请求的行为端到端地工作，涉及UI状态、数据持久化、构建配置和平台API。该基准在设备上安装并驱动交付的应用，以检查行为是否可观察。它涵盖三种输入来源：自然语言功能请求（新功能）、结构化场景规格（规格驱动）和错误描述（错误修复）。该基准包含153个顶层任务和242个功能点（F点），其中F点是一个可执行的行为检查。快照包括32个新功能任务、50个规格驱动任务（含139个F点）和71个错误修复任务。主排行榜按顶层任务评分，而非独立加权F点。我们描述了基准构建、统计和构建与测试评估流水线，并评估了DevEco Code与八个LLM在每次配置三次独立完整运行中的表现。三个发现浮现：第一，在评估的模型家族对中，新一代模型比前代完成更多任务；第二，可构建性接近饱和，而行为正确性未饱和：平均最终构建成功率在94.77%到100.00%之间，而平均任务完成率在48.36%到58.39%之间；第三，在全部检查的任务评分下，规格驱动任务的任务完成率最低，没有配置超过35%。代码、数据、任务、参考解决方案、测试、评估脚本和排行榜通过官方OPENHARMONY BENCH网站发布：https://bench.matrix.openharmony.cn/。

## Abstract
We present OPENHARMONY BENCH, an app-level coding benchmark for evaluating LLM-based coding agents on OpenHarmony ArkTS applications. Unlike function-level benchmarks, it evaluates complete app-level changes: each task requires an agent to modify a buildable ArkTS project so that a requested behavior works end to end, involving UI state, data persistence, build configuration, and platform APIs. The benchmark installs and drives the delivered application on a device to check whether the behavior is observable. It covers three input sources: natural-language feature requests (new-feature), structured scenario specifications (spec-driven), and bug descriptions (bug-fix). The benchmark contains 153 top-level tasks and 242 Feature points (F-points), where an F-point is one executable behavior check. The snapshot includes 32 new-feature tasks, 50 spec-driven tasks with 139 F-points, and 71 bug-fix tasks. The main leaderboard is scored over top-level tasks rather than independently weighted F-points. We describe the benchmark construction, statistics, and build-and-test evaluation pipeline, and evaluate DevEco Code with eight LLMs across three independent full-suite runs per configuration. Three findings emerge. First, newer generations complete more tasks than their predecessors within evaluated model-family pairs. Second, buildability is close to saturated while behavioral correctness is not: mean Final Build Success Rate is 94.77% to 100.00%, whereas mean Task Completion is 48.36% to 58.39%. Third, spec-driven tasks have the lowest Task Completion under all-checks task scoring, with no configuration exceeding 35%. The code, data, tasks, reference solutions, tests, evaluation scripts, and leaderboard are released through the official OPENHARMONY BENCH website at https://bench.matrix.openharmony.cn/.

## 一、论文的核心问题与整体含义（研究动机与背景）

- **核心问题**：现有代码生成基准大多停留在函数级、Issue 级或单元测试级，难以评估 LLM 及编码代理（Coding Agent）在真实应用级开发中的综合能力。移动端应用开发（尤其是 OpenHarmony 平台）要求代理不仅生成代码片段，还要将源码级修改转化为可构建、可启动、GUI 行为正确的完整应用，这涉及 UI 组件、页面路由、状态管理、数据持久化、平台 API、构建配置等多维度的协同。
- **研究动机**：尽管已有 SWE-bench、AndroidWorld、Mobile-Bench 等基准，但它们要么聚焦于函数/补丁级别的正确性，要么聚焦于操作既有 App 的 GUI 任务，**缺少一个面向 OpenHarmony ArkTS 应用、以端到端可观察行为为验收标准、评估"能否交付完整功能"的基准**。OpenHarmony 的 ArkTS/ArkUI 生态具有广泛的应用场景，且其平台 API、构建工具快速演进，非常适合作为应用级编码评估的载体。
- **整体含义**：论文提出 **OPENHARMONY BENCH**，填补了应用级（App-level）编码基准的空白——代理必须交付"构建成功 + 行为正确"的完整应用，而非仅满足局部检查。这为评估 LLM 编码代理在真实平台工程环境中的交付能力提供了可复现的实验场。

## 二、论文提出的方法论（核心思想与关键技术细节）

### 核心思想
- **以"可观察行为"而非"补丁相似度"为验收标准**：代理面对的是自然语言需求或规范描述，并不知道具体测试；评测仅通过构建和可执行 UI 测试来判断交付是否满足需求，避免代理对 oracle 的过拟合。
- **双单元体系**：
  - **顶层输入（Top-level task）**：评分单元，一个任务 = 一个新功能请求、一个规格说明书或一个 Bug 报告。排行榜按顶层任务计分。
  - **功能点（F-point）**：检查单元，即一条可执行的行为检查。绝大多数任务一个 F-point，规格驱动任务平均每任务 2.78 个 F-point，但任务必须**全部 F-point 通过**才计为完成（all-or-nothing）。

### 基准结构（三类任务来源）
1. **New-feature（32 个任务）**：需求式增量功能开发，基于华为官方模板项目，要求代理理解并修改现有工程，实现新业务功能。
2. **Spec-driven（50 个任务，139 个 F-points）**：标准化场景级规范，源于开源项目，经预处理、人工筛选与策划合并，涵盖多个可观察行为，强调精确的规格遵循。
3. **Bug-fix（71 个任务）**：源自真实开源项目的历史 Bug 修复 PR，要求故障定位与修复，测试必须能从"失败→通过"区分修复前后状态。

### 评估流水线（六阶段）
1. **工作区初始化**：从任务脚手架或基础项目创建干净工作区。
2. **代理执行**：代理接收任务描述、项目上下文、系统指令、工具访问权，产出修改后的工作区。
3. **Diff 记录**：记录是否产生非空 diff（诊断信号，非正确性信号）。
4. **首次构建**：记录在编译修复前的首次构建结果。
5. **编译修复**：若首次构建失败，允许至多 5 轮编译修复循环（仅返回构建日志，不泄露测试或 oracle 信息）。
6. **行为验证**：最终构建成功后，通过 HDC 安装 App 到模拟器/设备，用 Hypium 执行 Python 任务级 UI 测试。

### 指标定义（核心公式）
- **Task Completion（TC）**：主指标，任务构建成功且全部可执行检查通过，才记为完成。
  \[
  TC_{c,r}(S)=\frac{C_{c,r}}{N}, \quad TC_c(S)=\frac{1}{k}\sum_{r=1}^{k}TC_{c,r}(S)
  \]
  其中 \( k=3 \) 次独立完整运行，报告三次运行的算术平均值。
- **Final Build Success Rate（FBR）**：最终构建成功率（代理运行及允许的编译修复后）。
- **First Build Success Rate（IBR）**：首次构建成功率（编译修复前）。
- **Run Range**：三次运行中观察到的 TC 最小值和最大值，作为描述性区间而非统计推断区间。

## 六、论文的主要结论与发现

1. **总体性能**：在 153 个任务上，**GLM-5.2 取得最高平均任务完成率 58.39%**（约 89.3/153 任务），Kimi-K3 和 Qwen3.8-Max-Preview 分别以 57.30% 和 55.99% 紧随其后。
2. **代际提升**：在评估的模型系列内部，新一代模型普遍优于前代（GLM-5.2 > GLM-5.1，Qwen3.8 > Qwen3.7，Kimi-K3 > Kimi-K2.7-Code）。
3. **可构建性与行为正确性脱节**：最终构建成功率已达 94.77%–100.00%，而任务完成率仅为 48.36%–58.39%——表明**大量项目"能编译但不正确"**，行为级正确性是当前主要瓶颈。
4. **规格驱动任务最难**：spec-driven 任务在 all-or-nothing 评分下任务完成率最低，**所有配置均未超过 35%**（Kimi-K3 最高为 34.67%），反映精确遵循多场景规格并端到端实现的高难度。
5. **Bug-fix 相对最好**：任务完成率最高（Kimi-K3 为 75.12%），且剩余失败主要是行为层面的而非编译失败。

## 七、优点（方法与实验设计的亮点）

1. **端到端行为验证范式**：不是检查补丁相似度，而是**在真实设备/模拟器上安装应用并执行 UI 测试**，直接验证用户可见行为，避免"编译通过=正确"的假象。
2. **三源任务结构**：需求式开发、规格驱动开发、Bug 修复三类任务互补，覆盖真实工程中的典型工作模式，提升基准的生态代表性。
3. **F-point 细粒度 + 顶层任务评分的双层体系**：既保留了规格驱动任务的细粒度诊断信息，又保持排行榜评分单元的一致性。
4. **防泄露设计**：测试对代理不可见、编译修复仅提供构建日志、F-point 必须满足 fail-to-pass 准则，降低了"刷分"风险。
5. **严格的质控流程**：双策展人验证、参考解决方案两次通过门槛、测试不区分状态即剔除，保证任务质量。
6. **透明的可复现性**：公开完整快照信息（版本、日期、脚本、设备配置、模型标识），记录基准版本和评估脚本快照，支持时间维度上的可比性。
7. **构建与行为双维度指标**：首次构建/最终构建/任务完成率分离评估，清晰刻画了"代理解决策略"与"行为正确性"两个不同层面的能力。

## 八、不足与局限

1. **单一代理框架**：所有结果基于 DevEco Code，未对比多种代理框架（如 AutoGPT、SWE-agent 等），结论的外推性受限，只能解释为"DevEco Code–模型"配置对的差异。
2. **重复运行次数有限**：每配置仅 3 次完整运行，只能提供描述性的 min–max 范围，无法给出置信区间或严格的统计显著性判断；相邻排名的区分度存疑。
3. **训练污染风险**：bug-fix 来源为历史公开 PR，存在预训练暴露风险；开放发布也可能引入未来污染。论文对此有意识但未能完全消除。
4. **资源指标不可直接横比**：不同提供商的 tokenizer 和缓存计费方式不同，token 数仅能表示数量级；墙钟时间受本地硬件影响，不可跨环境比较。
5. **覆盖面局限**：39 个高频 Kit 中仅覆盖 29 个，且多数 Kit 出现在少数任务中；10 个 Kit 未被覆盖。这限制了基准对 OpenHarmony 平台 API 全景的评估范围。
6. **难度标注为主观元数据**：任务难度（easy/medium/hard）由策展人判断，论文明确说明不是校准的性能预测器。
7. **规格驱动任务可能过严**：all-or-nothing 的评分方式对多 F-point 任务非常严格，可能与实际工程中"部分功能已可用"的开发状态不完全匹配，但这是设计选择而非疏忽。
8. **无消融实验**：未对代理框架组件（如提示模板、工具集、编译修复轮数、推理预算）做消融分析，无法判断哪些设计选择对结果影响最大。
