## 摘要
大多数技术型HCI研究项目的软件工件无法获取。缺乏访问这些工件的途径限制了学术知识的生产。这导致难以扩展或重用研究工件、在评估后续工作时使用强基线，以及进行复制或可重复性研究。在本工作中，我们展示了新型代理式AI技术在复活交互软件方面的潜力——直接从研究论文中重新实现系统。为了衡量该方法的成功程度，我们提出了一种可复活性度量。通过复活来自UIST的最新研究论文，并采访其原始作者，我们证明了复活系统的可行性（及局限性）。结果是令人鼓舞的：在许多情况下，生成的代码足以作为强基线使用。我们认为，这可能代表着技术HCI社区中我们生产、使用和评估研究工件的方式发生了根本性转变。

## Abstract
Software artifacts for most technical HCI research projects are unavailable. The lack of access to these imposes limits on academic knowledge production. It is difficult to: extend or reuse research artifacts; use strong baselines in evaluating follow-up work; and perform replication or reproducibility research. In this work, we demonstrate the potential of new agentic AI technologies to revibe interactive software: reimplement systems directly from research papers. To measure the success of the approach, we describe a revibeability metric. By revibing recent research papers from UIST, and interviewing their original authors, we demonstrate the plausibility (and limitations) of revibed system. The results are encouraging. In many cases producing code suitable for strong baseline use. We argue that this may represent a fundamental shift in how we produce, use, and evaluate research artifacts in the technical HCI community.

  2. 无法在后续工作中以原系统作为强基线（strong baseline）进行 A/B 对比评估；
  3. 复制（replication）和可重复性（reproducibility）研究无从开展。
- **后果**：知识生产被扭曲为“孤立的新颖性导向”——研究者因无法与既有系统直接比较，倾向于开拓全新方向，而不是在已有成果上增量推进。

- **核心主张**：本文提出 **revibe（复活）** 概念——仅基于论文章节和图像，由代理式编程工具自动重实现交互式软件系统；并定义 **revibeability（可复活性）** 作为量化评估指标。作者认为这可能为技术 HCI 社区带来**范式级的转变**：改变研究工件的生产、使用和评估方式。

## 二、方法论

### 核心概念

- **Revibe（动词）**：仅根据学术论文内容重实现软件工件；**revibe（名词）**：重构建出的工件本身。
- **目标定位**：不是追求与原始系统完全一致的高保真复制，而是足以作为 **A/B 测试中强基线** 的中等保真度重实现。
- **Vibe-coding 强调**：开发者和评估者全程**不接触代码**，只通过自然语言提示与代理环境交互，从而排除开发者编程技能的影响，测得“重实现的底限（floor）”。

### Revibeability 指标公式

使用系统特定的测试 rubric（测试评分标准）对重实现逐项打分，聚合得分为：

```
revibeability = (w_s·|t_success| + w_p·|t_partial| + w_f·|t_failure|) / (w_s·|t_all|)
```

其中权重：w_s = 2（完全成功）、w_p = 1（部分成功）、w_f = 0（失败）。

### 四步流程

1. **文本提取（步骤1）**：使用 PyMuPDF 将 PDF/HTML 解析为按章节命名的 Markdown 文件和图片，供后续处理。
2. **Rubric 自动生成（步骤2）**：通过专用构造提示，让 LLM 从论文章节和图像中提取关键 UX 元素和功能，生成结构化的手动测试评分表（interaction_validation.md）。每个测试包含：ID、前置条件、操作步骤、预期结果、三级成功标准（完全成功/部分成功/失败）、观察结果空白栏。测试按应用界面、跨应用集成、边缘情况三个层级组织。
3. **Unaided Revibe（步骤3-6）**：将论文章节和图片提供给代理编程工具，附初始提示（分析系统特征→创建 Web 应用或合适架构→生成 DEVELOPER.md 和 README.md）→运行系统并将报错反馈修复 → 发送“对比论文补齐缺失功能”的提示 → 产出可运行版本 → 评估者按 rubric 逐条测试打分，得到第一轮评分。
4. **Aided Revibe（步骤7-10）**：将打分后的 rubric 反馈给代理环境（“请修复 rubric 中报告的问题”），生成新版本后再评估；可多次迭代（本文最多两轮）。

### 关键设计决策

- 假设原文源代码不存在，避免模型在训练中见过原代码。
- 允许使用等效 API（如 OpenAI 换 Gemini）。
- 不接受开发者直接修改代码，只通过自然语言提示驱动。

## 三、实验设计

### 系统选取

- 从 UIST 2020–2024 年论文中，基于 Semantic Scholar 引用量筛选出 20 个纯软件型系统（排除含硬件、VR、已公开代码的系统，见附录 A.1）。
- 从 20 个中随机选出 10 个用于完整 revibe 实验：**B2、CoLadder、GenAssist、mage、Rescribe、Sketch-n-Sketch、Spellburst、EvalGen、Vizability、XCreation**。
- 额外做了 **PromptPaint** 的 revibe 尝试但因 GPU 限制失败，未计入正式结果。

### 代理环境与模型

- 三个代理式开发环境：**Claude Code**（claude-sonnet-4-6）、**Cursor**（gpt-5.4-xhigh）、**Gemini CLI**（gemini-3.1-pro / gemini-3-flash）。
- 10 个系统用 Gemini 和 Claude 各重实现一遍，7 个系统额外用 Cursor 重实现，总计 **27 次重实现**。
- 额外对照实验：mage 和 Spellburst 两个系统加测了 “Cursor 配 claude-sonnet-4-6” 的组合，以探究代理架构与模型的独立效应。

### Rubric 生成对比实验

- 用全部 20 个系统对比 Claude Code 与 Gemini 生成的 rubric，统计测试数量、文件大小、每个测试的步骤数。

### 作者访谈

- 访谈了 Spellburst（1 位）、B2（1 位）、mage（3 位）的原始作者，30–40 分钟 Zoom 通话，展示重实现并收集反馈。
- 访谈开始时未告知系统由 AI 生成以避免偏见，结束前进行说明。

### 评估方式

- 评估者为 CS 博士生、博士后和教师，均具备技术 HCI 经验。
- 每个系统按 rubric 测试打分（失败/部分/完全），汇总得 revibeability 分数。

## 四、资源与算力

- 原文**未提供 GPU 型号、数量或训练时长等硬性算力信息**（因为它不涉及模型训练，而是推理/代码生成任务）。
- 可用信息：
  - 每次自动 revibe 循环主要耗时 **30 分钟以内**；
  - 首次（unaided）revibe 的 API 成本约 **15 美元以下**，后续迭代因基于已有代码修改而更低；
  - **最大时间开销是人工 rubric 评估**：首轮每测试 1–2 分钟；
  - PromptPaint 案例中，因运行 Stable Diffusion 需要 **GPU 但环境无 GPU 访问**而失败，说明 revibeability 隐式依赖环境算力对齐。

## 五、实验数量与充分性

- **重实现实验**：10 个系统 × 3 个环境（其中 3 个系统未用 Cursor）= 27 次重实现，每轮含 unaided + 2 轮 aided。
- **Rubric 对比实验**：20 个系统的 rubric 生成对比。
- **作者访谈**：3 个系统、5 位作者。
- **覆盖的评估内容**：全面覆盖主要交互功能、跨界面集成、边缘情况。

**充分性评价**：
- 优点：系统数量（10 个）在同类研究中属较大规模；三个主流代理环境形成对比；作者访谈提供了外部效度验证。
- 不足：
  1. 每个系统每个环境**只执行一次**，未做多次重复以评估随机性影响；
  2. “最佳运行”（best-run）指标可能有幸存者偏差（用最高分而不是首次/中位数）；
  3. 得分方差较大（Claude std=0.16, Gemini std=0.18），说明结果对代理环境高度敏感；
  4. 评估者内部一致性未做校准；
  5. rubric 全部由 Claude Code 生成，对 Claude 产物可能存在隐性偏差（作者辩称 Cursor 用同一 rubric 也获得好成绩，但该论证不够强）；
  6. Bootstrap 分析（附录 A.4）表明置信区间较宽，个别系统 B2 和 CoLadder 的下界接近 0.75，结果解释需谨慎。

## 六、主要结论与发现

1. **可行性得到验证**：10 个系统中 2 个（Vizability、XCreation）达到完全 100% revibeability。
2. **分数与迭代效果**：
   - 两轮 aided 反馈后，平均 revibeability **94%**（均值），最低 80%，最高 100%；
   - “最佳运行”（任一环境任一run中的最高分）均值 0.939（min=0.8, max=1, stdev=0.069）；
   - Claude Code 起评分高：mean=0.87；Cursor mean=0.912；Gemini 明显较弱：mean=0.67；
   - 大多数情况下得分随迭代单调递增（仅有 4 次微小下降，幅度 <0.02）。
3. **Rubric 长度与上限负相关**：rubric 越长（系统越复杂），最佳 revibeability 越低（Pearson r = -0.74, p < .05）。
4. **Claude 生成的 rubric 显著更细致**：测试数量约为 Gemini 的 3.5 倍（35 vs 10），文件长度约 5 倍，步骤数 1.6 倍。
5. **定性发现**：
   - **近实现**：用新的等效 API 替代已退役的 GPT-3.5（如 Spellburst），以及因新模型不再出错而导致旧的错误处理功能失效；
   - **失败特征**：mage 的拖拽功能均未正确实现（且未发现任何环境能做到）；
   - **过度实现**：agent 常实现论文中标注为“未来工作”的功能（如 mage 的 Altair 版本、附加组件）；
   - **环境错配**：mage 和 B2 原为 Jupyter 插件，所有 agent 默认构建了独立 Web 应用——虽然功能覆盖率不低，但并不符合原作者的设计意图；
   - **Rubric 读取问题**：agent 回读 rubric 时可能只看“Observed result”字段，忽略成功/失败的定义行，导致修复不准确。
6. **作者访谈反馈**：
   - Spellburst 作者认为“设计与交互范式几乎完全对应”；
   - mage 作者指出 Jupyter 原生态环境对用户体验至关重要，重实现环境不值得完全满意；
   - B2 作者表示大部分缺失功能通过更多提示就能补全；
   - 作者们**自己也无法记住全部实现细节**——印证了论文写作时附带 rubric 的价值。
7. **不可 revibe 的范围**：对 UIST 2025 的约 210 篇论文评估显示，约 65% 可完全 revibe、15% 部分可 revibe（有硬件+软件混合贡献）、约 20% 纯硬件不可 revibe。

## 七、优点

- **概念创新**：首次系统化提出 “revibe” 和 “revibeability” 概念，并与 vibe-coding 思潮衔接，定义清晰、具有可操作性。
- **方法自动化程度高**：从文本抽取到 rubric 生成到代理反馈修复全程有固定流程，rubric 可自动生成，具备可扩展性。
- **消除开发者技能变量的实验设计**：通过纯自然语言交互排除编程技能影响，测得的“底限”结果具有方法论价值。
- **评估体系结构化**：rubric 测试（三级打分）兼顾交互功能、跨模块集成和边界情况，聚合公式透明、可复现。
- **外部验证充分**：访谈原始作者作为效果验证手段，增强了研究结论的生态效度。
- **跨代理环境对比**：同时使用三种主流代理工具，并专设 Cursor+Claude 模型对照实验（附录 A.2），剖析代理架构与模型各自的贡献。
- **诚实报告失败**：论文详细记录了失敗案例（PromptPaint 因 GPU 不可用而失败；mage 拖拽未被实现），为后续研究提供了参考。
- **对社区影响深远的讨论**：从知识生产、教育、论文评审、可复现性文化等多个维度讨论了 revibe 范式的影响。

## 八、不足与局限

1. **系统覆盖有限且偏向 Web 应用**：
   - 仅测试了 UIST 2020–2024 的部分纯软件系统，未覆盖硬件依赖型、JR 插件型、桌面应用型等更多形态的系统；
   - 提示词明确要求“尽量做成 Web 应用”，导致 Jupyter 插件类系统（mage、B2）的代表性受限。
2. **存在潜在评估偏差**：
   - rubric 全部由 Claude Code 生成，Claude 可能因自生成测试而得分偏高（作者仅以 Cursor 在 Claude rubric 下也好成绩来弱化这一顾虑，论证不够充分）；
   - 评估者同时是重实现执行者，可能对“部分成功/失败”判定存在主观性；
   - 未做多次独立 run 以量化随机性，也未做评估者间信度（inter-rater reliability）检验。
3. **模型/环境快速变动导致结果的时效性问题**：代理工具更新频繁，Gemini 与 Claude 的差距可能在版本迭代后改变。
4. **对非 UI 贡献覆盖不足**：rubric 集中于界面交互，无法直接测试后端算法质量（如 Rescribe 的动态规划优化、EvalGen 的选择性采样），反馈机制对这类系统不够对症。
5. **环境依赖限制**：GPU 缺失、API 模型退役、预训练数据中训练样本不匹配等问题使部分系统无法完全重实现，实际 revibe 需要一定的基础设施匹配度。
6. **成本虽不高但人工评估仍是瓶颈**：对于大型系统，rubric 评估耗时可能显著（如 Spellburst 的完整场景测试需 15–20 分钟），规模化应用受限。
7. **过度实现与简化实现并存**：代理工具可能在实现“未来工作”上耗费资源，同时对关键功能采取简化策略（如其内部系统提示强调“avoid over-engineering”），偏离论文本意。
8. **对原始论文质量的强依赖**：如果论文截图模糊、特征描述不完整或作者记忆出错（访谈中的实际发现），revibe 的质量上限将受到抑制。
9. **潜在负面后果**：可能使研究者面临“论文必须可 revibe”的评审压力，或进一步削弱作者公开原始代码的动机；agentic 编程本身的资源/环境成本也是需关注的问题。
