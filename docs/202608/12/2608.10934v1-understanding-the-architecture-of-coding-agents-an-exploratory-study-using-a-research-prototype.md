## 摘要
编码代理已迅速成为AI辅助软件开发的主要界面。然而，尽管其采用率日益增长，但对其内部架构的了解相对较少，目前也没有像编译器或操作系统那样系统性的架构描述。本文通过记录编码代理的主要架构组件、解释其职责、交互和执行流程来解决这一空白。为支持这项工作，我们还介绍了Ark（Agent Research Kit），一个为研究和教育设计的极简开源编码代理，它在保留现代编码代理基本架构机制的同时，强调简洁性和清晰性。我们还引入了ArkBench，一个包含十个代表性软件维护与演进任务的轻量级基准。使用gpt-5.4-mini，Ark成功解决了10个任务中的8个，且所需token消耗适中。最后，我们使用最近提出的架构分类法将Ark的架构与最先进的编码代理进行了比较。我们希望Ark和ArkBench能为编码代理的教学、研究和实验提供实用基础。

## Abstract
Coding agents have rapidly emerged as the primary interface for AI-assisted software development. However, despite their growing adoption, relatively little is known about their internal architecture, and no systematic architectural description comparable to those available for compilers or operating systems currently exists. This paper addresses this gap by documenting the main architectural components of coding agents, explaining their responsibilities, interactions, and execution flow. To support this effort, we also present Ark (Agent Research Kit), a minimal open-source coding agent designed for research and education that preserves the essential architectural mechanisms of modern coding agents while emphasizing simplicity and clarity. We also introduce ArkBench, a lightweight benchmark comprising ten representative software maintenance and evolution tasks. Using gpt-5.4-mini, Ark successfully solved 8 of the 10 tasks while requiring modest token consumption. Finally, we compare the architecture of Ark with those of state-of-the-art coding agents using a recently proposed architectural taxonomy. We hope that both Ark and ArkBench provide a practical foundation for teaching, research, and experimentation on coding agents.

## 3. 实验设计

### 3.1 基准介绍：ArkBench

为了评估Ark，作者设计了**ArkBench**：一个面向软件维护与演进任务、刻意保持轻量级的小型基准。基准基于一个过程式电商应用（约10个文件，每个文件单一职责），使用Python原生数据结构（字典、列表），避免外部框架和数据库的偶然复杂度。

基准包含**10个独立维护任务**，均有完整代码副本：

- **Bug修复（3个）**：目录分页的差一错误（off-by-one）；拒绝无客户或产品的订单；折扣阈值计算错误
- **重构（3个）**：提取重复的小计计算为共享函数；将价格格式化函数移到专用文件；重命名公共产品搜索函数并更新调用
- **功能实现（4个）**：按价格区间过滤产品；按价格排序产品；导出CSV格式订单报告；按产品类别分组销售

### 3.2 任务结构与评估方式

每个任务遵循统一目录结构：
- `prompt.txt`：以GitHub issue风格描述任务，**不指明需要修改的文件**
- `tests/`：公开测试（代理可访问）
- `evaluation/`：隐藏的后置测试和结构化验证脚本（仅在任务完成后执行）

对于重构任务，还有专门的结构验证脚本（如检查新提取的函数是否存在、函数是否真的移动到目标文件、旧公共API是否完全移除）。

### 3.3 对比方法

论文不直接与其他编码代理在ArkBench上对比（作者明确声明这不是目标），而是使用Rombaut最近提出的架构分类法，将Ark与两个代表性代理在**十二个维度、三个层次**上进行架构层面的系统比较：
- **Codex CLI**（OpenAI）：商业编码代理的代表
- **OpenCode**：最流行的开源编码代理之一，代表社区驱动的项目

比较维度覆盖控制架构（控制循环类型、驱动者、实现方式）、工具与环境接口（工具集大小、编辑格式、工具发现机制、上下文检索、执行隔离）、资源管理（状态管理、上下文压缩、多模型路由、持久内存）。

## 6. 主要结论与发现

1. **架构可行性**：采用极简架构的Ark在gpt-5.4-mini驱动下，成功解决**10个任务中的8个（80%）**，证明了不依赖复杂模块也能构建功能正常的编码代理。

2. **效率良好**：平均每任务仅23.5秒、3342个token、7.1次工具调用，整个基准测试API成本低于0.50美元，表明极简架构在计算效率上的优势。

3. **失败案例分析**：
   - bugfix-02：部分修复——公开测试通过但隐藏测试失败，原因是异常类型使用错误（KeyError而非ValueError）
   - refactor-03：重命名未全量传播——函数定义和可见测试已更新，但遗漏了导入和部分调用点，导致隐藏评估阶段出现导入错误。这反映了一个**常见的LLM代理局限**：主变换正确但容易遗漏次要依赖

4. **架构比较结论**：
   - **控制层面**：Ark与Codex CLI、OpenCode一致——均采用LLM驱动的ReAct循环、命令式while循环实现
   - **工具与接口层面**：主要差异在于Ark工具集更小（5个vs 18+）、静态而非动态工具发现、仅关键词搜索、无平台级沙箱
   - **资源管理层**：Ark的状态管理为“破坏性截断”（直接丢弃旧历史）而非LLM摘要压缩；无多模型路由；无持久化记忆

5. **核心信息**：极简实现可以保留现代编码代理的核心架构原则（尤其控制架构），同时显著缩小系统规模，更适合教学、研究与快速实验。

## 8. 不足与局限

1. **比较维度有限**：未在ArkBench上将Ark与Codex CLI或OpenCode进行直接基准对比，缺乏关于“Ark相对其他代理的实际性能差距”的量化证据（虽然这不是论文所声明的目标）。

6. **架构简化带来的实用限制**：
   - 上下文压缩采用直接丢弃旧历史（大小截断）而非LLM摘要，长任务中可能丢失关键信息
   - 无持久化记忆/会话机制，无法跨执行复用知识
