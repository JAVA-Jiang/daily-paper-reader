## 摘要
大语言模型广泛用于生成源代码或JSON等结构化输出。语法约束解码（GCD）通过掩蔽违反上下文无关文法规则的标记，可以保证生成输出的语法有效性。然而，现有GCD方法的在线计算开销（延迟通常随词汇表大小线性增长）限制了大语言模型的吞吐量，尤其是对于词汇量大的模型。为解决这一问题，我们提出PSC，一种新颖的语法约束解码方法。通过在预处理阶段将所有词汇标记的接受条件合并为解析器栈上的单个分类器，PSC可以在每个解码步骤仅检查一次解析器栈的情况下计算完整的词汇掩码，时间复杂度与词汇表大小无关。实验表明，在复杂编程语言文法上，PSC计算掩码的速度比基线快达700倍，在符合模式的JSON上快达30倍；使用PSC的端到端大语言模型吞吐量接近无约束解码。我们分析了预处理提供者和解码用户的预处理开销，并提供了盈亏平衡点分析，以帮助用户决定是否自行进行预处理。

## Abstract
LLMs are widely used to generate structured output like source code or JSON. Grammar-constrained decoding (GCD) can guarantee the syntactic validity of the generated output, by masking out tokens that violate rules specified by a context-free grammar. However, the online computational overhead of existing GCD methods, with latency typically scaling linearly with vocabulary size, limits the throughput of LLMs, especially for models with large vocabularies. To address this issue, we propose PSC, a novel grammar-constrained decoding method. By combining acceptance conditions of all vocabulary tokens into a single classifier of the parser stack during preprocessing, PSC can compute the complete vocabulary mask by checking the parser stack exactly once per decoding step, with time complexity independent of the vocabulary size. Experiments show that PSC computes masks up to 700$\times$ faster than baselines on complex programming language grammars, and up to 30$\times$ faster for schema-conformant JSON; end-to-end LLM throughput with PSC approaches that of unconstrained decoding. We analyze the preprocessing overhead for preprocessing providers and decoding users, and provide a break-even point analysis to help users decide whether to do preprocessing by themselves.

## 方法论：PSC（Parser Stack Classification）

**核心思想**

- 现有方法在解码每个步骤时，需要针对词汇表中的大量 token 反复调用解析器来判断合法性（即 O(|V|) 次解析）。
- PSC 的核心洞察是：每个 token 对解析器栈的接受条件可以形式化地描述为一个**有限状态自动机（FSA）**。在预处理阶段，将所有 token 的接受条件合并为一个统一的 FSA 分类器；在线解码时，只需将当前解析器栈输入该分类器**一次**，即可得到完整的合法 token 掩码（掩码以查表方式 O(1) 获取）。

**关键技术细节**

1. **词法预处理**：沿用 GreatGramma 的 lexer 处理方法，为每个 token v 和词法状态 q 预计算可实现终结符序列集合 R_q(v)（包含词法状态转移后的后续可能前缀）。
2. **构造处理 ε 转移的 FST P_ε**：P_ε 将任意解析器栈稳定化（反复执行 ε 转移直到达到稳定状态），其构造基于 PDA 终止性保证状态有限，正确性由 Theorem 1 证明。
3. **构造单个终结符 a 的 FST P̃_a**：模拟 PDA 在栈顶执行一个 a 标记转移的输入输出行为（式 6、7）。
4. **构造任意终结符序列 w 的 FST P_w**：通过组合 P_w = P_ε ∘ P̃_{w₁} ∘ P_ε ∘ … ∘ P_ε ∘ P̃_{wₙ} ∘ P_ε 实现（式 8），正确性由 Theorem 2 证明。
5. **构造统一 FSA A**：将每个 token 的接受条件构造成 I_q · A_w · I_v 的形式（先检查词法状态、再检查栈、最后输出 token），对所有 v∈V 和 q∈Q 取并集，然后进行确定化和最小化，最终得到单一 FSA（式 9）。在线时只需 |α|（栈长度）次状态转移即可得到掩码索引。
6. **理论贡献**：Theorem 3 证明所有接受给定 token 的（词法状态，解析器栈）对构成正则语言，为 FSA 构造提供了理论基础。

**算法流程**

- Algorithm 1（离线预处理）：构造 P_ε → 构造所有 P̃_a → 对每个可达终结符序列构造 P_w → 去掉输出构造 A_w → 合并为 A → 最小化 → 预计算所有掩码。
- Algorithm 2（在线执行）：维护词法状态 q 和解析器栈 α → 将 q 和 α 输入 A 得到状态 s → 查表返回对应掩码 A_s。

## 实验设计

**数据集与场景**

1. **代码生成**：Java、Go、SQL 三个编程语言语法。从 Stack 数据集中各取 1000 个可被 Lark 解析器成功解析的样本作为测试集。
2. **Schema 约束 JSON 生成**：使用 MaskBench 基准（基于 JSON Schema Bench 扩展），随机采样 1000 个 schema，共 1337 个正样本和 2072 个负样本。
3. **下游任务**：Go 生成（Multilingual HumanEval Go 子集 160 样本、MBGP 939 样本、McEval Go 子集 50 样本）、schema 约束 JSON（JSON-Mode-Eval 100 样本）、Text-to-SQL（Spider 开发集 1034 样本）。

**对比基线**

- XGrammar：基于 Earley parser，预计算上下文无关接受/拒绝 token 集。
- GreatGramma：使用 lexer + parser，共享 token 的终结符序列以减少解析次数。
- Formatron：基于 Earley parser，动态剪枝无效解析状态。
- LLGuidance：使用 lexer + Earley parser，将词汇表组织为 trie 并跳过被拒绝的前缀子树。

**模型**

- 三个模型系列：Llama 3.2（128k 词表）、Qwen2.5（151k 词表）、Gemma 3（262k 词表）。
- 吞吐实验使用各系列最小模型（Llama 3 1B、Qwen2.5 0.5B、Gemma 3 270M），另包括 Qwen2.5 7B 以考察模型规模影响。

**实现与执行环境**

- 实验环境：8 块 NVIDIA A100 GPU（40GB），2 个 Intel Xeon Gold 6348 CPU（2.6GHz、56 核），512GB RAM。
- 所有实验使用单 GPU 和单 CPU 线程，保证公平性。
- PSC 实现约 1100 行 Python，基于 Lark 解析器构建 lexer 和 LALR(1) parser。

## 主要结论与发现

1. **正确性**：PSC 在全部语法和模型上样本通过率接近 100%（99.6%-100%），错误均由复用的 lexer 造成，非 PSC 自身问题。
2. **掩码计算效率**：PSC 平均掩码计算开销为 2.2-2.6 微秒/步，相比最佳基线 LLGuidance 在复杂编程语言语法上快 **300-700 倍**，在 JSON schema 上快约 **30 倍**；且开销在不同语法和模型间保持稳定，不随词表大小增长。
3. **端到端吞吐**：PSC 在所有数据集、模型和 batch 大小上均优于 LLGuidance，吞吐接近无约束解码上限；差异在更小模型和更大 batch 时更显著。
4. **下游任务提升**：PSC 的 GCD 在 Go 生成、schema 约束 JSON 生成、Text-to-SQL 三类任务上均稳定优于无约束解码，验证了 GCD 的实用价值。
5. **预处理权衡**：JSON schema 预处理开销小（半分钟）、盈亏平衡点约 20-40 秒解码时间，建议用户自行预处理；编程语言语法预处理开销大（几分钟到 1 小时+），建议使用提供者共享的预处理结果。

## 优点

1. **理论创新**：首先证明"接受特定 token 的解析器栈集合构成正则语言"，为基于 FSA 的栈分类提供了形式化基础。
2. **时间复杂度突破性改进**：将 GCD 的在线掩码计算从 O(|V|) 降至 O(|栈|)，理论上达到任何 GCD 方法的最小检查次数（每步一次）。
3. **跨模型、跨语法的稳定性**：开销几乎不随词汇表大小和文法复杂度变化，与基线随词汇表增长而线性上升形成鲜明对比。
4. **实验严谨性**：使用 teacher-forcing 保证评估条件一致；提供盈亏平衡点分析帮助用户做出实用决策；分析并区分了 PSC 本身错误（无）与 lexer 引入的错误。
5. **工程贡献**：开源实现、数据集、预处理结果和复现脚本，降低使用门槛。

## 不足与局限

1. **仅支持 DCFG**：PSC 基于确定性下推自动机（DPDA），只能处理确定性上下文无关文法。部分现有方法（如 Earley parser 类）可处理更一般的 CFG，适用范围受限。
2. **词法层依赖外部实现**：PSC 复用了 GreatGramma 的 lexer，存在两个已知缺陷：(1) 不支持将单个 Unicode 字符拆分为多个 token 的分词器；(2) 单字符 lookahead 设计在边角情况导致误判。这会导致约 0.1%-0.4% 的样本被错误拒绝。
3. **预处理成本较高**：编程语言文法的预处理器耗时可达 1.3 小时（SQL），内存占用最高达 255 GiB，需要较大计算资源；虽然可共享预处理结果，但用户自行处理时负担较大，需要做盈亏平衡分析。
4. **运行时内存开销**：复杂语法（Go、SQL）的预计算掩码运行时内存占用较大（如 Gemma 3 的 Go 掩码占 6.32 GiB），对内存受限的部署环境可能造成压力。
5. **基准实验的基线公平性风险**：不同方法使用不同语法格式，需要人工转换语法，文法转换质量的微小差异可能影响性能对比的客观性；Formatron 在 SQL 上失败率超过 30%、LLGuidance 在 Go 上报告 ParserTooComplex，说明部分基线可能未处于最佳状态。
6. **下游任务评测限制**：JSON-Mode-Eval 中部分 schema 无法被语法生成脚本处理（5 个样本仅用 JSON 语法兜底、6 个样本替换为等价 schema），可能对评测完整性有轻微影响。
7. **未覆盖的内容**：论文没有涉及非确定性 CFG 的处理、未与其他未开源方法（如 Domino、Koo 等）进行对比，也没有探讨 PSC 在词级（而非 token 级）或其他类型约束（如正则约束）上的扩展。
