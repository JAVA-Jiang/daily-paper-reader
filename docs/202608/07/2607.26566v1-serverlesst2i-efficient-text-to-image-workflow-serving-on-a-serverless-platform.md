## 摘要
文本到图像（T2I）工作流越来越多地部署在无服务器平台上，因为用户经常组合自定义工作流并间歇性地调用它们。现有平台通常将每个工作流部署为一个不透明的GPU函数，将工作流中的所有组成模型一起供应、放置和扩展。这种单体设计掩盖了工作流结构，增加了扩展开销，迫使用户管理底层GPU协调，并在多租户集群中限制了细粒度的公平性。在本文中，我们提出了ServerlessT2I，一个原生无服务器系统，它将T2I工作流分解为松耦合的模型函数，这些函数可以独立管理和调度。通过显式管理单个模型执行，ServerlessT2I实现了按模型扩展、声明式工作流组合、透明的GPU驻留通信和公平感知调度。为了使这种分解高效，ServerlessT2I利用计算密集型T2I推理留下的空闲GPU内存来构建数据平面，从而减少模型加载和数据通信开销。该系统还引入了一个用于多租户服务的公平调度器。使用生产轨迹，ServerlessT2I在相同GPU预算下比现有T2I工作流服务系统维持高达2倍的请求率；对于固定请求率，它在满足服务水平目标（SLO）的同时节省高达3倍的GPU资源。

## Abstract
Text-to-image (T2I) workflows are increasingly deployed on serverless platforms because users often compose customized workflows and invoke them intermittently. Existing platforms typically deploy each workflow as an opaque GPU function, provisioning, placing, and scaling all constituent models in the workflow together. This monolithic design obscures workflow structure, inflates scaling overhead, forces users to manage low-level GPU coordination, and limits fine-grained fairness in multi-tenant clusters. In this paper, we present ServerlessT2I, a serverless-native system that decomposes a T2I workflow into loosely coupled model functions that can be independently managed and scheduled. By explicitly managing individual model execution, ServerlessT2I enables per-model scaling, declarative workflow composition, transparent GPU-resident communication, and fairness-aware scheduling. To make this decomposition efficient, ServerlessT2I harvests slack GPU memory left idle by compute-bound T2I inference to build a data plane that reduces model loading and data communication overheads. \sys{} further introduces a fair scheduler for multi-tenant serving. Using production traces, ServerlessT2I sustains up to 2$\times$ higher request rates than existing T2I workflow serving systems with the same GPU budget; for a fixed request rate, it saves up to 3$\times$ GPU resources while satisfying service level objectives (SLOs).

## 1. 论文的核心问题与整体含义（研究动机和背景）

**研究背景：**
- 文本到图像（Text-to-Image，T2I）工作流已成为现代图像生成的核心技术，支撑着数百万用户、每秒超过 1 万次请求的商业服务。
- T2I 工作流日益向无服务器（Serverless）平台迁移，原因有二：一是用户高度定制化——生产环境中 20 天内有 31,133 个不同工作流；二是需求往往是临时性且突发的（bursty）。

**核心问题：**
当前云平台将每个 T2I 工作流部署为一个整体的、不透明的 GPU 函数（monolithic GPU function），这带来三个严重问题：
- **高扩展开销（L1）**：将整个工作流而非单个模型作为扩展单元，即使只有单个组件是瓶颈，也必须复制整个工作流，导致启动延迟和显存占用巨大。例如，Flux1-Schnell 工作流在 H800 上扩展耗时 1.1 秒，比模型推理本身慢 110%。
- **暴露通信复杂性（L2）**：多 GPU 并行化所需的 GPU 放置、同步和数据移动等底层细节暴露给用户，违背无服务器计算隐藏基础设施的原则。
- **多租户公平性受限（L3）**：GPU 稀缺导致高峰时段请求积压，"请求数"配额与实际 GPU 消耗不匹配。不同工作流推理延迟相差可达 16 倍，成本高昂的工作流会不成比例地消耗 GPU 时间。

**核心洞察：**
T2I 推理是典型计算密集型（compute-bound），在 GPU 上留下大量空闲显存：生产环境中 diffusion 模型的 P95 显存用量仅 35 GiB，约占现代 H20 GPU 的 36%。这部分"闲置显存"可以被有效转化为系统后端数据平面，用于缓存模型权重和中间张量通信。

**整体含义：**
ServerlessT2I 将无服务器计算的承诺（弹性扩展、隐藏底层细节、按需计费）与 T2I 工作流服务的高效性结合起来，为多租户环境下数千个异构自定义工作流的动态服务提供了首个系统化解决方案。

## 2. 论文提出的方法论：核心思想、关键技术细节

### 2.1 核心思想：工作流 DAG 分解

ServerlessT2I 将 T2I 工作流从"单体 GPU 函数"重构为**模型 DAG（有向无环图）**，其中每个模型是独立的"模型函数"（ModelFn），模型间的数据依赖构成 DAG 边。这实现了：
- 按模型（per-model）独立扩展，而非按整个工作流扩展
- 工作流结构的显式声明，便于并行化和资源管理
- 细粒度的资源计费和公平调度

### 2.2 编程接口（第4节）

设计目标：让用户专注于应用逻辑，隐藏底层基础设施。用户实现三个方法：
- `setup_io()`：声明模型输入输出接口（`add_input`/`add_output`），由此推断 DAG 数据依赖
- `load_model()`：封装模型加载逻辑
- `execute()`：封装模型推理逻辑

工作流通过声明式编排函数（类似 Azure Durable Functions）组装，系统自动推断数据依赖并执行拓扑排序。模型函数是无状态的，支持安全重试。

### 2.3 GPU 驻留数据平面（第5节）

**模型加载优化——缓存前几层：**
- 关键观察：diffusion 模型加载比单次推理慢得多（Flux1-Dev 各组件加载比推理慢 3.2×~13.5×），全量加载无法被推理隐藏。
- 方法：将模型按层拆分，预缓存前 L′_e 层到 GPU，其余层留在主机内存，异步加载。
- 隐藏加载延迟的最优前缀长度公式：

  **T_e2e(L_e) = max( L·T_comp, (L - L_e)·T_load + T_comp )**
  
  **L′_e = ⌈ (L·T_load - T_comp + T_comp) / T_load ⌉**

  其中 T_load 为单层加载延迟，T_comp 为单层推理延迟。只需两个剖析量即可计算。

**通信优化——NVSHMEM + 回调式数据获取：**
- 使用 NVSHMEM 提供单边 GPU 通信（NVLink/RDMA），避免 PCIe 往返和 socket 开销（传统方式下 SD3 某模型通信延迟是执行延迟的 28 倍）。
- 回调式（callback-based）数据获取：下游模型执行到需要数据的程序点时，才触发一次单边 NVSHMEM 拉取，实现计算与通信重叠（如 ControlNet 并行化场景）。

**统一 GPU 内存管理——模型权重虚拟化：**
- 将 GPU 内存划分为 PyTorch 区域和 NVSHMEM 区域，通过"权重虚拟化"层解耦模型的逻辑层与物理内存位置（类似操作系统虚拟内存）。
- 权重可透明地存放在任一区域，通过 Layer Lookup Table 映射和 torch::from_blob 指针重绑定实现。
- 权重被视为可驱逐的弹性状态，按 LRU + 层粒度驱逐（保持第一层以保留加载重叠能力）。

### 2.4 公平调度（第6节）

**vTime 计费单位：**
- 每次 ModelFn 执行按 GPU 墙钟时间计费（含计算、模型加载、张量传输），归入所属租户的累计 vTime。
- 调度时先用历史估计值预先扣费，执行后校正。

**两层调度器：**
1. **第一层（公平性过滤）**：只允许累计 vTime 与最低服务租户之差在操作者可配置的松弛量 Δ 内的租户进入候选集。
2. **第二层（优先级评分）**：对候选集中的就绪函数按 score(n) = ŵ(n) − r̂(n) − ê(n) 排序（等待时间 − 剩余关键路径时间 − 执行延迟），兼顾公平、延迟和效率。

**公平性保证：**
- 定义"符合资格积压"（eligible-backlogged）：在区间内每个时刻至少有一个就绪 ModelFn。
- 理论保证：任意两个 eligible-backlogged 租户在 [t₁,t₂) 内获得的服务量之差 ≤ 2(Δ + L_max)，其中 L_max 为单次调度的最大 vTime 开销。

## 6. 论文的主要结论与发现

1. **性能显著提升**：相同 GPU 预算下，ServerlessT2I 可维持高达 2 倍的请求率；固定请求率下可节省高达 3 倍 GPU 资源，同时保持 90% 以上的 SLO 达成率。
2. **小规模满足 SLO**：S1 中仅需 8 块 GPU 即可达成 90% SLO 目标，而最强的 vLLM-Omni 基线需要 24 块 GPU。
3. **高突发容忍度**：在 S2 中，请求突发性（CoV）可提升至 5 倍仍保持 90% 以上的 SLO 达成率，而基线在 2.5 倍时已跌破 90%。
4. **GPU 内存利用率大幅提升**：S1 中 ServerlessT2I 达到 88% 的 GPU 内存利用率（NoCache 仅 13%），主要通过细粒度（层级）缓存减少内部碎片实现。
5. **数据平面有效性**：缓存前 L′_e 层可将加载延迟降低 90%，整体延迟降低 21%；通信设计使并行化速度接近理论最优。
6. **公平性与效率可权衡**：通过可配置松弛量 Δ，调度器可在公平性（服务差异 ≤ 2(Δ+L_max)）和效率（SLO 达成率 62%→84%）之间灵活调节。

## 7. 优点

1. **问题把握准确**：准确识别了 T2I 工作流在无服务器场景下的核心痛点，且基于真实生产观测（31,133 个工作流、突发性对比、GPU 显存闲置现象），问题驱动性强。
2. **系统设计完整**：从编程接口 → DAG 调度 → 数据平面 → 公平调度，形成完整的系统闭环，"用 DAG 分解换取细粒度控制 + 用显存收割补偿分解开销"的设计思路清晰且自洽。
3. **洞察深刻**：发现"T2I 计算密集、GPU 显存大量闲置"这一特性并系统性利用，是有价值且可推广的洞见。
4. **通信设计巧妙**：结合 NVSHMEM 与回调式数据获取，用单个抽象同时解决了通信效率和并行化灵活性两个问题。
5. **公平性定义合理**：使用 GPU 时间（vTime）而非请求数或操作数，更准确地反映了多租户场景中"服务公平"的本质；理论公平边界推导严谨（Δ + L_max 界限）。
6. **公平基线设计**：为基线引入 NoCache/WCache/MCache 三种变体进行消融，可以分离"显存缓存"与"模型级分解"各自的贡献。

## 8. 不足与局限

1. **应用范围有限**：论文明确承认不适用于视频生成模型——视频模型加载/计算比例不同（加载可被计算隐藏）、且通常通过标准 API 而非用户自定义工作流提供服务。
2. **依赖特定硬件特性**：数据平面依赖 NVSHMEM 和 NVLink/RDMA 等高速互联，在无 NVLink 的异构 GPU 集群或跨节点场景下效果未经验证。
3. **实验覆盖不够全面**：公平调度实验仅涉及 2 个租户的简单场景；对更多租户、更多样化工作流混合、租户动态进出等复杂场景缺乏验证。
4. **仿真实验可信度有限**：256 GPU 大规模验证基于仿真而非真实系统部署，未能验证控制平面在高并发下的真实表现。
5. **统计严谨性可提升**：未报告多次运行的方差/置信区间，难以判断结果的统计显著性。
6. **未讨论模型更新版本问题**：用户频繁更新模型版本时，缓存失效策略和主机内存缓存（仅缓存前 15 个流行工作流覆盖 99% 请求）的效用如何变化，未做讨论。
7. **安全与隔离问题**：多租户共享 GPU/主机内存缓存，张量数据在所有中间状态可读的架构下是否存在信息泄露风险，未被探讨。
8. **生产落地障碍**：NVSHMEM 区域大小需初始化时固定，在动态扩展和集群规模变化场景中，该约束的回退策略并未完整讨论。
