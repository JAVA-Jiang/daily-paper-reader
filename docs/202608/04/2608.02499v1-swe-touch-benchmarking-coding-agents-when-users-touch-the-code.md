## 摘要
现实世界的软件开发要求编码智能体在共享工作空间中操作，用户可能会在任务进行中检查和修改代码，然而现有的仓库级基准通常评估智能体单独工作或将用户参与限制为消息。这引出了一个问题：编码智能体如何理解并响应共享工作空间中的代码变更？我们引入了SWE-Touch，一个通过经过验证的反向编辑（Counter-Edits）来压力测试这一场景的框架：这些编辑是对任务相关代码的合理修改，但与任务完成相冲突。SWE-Touch从多个修复轨迹中挖掘任务关键区域，使用单独的用户补丁生成器来构建编辑，并在智能体到达相关代码时注入带有上下文信息的用户消息。我们在SWE-bench Verified上评估了九个编码模型，并在SWE-Bench Pro和DeepSWE的长时程任务上进行了额外实验。在SWE-bench Verified上，反向编辑将平均解决率降低了7.7个百分点，且在两个长时程基准上退化现象依然存在。轨迹分析将这些失败归因于对演化工作空间有限的感知：智能体可能保留冲突代码，或在未充分重新检查仓库并用针对性测试验证修改后代码的情况下替换它。这些发现表明，强大的自主性能尚不能确保共享工作空间协作所需的态势感知和自适应行为，并为未来的优化指出了关键能力方向：检测工作空间变化、调和冲突编辑与任务的关系，以及验证受影响的行为。

## Abstract
Real-world software development requires coding agents to operate in shared workspaces where users may inspect and modify code during an ongoing task, yet existing repository-level benchmarks typically evaluate agents working alone or restrict user participation to messages. This leads us to ask: how do coding agents understand and respond to code changes in a shared workspace? We introduce SWE-Touch, a framework that stress-tests this setting through validated Counter-Edits: plausible edits to task-relevant code that conflict with task completion. SWE-Touch mines task-critical regions from multiple repair trajectories, uses a separate User Patch Generator to construct the edits, and injects them with contextual user messages when agents reach the relevant code. We evaluate nine coding models on SWE-bench Verified, with additional experiments on longer-horizon tasks from SWE-Bench Pro and DeepSWE. Counter-Edit lowers average resolve rate by 7.7 percentage points on SWE-bench Verified, with degradation also persisting on both longer-horizon benchmarks. Trajectory analysis links these failures to limited awareness of the evolving workspace: agents may retain conflicting code or replace it without sufficiently re-inspecting the repository and validating the revised code with targeted tests. These findings show that strong autonomous performance does not yet ensure the state awareness and adaptive behavior needed for shared-workspace collaboration, and point to detecting workspace changes, reconciling conflicting edits with the task, and verifying the affected behavior as key capabilities for future optimization.

## 2. 论文提出的方法论

论文提出 **SWE-Touch** 框架，流程分为三步：

### (1) 挖掘任务关键区域（Task-Critical Region Mining）
- 用三个不同模型家族的智能体（GPT 5.5、GLM 5.1、MiniMax M2.7）在每项任务上生成完整修复轨迹。
- 用 GPT-5.5、GLM-5.1、MiniMax M2.7 三类轨迹提取读（Read）和编辑（Edit）两种证据，代码区域表示为 `r = (p, s, e)`（路径 + 起止行号），对轨迹间的证据覆盖取交集，得到读核心 `CRead` 与编辑核心 `CEdit`。
- 按确定性优先级选取关键区域：编辑证据优先于读取证据，实现文件优先于测试/元数据，每任务最多保留 8 个区域。

### (2) 构建用户编辑（User Edit Construction）
- 使用独立的 **User Patch Generator**（基于 GPT 5.5 的智能体），输入 issue、代码库、关键区域、参考补丁和测试命令，生成一个语法合法、局部合理但**与任务完成相冲突**的 Counter-Edit（平均 7.0 个变更行/1.04 个文件）。
- **三重验证条件**（核心公式）：

  ```
  VFi(R−) = 0      // 用户编辑单独不能解决任务
  VFi(R⋆) = 1      // 参考补丁可以解决任务
  VFi(R−⋆) = 0     // 用户编辑 + 参考补丁组合后仍失败
  ```

  这保证了编辑既不能单独奏效，也不能被参考修复平凡地吸收。

### (3) 共享工作空间评估（Shared Workspace Evaluation）
- 运行时监控智能体动作，当智能体访问到与补丁区域 `Ui` 重叠的代码时触发交付（默认 K=3 次），由 GPT-4o 模拟器生成随上下文变化的自然语言用户消息（语气随干预阶段逐步加强：合作 → 坚定 → 坚持）。
- 补丁通过上下文匹配的 unified diff 应用，若无法唯一应用则仅送达消息，运行仍计入得分（使结果偏保守）。

## 6. 论文的主要结论与发现

- **主结果**：在 SWE-bench Verified 上，Counter-Edit 使平均解决率下降 **7.7 个百分点**（1.3~16.5 点不等），且**显著重排了模型排名**——如 MiniMax M2.7 从第 3 跌至第 8，Qwen 3.7 Max 从第 5 升至第 3，说明共享工作空间鲁棒性是一个独立的评估维度。
- **长时程任务**：退化在 SWE-Bench Pro（平均 −4.9 点）和 DeepSWE（平均 −3.4 点）上持续存在，但受影响模型有所不同；多数模型增加步骤/token 却未能恢复。
- **消融结论**：仅消息影响有限且不稳定（−2.0~+3.0 点）；仅代码编辑导致一致下降（−1.0~−9.5 点）；Co-Edit 对照（非冲突外部编辑）平均仅 −0.1 点——**核心难度在于调和与任务冲突的程序状态**，而非响应说服性措辞或外部修改本身。
- **失败机制**：63.3% 的失败运行**保留了用户的冲突代码**；13.9% 为错误替换、11.6% 为不完整调和、5.5% 为偏离目标。Claude Opus 4.8 表现为"积极反对但修复错误"（37.9% 错误替换），而 MiniMax/DeepSeek 则倾向"顺从保留冲突"（>70%）。
- **行为过程**：修改/撤销用户编辑的频率与性能变化显著相关（Spearman ρ=0.80），但挑战编辑本身不等于成功——28% 反对编辑的轨迹仍以失败告终；测试数量少且不能区分成功与失败轨迹，说明**恢复取决于检查位置、修正正确性和验证充分性**。
- **总体判断**：自主解决率无法可靠预测共享工作空间中的协作表现，开源模型在此场景下退化尤为明显。

## 7. 优点

- **填补真实空白**：首次将"用户直接修改共享代码库"作为交互渠道纳入编码智能体评测，并以真实用户数据（SWE-chat 59% 比例）佐证其现实性。
- **受控、可复现**：Counter-Edit 经三重验证（单独不解决、参考补丁可解决、组合仍失败），保证编辑"不琐碎可忽略"也不"单独泄漏答案"；补丁采用上下文匹配应用，避免行号漂移。
- **消融设计严谨**：将代码编辑与消息分离、引入 Co-Edit 对照，排除了"任何外部干扰都导致失败"的替代解释。
- **细粒度失败分析**：526 条轨迹的双标注审计 + 明确证据引用规则，将失败归因到保留冲突/错误替换/不完整调和/验证崩溃等具体机制，且按模型分别画像。
- **覆盖面广**：9 个模型、3 个基准、多运行次数，叠加长时程任务与成本-性能分析，结论具有较强普适性。

## 8. 不足与局限

- **受控干预不等于真实协作分布**：论文明确承认，Counter-Edit 是受控、模拟的任务冲突编辑，而非真实用户行为的完整分布；未覆盖互补编辑、部分正确修复、需求变更等更丰富的用户贡献形式。
- **触发机制的人为性**：主实验的区域触发和长时程实验的固定分数注入均是为可控比较设计的，与真实用户"观察-决定-干预"的自适应动态行为仍有差距。
- **数据缺口**：4% 的任务退化为纯文本反馈，6.4% 的运行补丁未实际落地；42/192 个编辑破坏了参考补丁的可应用性，可能引入额外噪声。
- **无人类参与者**：所有用户消息和编辑均为合成生成，缺少真实开发者行为模式的验证。
- **资源披露不足**：未报告 GPU 算力、训练时长等资源信息，且长时程实验多处采用与主实验不同的调度规则，跨设置比较需谨慎。
- **未来方向未实现**：论文提出的自适应用户模拟器、协作感知训练目标、"既不全盘接受也不自动回退"的校准行为等，均留待后续工作。
