## 摘要
大多数技术性HCI研究项目的软件人工制品无法获取。缺乏访问途径限制了对学术知识的生产。难以扩展或重用研究人工制品；在评估后续工作时使用强基线；以及进行复制或可重现性研究。在这项工作中，我们展示了新型智能体AI技术在重焕交互软件方面的潜力：直接从研究论文中重新实现系统。为了衡量该方法的成功，我们描述了一个可重焕性度量标准。通过重新实现UIST近期研究论文，并访谈其原始作者，我们证明了重焕系统的可行性（和局限性）。结果是令人鼓舞的。在许多情况下，生成的代码适用于强基线使用。我们认为这可能代表了我们如何在技术HCI社区中生产、使用和评估研究人工制品的根本性转变。

## Abstract
Software artifacts for most technical HCI research projects are unavailable. The lack of access to these imposes limits on academic knowledge production. It is difficult to: extend or reuse research artifacts; use strong baselines in evaluating follow-up work; and perform replication or reproducibility research. In this work, we demonstrate the potential of new agentic AI technologies to revibe interactive software: reimplement systems directly from research papers. To measure the success of the approach, we describe a revibeability metric. By revibing recent research papers from UIST, and interviewing their original authors, we demonstrate the plausibility (and limitations) of revibed system. The results are encouraging. In many cases producing code suitable for strong baseline use. We argue that this may represent a fundamental shift in how we produce, use, and evaluate research artifacts in the technical HCI community.

## 论文核心问题与整体含义（研究动机和背景）

- **核心问题**：技术型 HCI 研究论文中描述的软件工件（软件原型/系统）大多不可获得（仅有约 2–3.5% 的 CHI 论文作者开源其代码），这严重限制了学术知识生产：
  - 无法扩展或重用已有研究工件；
  - 无法用强基线（strong baseline）评估后续工作；
  - 无法开展复现（replication）或可重复性（reproducibility）研究。
- **根本含义**：工件的缺失使知识生产偏向“孤立新颖性”——研究者倾向于开辟全新方向而非与已有系统对比，也难以承接、改进前人的技术贡献。论文认为，新的智能体 AI 编程工具可能从根本上改变这一局面。

## 方法论：核心思想、关键技术细节、公式与流程

- **核心概念**：
  - **Revibe（动词/名词）**：仅基于论文文本与图像，由 AI 智能体自动重新实现（reimplement）软件工件，开发者不直接触碰代码（即 vibe-coding 范式）。
  - **Revibeability（可重焕性指标）**：通过系统特定的测试 rubric（评估清单）对重实现质量进行量化评分。
- **关键技术流程**（论文 Fig. 2 展示的四步流程）：
  1. **文本与图像提取**：用 PyMuPDF 将 PDF/HTML 转成按章节拆分的 markdown 文件 + 图片，便于智能体聚焦实现细节部分。
  2. **Rubric 自动生成**：通过专门构造的 prompt，让 LLM（作者选用 Claude Code，Sonnet 4.6，因其生成的 rubric 最详细——平均 35.1 个测试/系统，超过 Gemini 的 10.25 个）自动生成测试清单。每个测试包含：ID、前置条件、操作步骤、预期结果、三级成功标准（Full Success / Partial Success / Failure），以及空白“观察结果”栏。
  3. **Unaided Revibe（无辅助重实现）**：将论文拆分文本 + 图片和通用 prompt 交给三种智能体工具（Cursor、Claude Code、Gemini），生成初始实现；对运行报错通过简单的 debug prompt 反馈修复直到应用可启动；随后用“Compare the implemented features…”prompt 补足遗漏功能，得到 Version 1。
  4. **Aided Revibe（有辅助重实现）**：将人评测后的 rubric（含失败项）反馈给智能体，使其修复失败功能，产生新版本；循环可重复（本文最多两轮）。
- **关键公式——Revibeability 聚合指标**：
  \[
  revibeability = \frac{w_s \cdot |t_{success}| + w_p \cdot |t_{partial}| + w_f \cdot |t_{failure}|}{w_s \cdot |t_{all}|}
  \]
  其中 \(w_s = 2\)（全成功）、\(w_p = 1\)（部分成功）、\(w_f = 0\)（失败）。

## 实验设计：数据集/场景、Benchmark、对比方法

- **系统选择**：从 Semantic Scholar 按引用量筛选 UIST 2020–2024 的软件类论文，排除有公开实现或需特殊硬件（VR/ fabrication）的系统，共选出 20 个系统用于 rubric 对比实验；其中 10 个用于完整 revibe 实验（B2、CoLadder、GenAssist、mage、Rescribe、Sketch-n-Sketch、Spellburst、EvalGen、Vizability、XCreation）。因为许多 UIST 论文涉及 LLM 组件，作者特意多选了几篇非 LLM 中心的系统以平衡样本。
- **Benchmark 性质**：本文不依赖原有代码或自动测试，而是构建**基于论文描述**的系统专属交互测试 rubric（revibeability rubric），作为评测基准。
- **对比方法与工具**：使用三个主流智能体编程环境：
  - **Gemini**（gemini-3.1-pro / gemini-3-flash）
  - **Claude Code**（claude-sonnet-4-6）
  - **Cursor**（gpt-5.4-xhigh）
  - 共 27 次完整的重实现（10 个系统 × Gemini + Claude，7 个系统额外用 Cursor；另有两个系统测试了 Cursor+claude-sonnet-4-6 组合）。
- **评测流程**：每个系统经历一轮 unaided revibe + 两轮 aided revibe（每次均以 rubric 评测，共获得 rubric 1、2、3 三组评分）；另对 Spellburst、B2、mage 三篇论文原作者进行了 30–40 分钟的访谈。

## 资源与算力

- 论文**未明确报告 GPU 型号、数量或训练时长**（因为不涉及模型训练）。
- 相关运行成本信息：大多数自动 revibe 循环在 **30 分钟以内**完成；首轮 revibe 费用普遍低于 $15，后续修订轮次（在已有代码上修改）成本更低；主要人力开销在 rubric 评测上（首轮每个测试 1–2 分钟，后续更快）。
- 反面教训：对于需要 GPU 的系统（如 PromptPaint，依赖 Stable Diffusion），在无 GPU 环境下 agent 尝试改用外部 API 引发一系列级联错误，最终未能完成 revibe——表明环境对齐（GPU 等硬件资源）是 revibeability 的隐性前提。

## 实验数量与充分性

- **实验规模**：
  - 10 个系统 × 2–3 个 agent 环境 = 27 次重实现；
  - 20 个系统用于 rubric 生成质量对比（Claude Code vs Gemini）；
  - 两轮 aided revibe 后的最终评估；
  - 3 组原作者访谈（共 5 位作者）。
- **充分性评价**：
  - **整体合理但偏探索性**：作者明确表示选择了“广度优先”而非“深度优先”（未等到评分饱和就停止）；每种环境只做一次构建，未对同一环境+同模型的随机性做多次重复验证；评测者只有一组（团队内部），虽在开始前讨论过评分标准，但未做严格的评分者间信度（inter-rater reliability）校准。
  - **潜在的公平性问题**：rubric 选用了 Claude Code 生成，可能对 Claude 自身实现有隐式偏向。作者通过（a）rubric 生成与代码构建 prompt 差异大、（b）Cursor（非 Claude 环境）在 Claude 生成的 rubric 上表现也较好等理由进行了辩护，但仍是一个潜在混淆因素。

## 主要结论与发现

- **可行性得到验证**：绝大多数系统可被重实现到较高完成度。最佳运行（best-run）revibeability 均值 **0.939**（min=0.8，max=1，σ=0.069）；Vizability 和 XCreation 达到满分 1.0。
- **Aided revibe 有效**：在几乎全部案例中，revibeability 随反馈轮次单调提升（少数轻微下降均 < 0.02），且只用 N=2 轮反馈即达到上述水平。
- **不同工具的差异**：Cursor 平均最高（0.912）；Claude 其次（0.87，但方差更大，min=0.53）；Gemini 最低（0.67，min=0.33）。工具内部系统提示词对结果有显著影响（agent × model 交叉实验）。
- **Rubric 长度与得分负相关**：rubric 测试越多，分数越低（Pearson r=-0.74，p<0.05），反映测试覆盖广度与失败暴露点的权衡。
- **定性发现**：
  - **接近实现但有偏差**：如 Spellburst 原用 GPT-3.5，revibe 时改用 Claude API；一些针对早期模型失败设计的错误处理功能在新的更强大的模型下消失（未必是坏事但偏离原文）。
  - **功能缺失**：如 mage 的拖拽功能在所有环境中均未完整实现，B2 的响应式单元格在自研 web 版本中实现得不够健壮。
  - **过度实现**：agent 常自行添加论文中未描述的功能（如 mage 中所有“未来工作”的小组件都被实现了），或将桌面/notebook 原生系统改造成 web app，偏离原设计目标环境。
  - **作者访谈反馈**：作者们总体上认可 revibe 的交互范式还原度，但也指出其对“熟悉环境”（如 Jupyter）的替代影响了系统价值；作者自身有时也记不清论文中的实现细节——这反过来支持了“论文写作时配套 rubric 可提升 revibeability”的论点。

## 优点

- **概念创新性强**：提出“revibe”和“revibeability”两个精准的新概念，为研究工件缺失这一长期痛点提供了新解法路径，可能根本改变 HCI 社区生产、使用和评估技术工件的模式。
- **方法规范性较好**：rubric 生成用统一的自动 prompt 标准化，评测标准细化到“操作步骤+三级成功标准”，且 rubric 本身可反馈给 agent 形成闭环优化。
- **实验设计多元化**：横跨 3 个 agent 环境、10 个系统、2 轮辅助反馈，并结合作者访谈的定性验证，兼顾了广度与深度。
- **现实反思有建设性**：对“over-implementation”“设计目标环境偏移”“旧 API 消失”等失败模式的分析深入，为后续研究提供了明确的改进方向。
- **对社区的启示丰富**：讨论了 revibeability 作为论文 badge、benchmark、论文详细度评测工具、教学手段等多项潜在应用。

## 不足与局限

- **样本与外部效度局限**：仅覆盖 UIST 2020–2024 的 10 个系统，且经过筛选（排除硬件、公开实现的系统）；对其他会议（CHI、CSCW 等）、更老/更新的系统、硬件混合系统等缺乏验证。作者估计 UIST 2025 年 65% 的论文“潜在可 revibe”，15% 部分可 revibe，但这是团队内部粗略估计，未做正式评估。
- **随机性与偏差风险**：同环境同模型多次运行的结果稳定性未系统测试；rubric 完全由 Claude 生成，可能对 Claude 实现友好；评测者单一且未做 inter-rater reliability 验证。
- **测试覆盖不全面**：rubric 主要覆盖 UI 交互，对后端算法、非界面核心贡献（如 Rescribe 的动态规划优化、EvalGen 的选择性采样机制）缺少直接测试手段。
- **环境依赖问题**：硬件/软件环境不匹配可导致完全失败（如 PromptPaint 无 GPU 的级联失败）；论文中使用的 API 被退役后无法精确复现原始行为。
- **潜在学术生态风险（作者自己亦承认）**：
  - 重实现与原始系统的差距若系统性地被忽视，可能导致不严谨的 A-B 对比结论；
  - 可能催生“论文必须可 revibe”的评审压力，反而抑制创新性和非软件类贡献；
  - 作者可能因此更不愿意共享原始代码，进一步强化封闭生态；
  - vibecoding 带来的能源/资源消耗问题未评估。
- **prompt 局限**：初始 prompt 偏重 web app（即使允许替代方案），对 Jupyter 插件等非 web 形态的工件引导不佳（对 mage、B2 均造成偏差）；主要依赖英文文本和截图信息，视频、补充材料等未利用。
