## 摘要
编码代理基础设施正在从测试工具工程转向循环工程，因为编码代理被部署用于持续的长期软件开发。现有基准测试通常集中于局部任务或最终状态结果，对持续执行的洞察有限。我们引入了LOOPSBENCH，一个用于编码代理评估中循环工程的长期基准。每个任务是一个依赖DAG，包含可单独测试的开发单元，并具有来源证据的前置条件边。LOOPSBENCH包含来自真实来源的112个任务，涵盖8种编程语言和9个领域。其流感知运行时沿就绪边界发布测试，并将已完成的节点保留为回归义务。我们评估了前沿编码代理与广泛使用的循环实现配对。最强的配置，Opus-4.7与Claude Code和外部延续，解决了25.00%的任务。记录的计划仅恢复了部分来源恢复的前置条件DAG，并且在评估的循环配置文件中回归事件仍然可见。我们在microsoft/Loopsbench开源了基准数据和代码，包括所有任务、5,300多个开发单元和可执行测试。

## Abstract
Coding agent infrastructure is shifting from harness engineering toward loop engineering as coding agents are deployed for sustained long-horizon software development. Existing benchmarks often center on localized tasks or end-state outcomes, offering limited insight into sustained execution. We introduce LOOPSBENCH, a long-horizon benchmark for loop engineering in coding agent evaluation. Each task is a dependency DAG over separately testable development units with source-evidenced prerequisite edges. LOOPSBENCH comprises 112 tasks from authentic sources spanning 8 programming languages and 9 domains. Its flow-aware runtime releases tests along the ready frontier and retains completed nodes as regression obligations. We evaluate frontier coding agents paired with widely used loop implementations. The strongest configuration, Opus-4.7 with Claude Code and outer continuation, resolves 25.00% of tasks. Recorded plans recover only part of the source-recovered prerequisite DAG, and regression events remain visible across the evaluated loop profiles. We open source the benchmark data and code, including all tasks, more than 5,300 development units, and executable tests, at microsoft/Loopsbench.

## 一、论文的核心问题与整体含义

### 研究动机
- 编码智能体（Coding Agent）基础设施正从 **harness engineering（测试工具工程）** 转向 **loop engineering（循环工程）**——即编码智能体越来越多地被部署于持续、长周期的软件开发任务中，需要能在长时间内维持目标、跟踪进展状态并管理累积的回归压力。
- 当前主流编码基准（如 SWE-bench 及其变体、FeatureBench、MLE-Bench 等）存在明显不足：
  - 任务抽象本质上是**终端式（terminal）**的：智能体接收孤立 issue 或扁平规格说明，只以最终任务成败判定结果；
  - 无法回答关键问题：智能体是否保住了中间义务？是否避免了回归？是否按可行顺序完成了相互依赖的子问题？
  - 此类设计仅衡量"issue 解决能力"，无法揭示长期执行中的循环行为。

### 整体含义
- 论文提出 **LOOPSBENCH**，定位为"**第一个面向循环工程评测的基准**"，将编码智能体评测从"只看终点"推进到"可观测执行过程"，使**规划、路由、状态保持、义务保留**等循环层面因素成为可测量的评测维度。

## 二、论文提出的方法论

### 核心思想
- 每个任务被建模为一个**依赖 DAG（有向无环图）**：节点为可独立测试的"开发单元（development unit）"，边为带有来源证据的前置条件关系。
- 任务指令呈现给智能体，DAG 结构用于控制**测试释放**；已完成单元保留为持续的**回归义务**；执行顺序不被强制，但通过**循环追踪（loop trace）**记录并分析。

### 关键技术细节

#### 1. 开发单元定义（五元组）
每个单元记为 $u = (r_u, s_u, p_u, \Delta_u, T_u)$：
- $r_u$：需求描述；
- $s_u$：文件/符号范围；
- $p_u$：前置单元集合；
- $\Delta_u$：参考补丁贡献；
- $T_u$：标准测试集。

#### 2. 前置边证据模式（4 种）
- 顺序 PR 链（沿合并历史）；
- 结构级模块复用（$v$ 编辑了 $u$ 引入的文件/符号）；
- 功能级生产者-消费者 API 边（$v$ 调用/导入了 $u$ 创建的权威定义）；
- 组合式分层（$v$ 扩展了 $u$ 声明的子类、schema 或接口）。
- 另外配有**去噪名单（denylist）**，排除热文件、生成物、lockfile 引发的伪链。

#### 3. 流程感知评估运行时（Flow-aware Runtime）
- **就绪前沿（Ready Frontier）**：在检查点 $t$，前置节点全部通过的节点 $v$ 进入前沿：$R_t = \{ v \in V \setminus C_t : \forall (u,v) \in E, u \in C_t \}$
- **拓扑门控测试释放**：仅当某单元的所有前置节点的测试均通过后，其测试才被释放（用于计分）；后续层的测试保持密封。
- **回归义务保留**：一旦某单元通过闸门，其测试连同所有前置单元测试，在后续所有层中持续强制执行。

#### 4. 测试套件合成三条件（fail-to-pass 检验）
每个单元的测试须同时满足：
- **可解性（solvability）**：完整黄金补丁使所有测试通过；
- **非平凡性（non-triviality）**：空工作区下没有测试通过；
- **判别性（discriminativeness）**：仅应用该单元 DAG 祖先的黄金补丁时，至少留有 1 个测试失败。

#### 5. 双容器快照管线
- 容器 A：承载工作树，是智能体唯一写目标；
- 容器 B：含完整测试套件与参考环境，按固定节奏采样 A、做 diff，将非空 diff 入队并在 B 中运行当前已释放测试层的测试。
- 该设计允许智能体持续编辑的同时，评估端独立采样工作区状态，在**真实变更点**和**最终状态**两处计算循环追踪指标。

#### 6. 任务构建管线（四阶段）
1. **任务收集**：三种真实来源（课程实验、PR 序列、研究演化）；
2. **任务预处理**：归一化为原子候选任务；
3. **任务选择**：两个来源无关阈值——时间跨度 ≥ 2.5 个月、解决方案规模 ≥ 1,200（来源特定尺度）；
4. **单元定义与关系恢复、任务插桩**：生成指令、Dockerfile、测试套件、DAG 描述文件。

## 五、实验数量与充分性

### 实验规模
- **RQ1 三组实验**：族内缩放 12 个模型配置（3 族 × 4 代）、模型扫描 8 个配置、循环扫描 6 个配置，共约 26 组模型-循环组合，全部在完整 112 个任务上运行；

- **RQ3**：4 种循环配置的深度对比；另含 pass@3 鲁棒性检查（12 个配置）；按来源拆分的解析率分析（14 个配置 × 3 来源）。

### 充分性与客观性分析
- **优点**：
  - 三个正交维度（模型、循环实现、来源类型）的系统扫描设计合理，能区分模型效应与循环效应；
  - 循环追踪指标丰富（Edge F1、Layer ρ、CPR、WR、Reg 等），将评测从"是否成功"推进到"如何执行"；
  - 可复现性措施到位：版本固定的环境、测试套件、对抗性检查（solvability / non-triviality / discriminativeness）。
- **不足**：
  - 每个配置在默认设置下仅运行 **1 次试验**（`n_attempts: 1`），除 pass@3 外缺少多次运行的方差估计；
  - PR 序列子集过于困难（仅 3 个配置成功解决 ≥ 1 个任务，9/14 配置为 0），区分度集中在课程实验，使综合得分主要由较简单子集驱动；
  - 研究演化子集仅 26 个任务，按来源拆分的估计置信区间较宽；
  - RQ3 的四种循环配置依赖各自的运行记录，未做严格受控的因果对比（作者也承认这一点）。

## 六、主要结论与发现

1. **长期循环进展严重受限**：最强配置（Opus-4.7 + Claude Code + 外部延续）仅解决 **25.00%** 的任务；无外部延续时，单次执行段通常只能达到较浅的依赖前缀。
2. **规划缺口**：记录的智能体计划仅能恢复"部分"来源证据 DAG；Edge F1 与 Layer ρ 与参考 DAG 均有较大差距，开放源码循环（OpenHands、SWE-agent）明显低于闭源循环实现。
3. **实现盈余**：候选补丁长度一致性地超过黄金补丁（PatchLen 1.58×~2.54×），而 token 重叠度仅中等（Jacc 0.62~0.76），表明状态缺失会表现为"实现膨胀"而非"截然不同的实现"。
4. **测试维护缺口**：长时间运行中智能体自撰测试稀疏（#T 11~28），远低于原生套件；回归率在所有部署级循环实现中达 2.18%~7.11%。
5. **上下文更新方式影响显著**：动态工作流（dynamic workflows）有最高的上下文预算轮次（97.96/run）和最佳 RR（24.11%），但回归事件在所有四种循环配置中仍然可见（0.13~0.36/run）——**路由与状态追踪是核心瓶颈**。
6. **按来源难度分层**：PR 序列最难（≤3.45%）、课程实验最容易（最多 24.56%）、研究演化居中（最多 15.38%）。

## 七、优点

- **开创性视角**：首次将"循环工程"作为独立于"测试工具工程"的评测维度，对准了真实工业界（Codex、Claude Code 等产品已内置 goal mode / dynamic workflows）的部署形态。
- **任务构造的多源与真实**：整合课程、开源仓库 PR、研究演化三种来源，任务均带来源证据，避免纯合成任务的人工性。
- **流程感知评估契约**：DAG 控制测试释放、回归义务持续执行、双容器快照追踪变更点，使中间过程可测、可追溯。
- **丰富的循环追踪指标**：RR / TPR / Depth 分离最终状态与过程深度；Reg 直接量化义务保留；Edge F1、Layer ρ、CPR、WR 等刻画规划保真度。
- **分离模型效应与循环效应**：三维实验设计（族内缩放、固定循环扫模型、固定模型扫循环）可归因性能差距的来源。
- **严格的质量控制**：测试套件经 solvability / non

triviality / discriminativeness 三道屏障检验；任务来源、前置边去噪、时间/规模阈值都有明确标准。
- **负结果同样有价值**：如“实现盈余”“测试维护缺口”等结论，指出了当前智能体长期执行的系统性问题，而非单纯比拼模型排名。

## 八、缺点与局限性

- **成本门槛高**：单任务平均计费 token 达 1.83M~9.10M，112 任务 × 26 组配置的完整评估成本极为高昂，普通研究团队难以复现或扩展。
- **评估单次运行方差缺失**：默认 `n_attempts: 1`，未报告多次运行的均值/方差；对随机性较高的闭环智能体而言，结论稳定性存疑。
- **PR 序列子集难度失衡**：14 个配置中有 9 个在 PR 序列上为 0 分，导致该来源几乎没有区分度，综合指标可能被课程实验主导。
- **DAG 恢复依赖来源证据质量**：前置边来自 PR 合并历史、模块复用、API 调用等模式，噪声过滤虽有 denylist，但难以完全避免隐式依赖漏检。
- **循环追踪指标的参考系单一**：指标以“黄金 DAG / 黄金补丁”为参照，而真实开发中实现方式多样化，合法替代实现可能被误判为“实现盈余”或“规划缺口”。
- **RQ3 因果归因不严格**：四种循环配置在模型、工具版本、上下文策略上均不相同，无法区分“循环设计因素”与“配置混杂因素”的独立贡献。
- **测试释放逻辑与实际可用性脱节**：拓扑门控测试释放是评估端约束，智能体在真实环境中可能依赖自撰测试或外部验证，评估框架未建模这种“测试环境不透明”的现实。
- **外部延续机制模糊**：论文提及“外部延续”（external continuation）可提升完成率至 25%，但未详细说明延续的触发条件、人工介入程度及自动化边界，削弱了可复现性。

## 九、对未来研究的启示

1. **循环工程评测应成为标准维度**：建议后续基准在保留终端指标的同时，强制报告循环追踪指标（RR、TPR、Depth、Reg 等），推动智能体从“一次性解题”转向“可持续交付”。
2. **需要低成本、可扩展的循环评测代用方案**：当前 token 成本过高，可探索任务子采样、分层抽样、提前终止准则等降本策略，使更多研究者能参与循环工程研究。
3. **构建更细粒度的状态追踪协议**：将智能体的计划、文件编辑、测试调用、错误恢复等信号标准化为统一日志格式，便于跨循环实现做公平归因。
4. **回归义务应成为核心优化目标**：论文中回归率在 2.18%~7.11% 之间，未来可设计专门的“回归惩罚”训练目标或循环内回归检测机制。
5. **动态工作流值得深入挖掘**：动态工作流（dynamic workflows）在上下文预算与 RR 上表现最佳，说明“按需扩展上下文”比“固定长上下文”更符合长周期任务需求。
6. **来源混合的基准需要分层报告**：不同来源任务的难度与结构差异极大，建议未来基准按来源分别给出 leaderboard，而非仅提供混合排名。
7. **探索多试验聚合策略**：单次运行受随机性影响大，pass@k 或多轮投票等聚合策略在循环场景下的适用性值得专门研究。
8. **循环工程的失败模式分析**：论文揭示了规划缺口、实现膨胀、测试稀疏三类典型失败，未来工作可针对每种失败模式设计针对性干预（如规划校验器、补丁精简约束、测试生成奖励）。

## 十、总评

LOOPSBENCH 是编码智能体评测从“终端式正确性”迈向“过程式循环能力”的一次重要奠基。它以依赖 DAG 为骨架、以拓扑门控测试释放和回归义务保留为核心机制，构建了第一个可量化循环行为的评测框架。尽管在成本、可复现性和因果归因上仍有明显短板，但其提出的循环追踪指标、多来源任务构造流程和“流程感知评估运行时”均具有很高的方法论参考价值。论文最核心的贡献不在于给出某个模型的排名，而在于**将“长期执行中的状态保持与义务履行”确立为编码智能体评测的一个基本维度**，并为后续研究提供了可操作的评测基座。
