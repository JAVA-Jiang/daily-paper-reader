## 摘要
自然语言代码检索是计算机科学中一项快速发展的任务。然而，1C:Enterprise生态系统将俄语语法与高度领域特定的术语相结合，此前几乎不存在开放数据集和专门模型。我们提出了一个完整的1C代码检索流程：一个包含3,413个真实世界、已去除个人身份信息(PII)的查询-代码对的开放基准，一个可复现的评估框架，以及一个专门的雙编码器。为了克服标记数据稀缺的问题，我们使用来自公共代码仓库的784,057个由google/gemma-4-26B-A4B-it生成的合成三元组进行微调，采用了Matryoshka表示学习(MRL)和隐私感知分词器。由于基准子集大小不同，我们报告了平衡子集宏平均、查询加权微平均以及仅论坛子集的结果。我们的模型在平衡宏nDCG@10上达到0.5992，微平均为0.5044，论坛数据上为0.4617，而基线架构的宏平均为0.4932，google/embeddinggemma-300m为0.5404。在移除所有被保守的精确/13-gram重叠审计标记的基准示例后，平衡宏平均为0.6011（微平均0.5010），这表明检测到的训练-基准重叠并不能解释主要结果。将MRL截断至256维可保留99.9%的检索质量，同时将稠密索引存储和精确相似度计算量减少为原来的三分之一。

## Abstract
Natural language code retrieval is a rapidly evolving task in computer science. However, the 1C:Enterprise ecosystem combines Russian syntax with highly domain-specific terminology, for which open datasets and specialized models have been virtually non-existent. We present a comprehensive pipeline for 1C code retrieval: an open benchmark of 3,413 real-world, PII-scrubbed query-code pairs, a reproducible evaluation harness, and a specialized bi-encoder. To overcome scarce labeled data, we fine-tune on 784,057 synthetic triplets generated by google/gemma-4-26B-A4B-it from public code repositories, using Matryoshka Representation Learning (MRL) and a privacy-aware tokenizer. Because the benchmark subsets differ in size, we report balanced-subset macro, query-weighted micro, and forum-only results. Our model reaches 0.5992 balanced macro nDCG@10, 0.5044 micro, and 0.4617 on forum, versus 0.4932 macro for the baseline architecture and 0.5404 for google/embeddinggemma-300m. Removing every benchmark example flagged by the conservative exact/13-gram overlap audit leaves 0.6011 balanced macro (0.5010 micro), indicating that detected train-benchmark overlap does not explain the headline result. MRL truncation to 256 dimensions preserves 99.9% of retrieval quality while reducing dense-index storage and exact similarity arithmetic by a factor of three.

## 2. 论文提出的方法论：核心思想、关键技术细节、公式或算法流程

**核心思想**：采用单阶段稠密闭集检索范式，通过双编码器（bi-encoder）将查询和文档分别嵌入到同一向量空间，以余弦相似度进行排序；为克服标注数据稀缺，利用 LLM 在公共代码上合成大规模三元组进行领域微调，并引入 MRL 支持维度压缩。

**关键技术细节**：

- **双编码器架构**：查询和文档独立编码，形式化为
  - `e_q = Enc(q; search_query)`
  - `e_d = Enc(d; search_document)`
  - `score(q, d) = cos(e_q, e_d)`（L2 归一化后等价于内积）
- **领域适应微调**：以 `deepvk/USER2-base`（149M 参数，基于 RuModernBERT，支持 8,192 token 上下文）为基座，沿用其 sentence-transformers 训练管线，采用 **Cached Multiple Negatives Ranking Loss（CachedMNRL）+ InfoNCE 损失**，并结合 **Matryoshka Representation Learning（MRL）** 在多个前缀维度 {768, 512, 384, 256, 128, 64, 32} 上同时优化。

## 8. 不足与局限

- **单金标评估失真风险**：每个查询仅标注一个金标文档，当存在多个等价或相近的相关片段时（人工抽查 50 条中 5 条发现此类情况），模型可能因正确排名的候选未被标注而被低估。
- **合成数据未经人工验证**：300 条样本的 LLM-as-a-judge 分数（相关性均值 4.33、自然度 4.17）只是近似信号，未报告与人工标注的一致性，且专门领域（俄语→BSL）的生成质量缺乏专家背书。
- **隐私清理非严格保证**：基于规则的 PII 清理仅覆盖常见表面形式，未报告精确率/召回率，也未进行残留 PII 的人工审计。
- **实验覆盖缺口**：没有重排序器实验、多随机种子方差、目标消融（如硬负例 vs. 随机负例、分词器补丁的独立贡献）、ANN 索引评估和端到端延迟测量。
- **混合检索探索不足**：朴素 RRF 融合失败后未尝试其他混合策略（如学习型融合、更精细的分词），结论可能被特定配置限制。
- **污染审计局限**：n-gram 只能捕捉表层重复，无法识别语义改写级别的数据泄露。
- **领域泛化风险**：训练数据来自 GitHub 公共代码，基准来自论坛和 FastCode，两者分布存在差距；模型是否适用于私有 1C 系统或更广泛的生产环境尚未验证。
