## 摘要
AI编程智能体需要的不仅是相关代码片段，还需要业务语义、验证证据、关系以及确保其上下文为最新的保证。现有系统通常通过检索、摘要、图谱、规则或逆向规格来推断或外化这些知识。我们研究一种互补的表示方式，其中选定的代码单元直接携带可供智能体使用的知识。我们提出可执行代码知识（Executable Code Knowledge, ECK），并将可执行代码知识单元（Executable Code Knowledge Unit, ECKU）定义为一种绑定源代码的对象，它结合了稳定身份、语义、可执行行为、契约、证据、关系、来源、验证状态和查询接口。我们的Python原型支持代码本地创作、清单导出、证据执行、精确变更行影响、新鲜度检查以及面向智能体的投影。在三个真实Python仓库和26个受控补丁任务中，直接ECK为11/11个带证据的任务提供了可执行测试覆盖，并为9/11个任务提供了精确选择器；隐藏已声明的证据会将精确恢复率降至1/11（配对精确McNemar检验p=0.0078）。从ECK派生的规则恢复了11/11个精确选择器，表明规则是有效的交付工件，同时ECK提供源代码绑定、验证状态、影响和新鲜度。精确的变更行影响与独立编写的标签在全部26个补丁上匹配（12个单位链接；精确率、召回率和F1均为1.000）。AST限定的指纹正确分类了50个正向变更和17个不相关的同文件对照，而静态规则快照未能检测出50个过期案例中的任何一个。基于模型的补丁审查和跨层研究衡量的是投影保真度，而非独立的发现能力。这些结果支持一种混合架构：检索用于覆盖，ECK用于源代码和证据治理，投影用于交付。

## Abstract
AI coding agents need more than relevant snippets: they need business semantics, validation evidence, relations, and assurance that their context is current. Existing systems usually infer or externalize this knowledge through retrieval, summaries, graphs, rules, or reverse specifications. We investigate a complementary representation in which selected code units directly carry agent-usable knowledge. We introduce Executable Code Knowledge (ECK) and define an Executable Code Knowledge Unit (ECKU) as a source-bound object combining stable identity, semantics, executable behavior, contracts, evidence, relations, provenance, validation state, and a query interface. Our Python prototype supports code-local authoring, manifest export, evidence execution, exact changed-line impact, freshness checking, and agent-facing projections. Across three real Python repositories and 26 controlled patch tasks, direct ECK provides executable test coverage for 11/11 evidence-bearing tasks and exact selectors for 9/11; hiding declared evidence reduces exact recovery to 1/11 (paired exact McNemar p=0.0078). ECK-derived rules recover 11/11 exact selectors, showing that rules are effective delivery artifacts while ECK supplies source binding, validation state, impact, and freshness. Exact changed-line impact matches independently authored labels on all 26 patches (12 unit links; precision, recall, and F1 all 1.000). AST-bounded fingerprints classify 50 positive changes and 17 unrelated same-file controls correctly, whereas static rules snapshots detect none of the 50 stale cases. Model-backed patch-review and cross-layer studies measure projection fidelity rather than independent impact discovery. These results support a hybrid architecture: retrieval for coverage, ECK for source and evidence governance, and projections for delivery.

## 论文总结：Executable Code Knowledge（ECK）

### 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：AI编码智能体在执行仓库级任务时，不仅需要“看起来相似”的代码片段，还需要知道：
  - 某段代码是否代表业务规则（而非实现细节）；
  - 哪些测试是权威的、应作为验证证据；
  - 与API、数据字段、策略等的关系；
  - 所属上下文是否仍然新鲜（未被修改后过期）。
- **现有方法的缺陷**：当前系统大多采用“从代码提取/外化知识”的管线：
  ```
  普通代码 → 检索/摘要/静态图/反向规格 → 智能体上下文
  ```
  这类方法存在**权威性问题**：检索片段不提供验证证据；静态图不区分领域不变量与非关键调用边；生成式摘要需要追溯、验证并保持新鲜。
- **本文核心主张**：让选定的代码单元**直接**携带智能体可用的知识（语义、契约、证据、关系、新鲜度等），而不是仅把代码当作被挖掘的文本。即代码本身可以是一种原生的、携带验证条件的知识表示。
- **整体含义**：提出一种混合架构的视角——**检索负责覆盖，ECK负责源代码绑定与证据治理，投影/规则负责交付**。ECK不取代检索，而是补充其缺失的“验证证据与新鲜度”维度。

### 2. 方法论：核心思想、关键技术细节

#### 核心概念：可执行代码知识单元（ECKU）

ECKU被形式化定义为：

```
ECKU = <I, S, B, C, E, R, P, V, Q>
```

字段含义：
- **I**：稳定身份标识（如 `pricing.discount.vip_large_order`）；
- **S**：领域语义（业务规则描述、阈值、折扣率等结构化字段）；
- **B**：可执行函数体（原始代码，不被装饰器包装污染）；
- **C**：契约（前置条件、后置条件）；
- **E**：证据（如可执行的pytest命令，包含测试ID、命令、声称的断言）；
- **R**：关系（关联的API、数据实体、测试、策略等）；
- **P**：来源/出处（作者、时间、修订等）；
- **V**：验证状态与新鲜度（哈希指纹比对结果）；
- **Q**：查询与组合接口（`build`、`query`、`validate`、`freshness`、`impact`等）。

#### 新鲜度与验证机制

定义了多个哈希指纹：

- `SourceHash(u)`：源码函数体/AST限定范围的哈希；
- `KnowledgeHash(u)`：身份、语义、关系、相关来源的规范化哈希；
- `ContractHash(u)`：契约字段哈希；
- `EvidenceHash(u)`：证据字段哈希。

**新鲜度判定**：当且仅当所有哈希与最近一次验证时一致时，`Fresh(u)` 为真；且所有可执行证据命令都通过时，`Supported(u)` 为真；两者同时满足则 `Valid(u)` 成立。

#### 系统实现（Python原型）

- **创作层**：使用装饰器（`@knowledge_unit`、`@contract`、`@evidence`）在代码中直接标注；
- **发现与清单层**：自动导入模块，发现ECKU，导出 `knowledge_units.jsonl`、`evidence.jsonl`、`validation_state.json`；
- **验证层**：执行证据命令，记录状态和哈希；
- **新鲜度层**：比较源码、知识、契约、证据四类指纹，报告 `source_changed`、`knowledge_changed`、`contract_changed`、`evidence_changed` 等精确过期原因；使用AST边界（`lineno/end_lineno`）限定函数体，并排除装饰器以避免混淆；
- **Agent上下文层**：生成紧凑的类型化上下文包（包含意图、符号、源码跨度、契约、证据命令、关系），智能体无需自行推断验证命令。

### 3. 实验设计：数据集 / 场景 / 基准 / 对比方法

#### 数据集与基准

- 使用三个真实Python仓库：
  - **python-dotenv**（6个ECKU）
  - **python-slugify**（5个ECKU）
  - **tomli**（6个ECKU）
- 总计17个人工确认的直接ECKU，其中16个携带可执行证据。
- 构建了**26个受控补丁任务**（issue风格变更请求），补丁触摸到11个ECKU，12条单位链接。

#### 对比方法

实验对比了六种上下文提供方式：

1. **Plain**：仅仓库树上下文；
2. **BM25 Chunk**：基于固定大小源码块的词法检索基线；
3. **EKP Retrieval**：从代码提取的知识包（extractive knowledge packets）；
4. **Rules Context**：由ECK派生的Markdown规则/记忆（模拟AGENTS.md或项目规则）；
5. **Direct ECK without Evidence**：直接ECK上下文但隐藏可执行证据命令；
6. **Direct ECK**：直接使用代码创作的ECKU。

此外还有**Rules with IDs**（带标识符的规则）、**ECK Projection**（任务特定的紧凑投影）等条件。

#### 评估场景

- **RQ1 Validation planning**：智能体根据变更请求生成计划（目标文件、符号、验证命令）；
- **RQ2 Patch impact**：给定补丁diff，智能体输出受影响的ECK ID、符号、验证命令、风险标志；
- **RQ3 Cross-layer projection**：跨API/DB/业务规则三层的合成企业服务案例（orders/pricing、subscriptions/entitlements、refunds/risk），共21个ECKU、18个补丁；
- **RQ4 Freshness**：可控扰动实验（源码、知识、契约、证据修改 + 同文件/异文件无关编辑）。

#### 度量指标

- 文件召回率（file recall）；
- 精确选择器召回率（exact selector recall，要求规范化命令完全相等）；
- 可执行覆盖召回率（executable coverage recall，允许文件/类/测试包含关系）；
- ECK ID召回率、API/DB字段/业务规则召回率；
- 严格JSON兼容率与宽松可解析率。

### 6. 主要结论与发现

1. **证据至关重要**：隐藏证据后，精确选择器恢复率从9/11骤降至1/11（p=0.0078）；但文件定位能力不变（0.981），说明证据主要提升**精确验证命令**的选择，而非文件定位。
2. **ECK不是“更好的RAG”**：在文件定位上与BM25持平（0.981），其独特价值在于**携带验证证据、约束和新鲜度状态**。
3. **规则是有效的交付格式**：直接ECK派生的Rules Context也可以达到100%的精确选择器恢复，但规则自身缺乏源代码绑定、影响操作和新鲜度机制；当代码变化后，规则快照无法检测任何过期（0/50），而ECK检测到50/50。
4. **精确变更行影响完全正确**：26个补丁上，与独立人工标签的12个单位链接匹配，精确率/召回率/F1均为1.000（并消除了整块hunk方法导致的边界误差）。
5. **投影格式优于原始格式**：任务特定的ECK Projection在跨层案例中保留了所有字段（ECK ID、业务规则、验证命令均1.000），且提示字符更短（4586 vs Direct ECK 6930），而规则在业务规则召回上明显不足（0.471）。
6. **新鲜度指纹学**：AST限定的源码指纹避免了同文件无关编辑的误报（特异性1.000）；独立的规范化知识指纹检测面向智能体语义和关系的变化。

### 7. 优点

- **问题定义尖锐**：明确区分了“相关检索”与“验证携带上下文”，并指出当前AI编码智能体缺乏权威证据的痛点。
- **形式化框架完整**：ECKU定义了九元组，覆盖身份、语义、契约、证据、关系、来源、验证状态、查询接口，概念清晰、可扩展。
- **双重验证机制**：不仅提供测试证据，还提供基于哈希的陈旧性检测（源码、知识、契约、证据分离），能够给出精确的过期原因。
- **实验设计精细**：采用了配对消融（证据隐藏）、统计检验（McNemar、Bootstrap）、独立人工标注、多基线对比（BM25、EKP、规则、纯文本），并区分“精确选择器”和“可执行覆盖”两种粒度。
- **诚实的态度**：明确指出哪些结果是“投影保真度”而非“独立发现能力”，不夸大泛化能力；讨论偏见和威胁。
- **重视工业实践**：提出“规则/记忆作为交付格式”的兼容性，并提供从提取到ECK的迁移步骤，实际部署路径清晰。

### 8. 不足与局限

- **规模有限**：仅3个小仓库（python-dotenv、python-slugify、tomli），17个ECKU、26个受控补丁，无法证明在大规模、多语言仓库上的通用性。
- **任务构造偏差**：变更请求由已知补丁反向生成，尽管避免直接使用补丁文件名，仍可能造成信息泄漏；报告提到“natural issue reports”是更强评估但未采用。
- **模型覆盖窄**：仅评估Qwen系列两个模型，未测试其他编码模型（GPT、Claude、DeepSeek等）的通用性。
