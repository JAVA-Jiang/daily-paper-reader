Abstract —Quantum Computing (QC) is an emerging tech-nology that requires customized tools, such as software stacks and programming interfaces. However, currently, the tools are generally tightly coupled and exhibit limited interoperability. This, in particular, affects High Performance Computing (HPC) facilities and data centers, which are required to support multiple programming interfaces. In this paper, we introduce MQSS Client, an unifying, context-aware access layer and programming library that decouples the programming interfaces and the underlying compilation and runtime stack. MQSS Client aims to support all existing programming interfaces by providing abstractions for resources, jobs, and results. It provides two access modes to accommodate the varied needs of remote and HPC users. Thus, interoperability between software stacks and programming interfaces increases. 

Index Terms —Quantum Computing, High Performance Com-puting, Programming Interfaces, Decoupling 

I. I NTRODUCTION 

Quantum Computing (QC) is advancing swiftly and promises to revolutionize computation by enabling solutions to problems that would require exponential resources for classical computing systems. Rather than replacing classical infras-tructure, Quantum Processing Units (QPUs) are increasingly envisioned as accelerators—similar to Graphics Processing Units (GPUs) and Field Programmable Gate Arrays (FP-GAs)—within existing High Performance Computing (HPC) environments. While remarkable progress has been made in hardware development, such as Google’s Willow [1] and IQM super-conducting quantum processors [2], these achievements alone are insufficient to unlock the full potential of QC. To achieve the quantum advance truly, the hardware requires compatible and sophisticated programming languages, models, and robust underlying compilation infrastructures. Finally, we conclude the paper in Section VI. II. B ACKGROUND AND RELATED WORK 

Quantum programming models and interfaces are essen-tial to interact with quantum hardware. While programming models define how computation is performed, interfaces are practical tools to enable creating quantum programs. The most well-known quantum programming models are gate-based, pulse-based, and Hamiltonian models. The gate-based model defines quantum circuits as a sequence of quantum gates. Similarly, the pulse-based model uses a sequence of physical signals. On the other hand, the Hamiltonian model describes the computation via the system’s energy function. To describe a quantum program at a higher level, we use programming interfaces, such as Qiskit [4] and CUDA Quantum [5]. Python is the dominant language in the QC domain. For instance, Qiskit [4] is a Python-based, open-source SDK developed by IBM and widely used in developing quantum ap-plications. It provides abstractions to define custom backends and quantum job definitions. Another widely used Python-based SDK is PennyLane [6], developed by Xanadu Quantum Technologies. As an extension to it, Catalyst is a Just-in-Time (JIT) compiler that compiles High-Performance Computing-Quantum Computing (HPCQC) applications as a whole [7]. PennyLane also provides an abstraction to create a custom backend. To enable the JIT, an additional custom backend needs to be created by inheriting the corresponding interface from Catalyst’s Runtime. While Python dominates quantum application development, it is unsuitable for HPC environments where low-latency, compiled code is standard. C and C++ remain the dominant languages in HPC, making native support for them essential for seamless HPCQC integration. Therefore, it is necessary to create programming interfaces in these languages to enable seamless HPCQC integration. For instance, CUDA Quantum [5] is a language extension that allows users to integrate quantum circuits using C++ and Python. It allows the creation of different backends with their abstraction classes. In parallel, Quantum Programming Interface (QPI) is a C-based runtime library solution that allows users to create quantum circuits within HPC applications. In addition, CQ [8] is a C-like API, programming model, and specifications for the hybrid application. In parallel, quantum software stacks, such as Munich Quan-tum Software Stack (MQSS) [9], [10], are required to support multiple programming models and quantum devices. Simi-larly, Rust-based Quantum Resource Management Interface (QRMI) [11] is a vendor-agnostic library for submitting quan-tum jobs and monitoring their behavior by abstracting away the complexity of quantum resources. On the backend side, QRMI provides an abstraction layer that supports multiple quantum devices. In addition, MQSS provides abstraction via Quantum Device Management Interface (QDMI) [12]. Hence, abstraction is a key concept for stripping away the complexity and versatility of the fast-paced development of the quantum ecosystem. III. D ESIGN AND IMPLEMENTATION 

As depicted in Figure 2, the MQSS Client is a unifying, context-aware access layer and programming library that de-couples the programming interfaces and the underlying com-pilation and runtime stack. We implement the MQSS Client 

using C++17 with Niels Lohmann’s JSON [13] to handle the JSON data format, libcurl [14] to establish the remote connection, rabbitmq-c [15] to handle the HPC connection. To create the Python bindings, we utilize pybind11 [16]. Figure 3 shows the full class structure of the MQSS Client .At the top level, MQSSClient is the single entry point for all user interactions. It delegates transport to one of two inter-nal backends — MQSSRestClient or MQSSHPCClient —both implementing the MQSSBaseClient interface. This design localizes transport-specific logic within the backend classes, keeping the public-facing MQSSClient API uni-form regardless of the chosen access mode. Outward from 

MQSSClient , three domain objects carry the core abstrac-tions: JobRequest defines what to run, JobResult cap-tures what came back, and Resource describes where it ran. We provide two access modes to accommodate distinct requirements: a REST-based remote access and a RabbitMQ-based HPC access. The access modes are built on top of the unified layer that encapsulates the job and resource interfaces. Fig. 2. We provide two interfaces within the MQSS Client to fulfill the requirements of end users and libraries built on top of it: the Job and Resource Interfaces. At a high level, a Job 

represents a quantum task while a Resource represents any quantum computation asset that can execute a quantum task, such as quantum computers, simulators, as well as stacks. The Job interface encapsulates the logic related to quantum task definition and execution. The job interface consists of highly customizable Job Request and Job Result classes. A Job Result includes the outcome of the quantum task and execution metrics, such as completion and submission times. Conversely, a Job Request defines the quantum task to be offloaded to the underlying stack. We define two job requests to accommodate the use of different quantum-computation assets: Circuit and Hamilto-nian . A circuit job request describes a gate-based quantum program, including the number of shots and the resources to be used during execution. On the other hand, a Hamiltonian job request describes a quantum task that determines the total energy of a quantum system with given interaction terms and coefficients. The MQSS Client can query the results of a job using the 

getJobResult function, where the first parameter is the job to be queried, followed by a boolean value indicating whether to wait for the results, and an integer value for the timeout. In that case, if the results are not produced or not ready, the returned value is NULL. Otherwise, the function returns a unique pointer to a Job Result . It contains the histogram of the results, along with metrics such as submission time and completion time. The Resource Interface dynamically abstracts the char-acteristics and capabilities of the available quantum compu-tation assets. It exposes methods such as getCouplingMap ,

getQubitCount , and getNativeGateset that provide information about the resources’ capabilities. Lines 7 to 9 in Listing 1 show querying the resources and receiving the properties of a resource. IV. I NSTANTIATIONS AND DEPLOYMENT

B. Instantiations as Backend Adapters 

In this instantiation, the MQSS Client is wrapped around the existing backend configurations to provide support for pro-gramming models and languages. The configurations support both REST-based remote and RabbitMQ-based HPC access modes, determined by the environment in which they are initiated. 

1) Stack-as-device QDMI Device: 

QDMI, one of the core components of the MQSS, is a C-based API that encapsulates job submission, capability queries, and the life cycle of a quantum system. Any implementation of QDMI specifications referred as QDMI Device 1. The majority of the QDMI devices correspond to a quantum asset. However, the Stack-as-device concept enables us to implement the QDMI specification as a software stack. In this way, various software stacks may exploit the quantum resources of other facilities and software stacks. 

1They can be found here: https://github.com/Munich-Quantum-Software-Stack/MQSS-QDMI-Devices-Suite 

We implement the specifications of the QDMI, using MQSS Client to create a QDMI device for Leibniz Supercomputing Centre (LRZ). The most critical components of the implemen-tation are outlined below: 1) The QDMI_device_initialize function initiate the de-vice. 2) The QDMI_device_session_init function initiate the session based on the given parameters, such as base URL and token , that set using 

QDMI_device_session_set_parameter function. 3) The QDMI_device_job_submit function submits a cir-cuit job, which is created and configured by us-ing the QDMI_device_session_create_device_job and 

QDMI_device_job_set_parameter functions, respec-tively. 

2) C-based QPI Backend: 

As mentioned earlier, QPI is a lightweight, C-based program-ming library that allows embedding quantum circuits in HPC applications. To connect QPI to MQSS Client, we embedded it into the runtime using C bindings. Hereby, users can submit a quantum job in a location and HPC environment without any modifications in the code.

4) Python-based Qiskit and Pennylane Backend: 

Qiskit Framework [4] provides abstractions to create custom backends. Abstractions such as BackendV2 and JobV1 , which are required components to execute a Qiskit circuit. To connect Qiskit to MQSS Client, we inherit the Back-endV2 class to orchestrate the job submission and receive information about the available quantum resources and JobV1 

class to create the CircuitJobRequest based on the OpenQASM [17] representation of the Qiskit Circuit. Similarly, a custom MQSS client further enables PennyLane [18] job submissions through a custom MQSS PennyLane adapter, allowing users to use native PennyLane features within hybrid workflows, such as quantum optimization via the parameter-shift method or gradient-based optimizers. The way to enable that is through the implementation of a PennyLane device [19], where execution occurs via MQSS client calls. Similar to the Qiskit adapter, the client can also fetch dynamic and static metadata, such as the device’s coupling map and basis gates. 

5) MQSS Benchmarking Framework: 

Another front-end module that MQSS Client enables is the MQSS Benchmarking Framework [20]. MQSS Benchmark-ing Framework is a software package that offers high-level interfaces to benchmarking workflows and further separates them into hardware, software, application, and simulation benchmarks. It provides abstract classes for adapters and benchmarks, enabling end users to implement their own. The module also defines core features and implementations of these abstract classes, namely the MQSS adapters, and a few core benchmarks, such as randomized benchmarking [21], QAOA [22], and Quantum Volume [23]. MQSS Client serves as the common entry point and the runtime module across all adapters. It also enables fetching hardware benchmark metrics, such as gate and readout fidelities, or runtime execution char-acteristics (compilation duration per job, quantum/classical time, etc.), without the need to couple individual adapters, as it forwards the required metrics directly to the framework. 2) Performance Experiment: 

For the performance experiment, we evaluate the performance introduced by the MQSS Client by comparing it against a direct implementation across two access modes — HPC and Remote — and two programming languages — C++ and Python. The direct implementation constructs and submits job requests manually. The Python experiment additionally validates the choice of C++ as the core implementation lan-guage, as the Python interface is built on top of the C++ core via pybind11 [16]; any overhead difference between the two languages reflects the cost of the binding layer. To ensure reproducibility and minimize measurement noise, experiments are conducted in the test environment rather than in the production environment, where the system’s load may affect performance results. While for the remote access experiments, we send requests to a remote server that is hosted by LRZ, for the HPC access experiments, the RabbitMQ daemon and the software stack are hosted locally on the same machine as the client. As a result, the reported HPC overhead reflects the cost of the abstraction layer alone, independent of network conditions. We note that submitted jobs are not executed on any quantum backend. B. Evaluation Results 

In this section, we present the results of our two experiments and evaluate them. Table II shows the results of our validation experiments. The results demonstrate that MQSS Client performs as expected across all programming languages and access modes. The HPC access mode outperforms the remote access mode across the programming languages. Even though the results are expected, the TE time is not a suitable metric for evaluating the MQSS Client, as it is highly dependent on the execution of the quantum circuit. The EQC shows variable elapsed time across the target devices, based not onl on access mode and programming language. This directly affects the TE, with on average 84.5% of the TE and a range of 81% to 88%. Even though the effect of the CC, introduced by the MQSS Client, is negligible, taking only 1.12 ∗ 10 −2% on average, it varies more across access modes than across programming lan-guages. This can be attributed to differences in the underlying communication infrastructure, whereas the HPC access mode is responsible for declaring the required messaging queues. However, after the initial communication is established, HPC access mode significantly outperforms HPC requirements on RQs and JSCs, which rely on communication. Table III shows the results of our performance experiments. Unlike validation experiments, we did not target the production environment. For remote access mode experiments, we target the staging environment with a mock device server; likewise, for HPC access mode experiments, we created a local test environment that exhibits the same behavior except for the execution of the quantum circuit. In the HPC access mode, the experiments mostly show predicted results across the access mode, language, and imple-mentation type. The direct implementation in C++ outperforms the other configurations, followed by client implementations in C++ and Python, and lastly, the direct implementation in Python. The TE difference between the C++ implementations is 0.21 seconds, and approximately 9%. The main cause of the difference is the EQC, which is 0.15 seconds longer in the client implementation. Since it is not directly caused by the MQSS Client itself, we can disregard it for more accurate evaluation. Another significant difference is the RES, which is 0.06 seconds higher in the client implementation. It may be caused by the state of the communication infrastructure, along with the overhead introduced by the MQSS Client. The TE difference between the Python implementations is 0.9 seconds, and approximately 2%, where the client imple-mentation outperforms. The main differences observed on the RES and EQC, where they differ by 0.5 and 0.6 seconds. While the direct implementation outperforms on RES, the client implementation outperforms on other parts, even if we disregard the EQC. The TE difference between client implementations is 0.2 seconds and approximately 8%. where the C++ implementa-tion outperforms. The results show similar behaviors. How-ever, we observe a noticeable difference in JSC and RES. Since JobRequest and JobResult carry larger data, this situation may have made the overhead added by these Python bindings more noticeable. We have drawn the following conclusions from our experi-ments: 1) The overhead introduced by the MQSS Client is negli-gible. 2) Using C++ in the core of the MQSS Client provides better performance. 3) Python bindings cause a negligible overhead. Experiments for the remote access mode lead to the same conclusions. Only a significant difference on CC is observed compared to HPC access mode. As stated earlier, this can be explained by the underlying communication infrastructure as CC in the HPC mode responsible for declaring messaging queues. VI. C ONCLUSION AND FUTURE WORK 

In this paper, we present MQSS Client, a unifying, context-aware access layer and programming library that decouples the programming model and the underlying compilation and runtime stack. MQSS Client addresses SDK fragmentation in HPC facilities, enabling diverse programming models to target the same quantum infrastructure without modification. Our evaluation shows that MQSS Client introduces negli-gible overhead compared to direct implementation in C++. Notably, the Python binding outperforms the direct Python implementation across both access modes, demonstrating the benefit of building the client on a compiled C++ core. As future work, we plan to extend the supported job types to include Annealing and Pulse-Level jobs, and to broaden compatibility with additional programming models beyond the current instantiations.
