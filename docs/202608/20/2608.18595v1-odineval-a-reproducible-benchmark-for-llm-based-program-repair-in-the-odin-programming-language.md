## 摘要
仓库级修复基准仍集中于少数主流语言，使得像Odin这样的系统语言在很大程度上未经测试。我们提出了OdinEval，一个基于公共Odin仓库中记录缺陷构建的可复现基准。每个实例将一个issue与基础提交和修复提交、一个黄金补丁、一个特定于issue的回归测试、一个历史工具链和执行记录绑定。准入要求是测试在基础修订版上失败，并在黄金修复后通过。当没有可用的开发者测试时，黑盒测试由同一模型的三个实例独立审查，在两种历史状态下执行，并根据版本化测试编写技能下的记录反馈进行修订。我们在一个共享协议下对六个语言模型在168个过滤实例上进行了评估。Kimi-K3以66.7%的Resolved得分最高，而Qwen3.8-Max以96.4%的Repro得分最高。发布内容包括冻结数据、源代码存档、容器、验证器、模型补丁和审计清单。

## Abstract
Repository-level repair benchmarks still center on a few mainstream languages, leaving systems languages such as Odin largely untested. We present OdinEval, a reproducible benchmark built from documented defects in public Odin repositories. Each instance binds an issue to base and fix commits, a gold patch, an issue-specific regression test, a historical toolchain, and execution records. Admission requires the test to fail on the base revision and pass after the gold fix. When no usable developer test exists, a black-box test is reviewed independently by three instances of the same model, executed in both historical states, and revised from recorded feedback under a versioned Test Writing Skill. We evaluate six language models on 168 filtered instances under one shared protocol. Kimi-K3 records the highest Resolved score at 66.7%, while Qwen3.8-Max has the highest Repro score at 96.4%. The release includes frozen data, source archives, containers, validators, model patches, and audit manifests.

- **研究动机**：现有仓库级程序修复基准（如 Defects4J、BugsInPy、SWE-bench）主要覆盖 Java、Python 等主流语言，而 Odin 这类系统级编程语言几乎未被测试。作者指出，现有方法能否迁移到 Odin 的工具链、项目布局和测试约定，仍是未知问题。
- **核心问题**：如何为 Odin 语言构建一个可复现、可审计的仓库级缺陷修复基准，使 LLM 修复能力能在该语言上被公平、严格地评测。
- **整体含义**：论文提出 OdinEval——一个基于公共 Odin 仓库中已记录缺陷构建的基准，每个实例将 issue 与基础/修复提交、金补丁（gold patch）、针对该 issue 的回归测试、历史工具链及执行记录绑定为一个可审计的证据包，从而为系统语言提供首个可复现的 LLM 修复评估资源。

## 2. 方法论

### 2.1 基准实例契约与准入规则

- 每个实例定义为元组：**I = (q, r_b, r_f, p_g, t, e, m)**，其中 q 为文档化 issue，r_b/r_f 为基础与修复提交，p_g 为金补丁，t 为回归测试，e 为历史工具链与执行规范，m 为审计清单。
- **准入规则**：同一验证器必须同时满足以下两式，实例才被接受：
  - `Run(r_b + t, e) = FAIL`（测试在基础版本失败）
  - `Run(r_b + p_g + t, e) = PASS`（加金补丁后测试通过）
- 基础失败必须归因于文档化行为缺陷，而非补丁应用失败、依赖解析、编译、测试发现或超时等基础设施问题。

- **两阶段流程**：①自动化的“候选画像”，记录仓库 URL、issue/PR 标识、基础与修复版本、变更路径、增删行数等，失败检索也被记录；②“语义治理”，由策展人按书面规则判断候选是否表示可接受的 issue 解决任务——需有明确症状文档、行为与历史变更的可追溯关系、可执行的基线检出路径，以及可行的 issue 特定测试。
- 排除大型迁移、纯格式化改动、版本升级等；补丁大小仅作优先级参考而非准入标准。

- **Skill 引导的黑盒测试生成**（无可用开发者测试时）：

  - 禁止对源码文本、AST 形状、可见性、精确标识符等做白盒断言，禁止泄漏金补丁结构；

## 3. 实验设计

- **任务设定**：给定基础仓库、issue 描述和源码范围，模型生成一个统一补丁；评估器应用补丁、运行验证器，严格实现 Apply（可应用性）、Repro（issue 复现）、Resolved（完整修复）三个关卡。
- **Benchmark**：168 个通过基准构建与过滤的 Odin 修复实例，全部来自公共 Odin 仓库。
- **两种源码定位条件**：
  - **词法定位**：基于 issue 文本的词法检索器返回 top-k 文件；
  - **Oracle 定位**：直接提供开发者变更文件对应的基础版路径（上界条件）。
- **模型**：GPT-5.6-sol、GPT-5.6-terra-max、GLM-5.2、MiniMax-M3、Qwen3.8-Max、Kimi-K3，六个模型共享同一 prompt、实例集、源码包、补丁格式、重试策略、超时和验证器，采用单次尝试的补丁协议，模型不得看到金补丁、修复版本、测试补丁或运行时日志。
- **评估指标**：同一 168 实例固定作为分母，报告 Apply、Repro、Resolved；每个失败按首个失败关卡分类。

## 6. 主要结论与发现

- **主结果**（168 个过滤实例）：

| 模型 | Apply | Repro | Resolved |
|---|---|---|---|
| Kimi-K3 | 100.0% | 93.5% | 66.7% |
| GLM-5.2 | 100.0% | 94.6% | 57.7% |
| GPT-5.6-sol | 100.0% | 90.5% | 50.6% |
| Qwen3.8-Max | 100.0% | 96.4% | 48.8% |
| GPT-5.6-terra-max | 99.4% | 90.5% | 48.8% |
| MiniMax-M3 | 93.5% | 88.7% | 45.8% |

- **关键发现**：
  - Kimi-K3 的 Resolved 分最高（66.7%），比第二名 GLM-5.2 高出 8.9 个百分点；
  - Qwen3.8-Max 的 Repro 分最高（96.4%），但其 Resolved 分比 Kimi-K3 低 17.9 个百分点；
  - **指标选择会改变赢家排名**——只报 Apply 会让四个模型难分高下，只报 Repro 会倾向 Qwen3.8-Max，Resolved 则明显偏向 Kimi-K3；因此三个指标必须分开报告，Repro 不能等同完整修复；
  - Apply 接近饱和（5 个模型 ≥99.4%），而 Resolved 跨度达 20.8 个百分点，说明主要瓶颈在补丁语义正确性而非应用能力。

## 7. 优点

- **证据链完整**：从公共 issue → 版本绑定 → 环境重建 → 双状态运行证据 → 冻结审计工件，每个实例都可独立审计。
- **严格的两状态验证**：只有测试在基础版本失败、加金补丁后通过，才算有效 oracle；且区分行为失败与基础设施失败，防止“测试没跑、环境变了”造成的假阳性。
- **黑盒测试生成受控**：禁止源码文本/AST/隐私断言，禁止金补丁泄漏；3 个同模型独立审查 + 版本化技能 + 结构化反馈重写循环，透明度极高。
- **修复、生成、验证流程解耦**：patch-only 协议避免 agent 循环和隐式工具反馈；词法定位与 oracle 定位分离，清楚区分“定位成本”和“修复能力”。
- **冻结资源与可复现性**：发布校验和、容器镜像摘要、审计清单，区分“重复评估”和“新基准版本”，防止拼接更简单 oracle 来虚报提升。
- **诚实披露局限**：论文多处强调“通过测试不等于语义正确”“同模型审查只是一致性检查”，边界声明清晰。

## 8. 不足与局限

- **实验覆盖有限**：仅 168 个过滤实例，只覆盖 Odin 一种系统语言、6 个私有/商业模型，不构成普遍排序。
- **测试 oracle 充分性风险**：fail-to-pass 测试可能过拟合金补丁的症状或假设；单次通过测试不能证明语义正确性；生成测试存在无法完全排除的泄漏或过拟合风险。
- **单一实验设置**：仅一种源码定位方案（无多定位方法对比、无多轮迭代修复实验），未考虑不同的反馈预算；结论不能被外推到 agent 式或多轮交互场景。
- **同模型自审的局限**：三个审查实例来自同一模型，只能提供一致性验证，不能提供跨模型共识，可能共享系统偏差。
- **选择偏差**：排除大型迁移、重构和无法复现的工具链实例，意味着基准只覆盖“局部、可行为验证”的修复类型，不能代表全部 Odin 开发工作。
- **外部与结论效度**：公共仓库的 issue 结构、项目惯例、Odin 生态的特定性，使迁移到其他系统语言（如 Zig、Nim）或闭源代码库的结论受限。
- **兼容性风险**：历史工具链、验证器更新、模型服务升级都可能改变结果；作者通过 manifest 绑定来缓解，但无法完全消除。
