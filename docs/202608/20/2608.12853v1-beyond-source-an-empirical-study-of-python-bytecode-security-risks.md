## 摘要
Python软件包安全主要围绕源代码展开，但Python运行时可以直接执行字节码，如通过.pyc文件、仅编译模块和序列化代码对象，从而形成检查与执行之间的鸿沟。我们针对作为安全工件的Python字节码进行了一项实证研究。我们测量了PyPI发行版中的字节码暴露程度，使用版本感知工具评估了实际可分析性，测试了CPython运行时在对抗性字节码下的鲁棒性，并检验了从源代码复现字节码发现的可能性。在收集的1,034,843个PyPI工件中，我们识别出7,388个包含字节码的工件，包括228,578个.pyc文件和28,193个工件本地的无源码.pyc文件。对于现代CPython 3.8-3.14字节码，在204,904个适用文件中，至少有一款选定的反编译器能够为204,901个文件生成源码，该结果衡量的是生成行为而非验证功能等价性。工具并非鲁棒：观察到的PyPI字节码会触发托管代码异常和超时，而对抗性变异字节码也会导致反编译器发生原生进程崩溃；这些结果共同产生了17种不同的鲁棒性特征。模糊测试产生了1,009个栈去重后的运行时发现，其中以指针解引用症状为主；261个组表现出潜在的内存破坏特征，且至少91.7%的组在文档标记为不安全的摄入边界之外到达了执行。这些发现均无法从普通Python源码中复现。因此，字节码既是一个可见的生态系统工件，也是一个实际的分析目标，更是一种与安全相关的解释器输入，其行为无需与源码级行为一致。

## Abstract
Python package security is largely source-centric, yet Python runtimes can execute bytecode directly through .pyc files, compiled-only modules, and marshalled code objects, creating an inspection-execution gap. We present an empirical study of Python bytecode as a security artifact. We measure bytecode exposure in PyPI distributions, evaluate practical analyzability using version-aware tooling, assess CPython runtime robustness under adversarial bytecode, and test source-level reproduction of bytecode findings. Across 1,034,843 collected PyPI artifacts, we identify 7,388 bytecode-containing artifacts, including 228,578 .pyc files and 28,193 artifact-local source-less .pyc files. For modern CPython 3.8-3.14 bytecode, at least one selected decompiler emits source for 204,901 of 204,904 in-scope files, a result measuring emission rather than verified functional equivalence. Tools are non-robust: observed PyPI bytecode triggers managed-code exceptions and timeouts, while adversarial mutated bytecode also drives decompilers into native process failures; together these outcomes yield 17 distinct robustness signatures. Fuzzing produces 1,009 stack-deduplicated runtime findings dominated by pointer-dereference symptoms; 261 groups exhibit potential memory-corruption characteristics, and at least 91.7% of groups reach execution beyond the documented-unsafe ingestion boundary. None reproduce from ordinary Python source. Bytecode is thus a visible ecosystem artifact, a practical analysis target, and a security-relevant interpreter input whose behavior need not match source-level behavior.

## 1. 核心问题与整体含义（研究动机和背景）

- 当前 Python 包安全研究高度以源码为中心：扫描器、依赖分析器、恶意包检测工具主要检查源码、元数据、依赖关系，但 Python 运行时可以直接执行字节码（.pyc 文件、仅编译模块、marshal 序列化的 code object）。
- 这导致一个“检查—执行鸿沟”：安全分析人员审查的是源码，而解释器实际执行的是字节码；两者可能不一致，甚至字节码完全缺少对应的源码。
- 已有研究覆盖了 PyPI 恶意包、供应链攻击、运行时 fuzzing，但没有系统回答：字节码在真实发行版中多常见？它是否缺乏本地源码？现有工具能否分析它？恶意字节码能否触发解释器异常终止？字节码级发现能否从源码级复现？
- 论文因此将 Python 字节码视为“一类安全工件”，从四个互补维度进行实证：生态可见性、工具可分析性、运行时鲁棒性、源码可复现性。

## 2. 方法论

- **总体思路**：采用分阶段实证设计，将生态测量与对抗性鲁棒性测试分离，并用“消费方”视角区分两种威胁：
  - 解释器执行边界（代码通道）；
  - 加载但不执行的字节码分析工具（数据通道），如扫描器、反编译器、恶意软件分析流水线。
- **研究问题**：
  - RQ1：字节码在 PyPI 发行版中的暴露模式与包装特征；
  - RQ2：现有版本感知工具对观察到的字节码的实际可分析性；
  - RQ3：CPython 执行变异字节码时暴露的安全相关的鲁棒性故障；
  - RQ4：选定的源码恢复工作流能否通过普通 Python 源码复现字节码级发现。
- **数据收集（Phase 1）**：
  - 从 PyPI 枚举包名，使用 JSON API 获取最新版本文件记录；
  - 对每个包最多保留一个 wheel 和一个 source distribution，且限制为五年内上传；包平衡而非上传平衡；
  - 扫描归档中的 .pyc 文件、pycache 目录、版本信息、动态加载指示符（marshal、importlib、exec、eval、CodeType 等）。
- **可分析性评估（Phase 2）**：
  - 定义五级分析级别：L0 不可加载、L1 可加载、L2 可反汇编、L3 部分反编译、L4 生成源码；
  - 工具选择标准：公开可用、现代 Python 兼容、实际采用、维护稳定性、覆盖主要分析阶段；
  - 使用 CPython marshal 和 dis（参考工具）、Decompyle++（原生 C++ 交叉版本反编译器）和 PyLingual（现代 Python 3 反编译器）；
  - 强调版本感知：每个 .pyc 文件用匹配的 CPython 版本加载、反汇编、反编译。
- **运行时模糊测试（Phase 3）**：
  - 针对 CPython 3.8–3.14，每个版本独立构建 instrumented CPython；
  - 使用该版本 CPython 的 unittest 套件编译为字节码种子；
  - 使用 honggfuzz 2.6 进行 24 小时单 worker 覆盖率引导的字节码变异模糊测试；
  - 对崩溃输入进行 gdb 复现和栈去重；
  - 按信号、故障地址、栈前缀将崩溃分类为可用性/抗分析类与潜在内存破坏类。
- **源码复现分析（Phase 4）**：
  - 对 Phase 3 确认的每个异常输入，使用 PyLingual 和 Decompyle++ 在匹配版本下反编译；
  - 将恢复的源码重新编译为字节码，在同一 CPython 版本下运行，与原始字节码的行为类别比较；
  - 划分为：无源码、编译失败、编译但未复现、源码复现成功。

## 3. 实验设计

- **数据集**：
  - PyPI 上收集的 **1,034,843 个工件**（包平衡，每包至多一个 wheel 和一个 source distribution）；
  - 包含 wheel、source distribution（tar）、zip/其他格式；
  - 其中 **7,388 个工件含字节码**，共 **228,578 个 .pyc 文件**；
  - 版本覆盖 CPython 2.6 到 3.15，重点分析现代 CPython 3.8–3.14 的 204,904 个文件。
- **对比方法**：
  - 分析工具对比：marshal、dis、Decompyle++、PyLingual 的加载、反汇编、反编译成功率与失败模式；
  - 运行时鲁棒性：每个 CPython 版本独立模糊测试，无跨版本“对比方法”，但按版本报告结果分布；
  - 源码复现：用两种反编译器分别尝试恢复源码并重编译运行。
- **Benchmark 性质**：该研究不是典型的模型/算法 benchmark，而是安全实证测量；“基准”是 PyPI 真实工件、CPython 官方 unittest 套件生成的种子，以及每个版本对应的官方解释器构建。

## 4. 资源与算力

- 硬件：Ubuntu 22.04 LTS，Intel Core i9-13900F（32 逻辑 CPU），64 GB RAM，8 TB 磁盘。
- 模糊测试：每个 CPython 版本一个 honggfuzz 单 worker 24 小时，共 7 个版本，总计 **168 小时 CPU 时间**，未使用 GPU。
- 分析工具版本固定：Decompyle++（zrsx/pycdc commit 175e0838e459）、PyLingual 0.1.0（commit 99c74eeff526）、honggfuzz 2.6（commit 01713bdad730）。
- 未提及 GPU 或大规模算力；算力属于中等规模的本地分析。

## 5. 实验数量与充分性

- **主要实验组**：
  - RQ1：1,034,843 个工件扫描，含字节码工件 7,388 个，.pyc 文件 228,578 个；
  - RQ2：20 万级 .pyc 文件的版本感知分析（共 204,904 个），4 种工具，记录 1,098 个失败结果并分类；
  - RQ3：7 个 CPython 版本 × 24 小时模糊测试，共 12,404 个崩溃输入，1,009 个栈去重崩溃组，每个组进行 gdb 复现；
  - RQ4：1,009 个崩溃组 × 2 种反编译器，共 2,018 条工具结果，系统分类失败阶段。
- **充分性评价**：
  - 优点：实验规模大，覆盖生态测量、工具评测、运行时鲁棒性、源码复现四个层面，形成完整证据链；对结果给出保守解释，区分“源码生成”与“语义等价”。
  - 不足：模糊测试每个版本仅运行一次 24 小时单 worker，无独立重复，故结果是存在性证明而非概率估计；未使用 ASAN/MSAN 消毒器，因此“潜在内存破坏”仅基于症状分类；动态加载指示符未进行人工标注精度验证；工具选择和版本范围有限。

## 6. 主要结论与发现

- **RQ1**：字节码在 PyPI 中普遍存在，且 28,193 个 .pyc 文件在工件本地缺少对应源码；在 21,541 个现代 CPython 3.8–3.14 无源 .pyc 文件中，约 2/3 是随发行版携带的导入缓存，1/3 是无缓存目录的裸编译模块（最可能是有意省略源码）。
- **RQ2**：现代 PyPI 字节码几乎全部可被反编译器生成源码（204,901/204,904 达到 L4），但 L4 仅表示“成功生成源码”，不代表功能等价；工具自身存在鲁棒性问题：50 个失败结果（主要为 dis 的 42 个 IndexError、PyLingual 超时、marshal EOFError），其中 PyLingual 的 3 个超时使对应文件仅达到 L3。
- **RQ3**：变异字节码在 CPython 3.8–3.14 全部可触发原生异常终止；1,009 个去重崩溃组中，多数为指针解引用症状，261 个表现出潜在内存破坏特征；至少 91.7% 的崩溃组越过文档标记为不安全的 marshal 摄入边界，进入解释器执行阶段（帧执行、对象运行时、垃圾回收、插桩等）。
- **RQ4**：1,009 个字节码级运行时发现均无法通过选定源码恢复工作流从普通源码复现：662 个无源码生成、285 个编译失败、62 个编译成功但行为不复现；反编译器在对抗性字节码下出现 23 次鲁棒性失败（11 个特征签名），包括 SIGSEGV、SIGABRT、SIGILL、SIGKILL、超时。

## 7. 优点

- **研究问题具有首创性和实践价值**：首次从“检查—执行鸿沟”角度系统度量 Python 字节码在包安全中的角色。
- **方法论严谨**：
  - 明确区分“源码生成”和“功能等价”，避免夸大反编译能力；
  - 版本感知分析避免了工具/解释器版本不匹配造成的误判；
  - 分离两类威胁（执行边界 vs 数据通道），使工具崩溃可被独立解释为安全后果；
  - 设计了四阶段流水线，各阶段输入、输出、归属清晰。
- **工具实现可复现**：开源 PycLens，保留清单、原始记录、失败日志、数据与脚本；对敏感崩溃输入采用“延迟公开”以兼顾可复现性和披露纪律。
- **结果解释保守**：明确将崩溃标记为“鲁棒性证据”而非“漏洞”，并将内存破坏类别描述为“症状性”而非“根因性”。
- **量化充分**：大规模 PyPI 测量 + 20 万级文件工具评估 + 1,009 个去重崩溃组与 2,018 条复现结果，证据强度高。

## 8. 不足与局限

- **数据范围局限**：仅覆盖 PyPI 的固定时间窗、最新版本、每包一个 wheel 和一个 sdist；不包含已删除包（恶意包可能因下架而缺失），也不覆盖安装环境、容器、私有索引。
- **源码可见性判断保守**：仅做工件本地路径匹配的“无源”判断，不验证源码与字节码是否真正对应；动态加载指示符只是静态文本匹配，可能导致误报。
- **模糊测试随机性**：每个版本仅一次 24 小时单 worker 运行，无重复；崩溃数量与分布是点估计，不能用于版本间安全排名。
- **消毒器缺失**：未使用 ASAN/MSAN，因此“潜在内存破坏”只基于故障地址、分配器诊断等信息，不能确认根因或可利用性。
- **工具选择有限**：仅评估 marshal、dis、Decompyle++、PyLingual；其他反编译器或未来版本可能有不同表现；Decompyle++ 实际是 fork 而非上游 pycdc。
- **复现失败是工具受限结论**：RQ4 的“无法复现”是相对所选工作流而言，不等于存在原则上不可源码复现的行为。
- **字节码变异模型局限**：只做字节级变异，未手工构造“有效但恶意”的 marshal 流或正常导入的编译载荷，这类攻击者模型留作未来工作。
